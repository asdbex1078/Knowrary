# tech-doc：技术讲解对话 → 可复看的文档

## 这个 skill 服务的场景

用户向 AI 请教一个自己不熟的技术概念，聊到听懂了，要把它存成半年后还能看懂的文档。
典型主题：注意力机制从 MHA 到 MQA/GQA/MLA 的演进、CPU 分支预测与推测执行、编译器前后端、
内存序、共识算法、GC 算法……**不是**线上排查记录，也不是方案评审纪要。

这类文档的三个特点，决定了下面所有的写法：
1. **没有「跑一遍就知道对不对」**——风险在于 AI 讲错。事实性内容必须可核对。
2. **最值钱的是当时那个让你听懂的类比**，不是教科书式的正确定义。
3. **回看时需要分层**——先看一句话，再看够用版，想深入再往下。

## 固定路径

- 发布脚本：`/Users/moka/IdeaProjects/Knowrary/tools/tech-doc/publish-doc.sh`
- 目标分支：**main**（`TECHDOC_BRANCH` 可覆盖）
- 目标位置：`doc/技术文档/<领域>/<主题>.md`
  - **领域取 Knowrary vault 里 `field` 的值**，不是随手起的分类。现有领域只有两个：
    `计算机体系结构`（vault 里 `nodes/01-理论基础` ~ `07-高级语言` 全部属于它）、`AI-Agent`。
    查证方式：`ls fields/` 或看任一节点 frontmatter 的 `field`。
  - 编译原理、JVM、汇编、内存模型这些**是 `计算机体系结构` 下的子区，不是领域**，别给它们单开目录。
  - 确实是新领域（例如 Transformer 内部机制更像 `LLM` 而非 `AI-Agent`）才新建，并在汇报时明确说
    「新建了领域 X」，让用户决定是否接受——领域一旦散开，vault 和文档就对不上了。
  - 文件名用主题本身，**不加日期前缀**——概念文档会被反复补充修订，日期写在 frontmatter 里
  - 例：`doc/技术文档/计算机体系结构/推测执行与分支预测.md`、`doc/技术文档/LLM/注意力机制-从MHA到MLA.md`
- 草稿一律先写到本次会话的 scratchpad，**不要**写进仓库工作区

## 为什么不直接 git add

用户会在各种 feature 分支上开发。脚本用 `hash-object` / `commit-tree` / `update-ref` 直接在 main 上造提交，
全程不切分支、不碰工作区、不碰仓库 index，当前分支有多少未提交改动都无所谓。
（若当时恰好 checkout 在 main 上，脚本自动改走「落盘 + 路径受限提交」，只提交这一个文件，其余脏改动不动。）

## 流程

### 1. 定范围与类型

默认范围 = 本次会话里围绕**一个概念**讲透的那一段。会话里聊了两个不相干的概念，就是两篇，先问用户写哪个。

| 类型 | 用于 | 例子 | 骨架重点 |
|---|---|---|---|
| **原理型** | 一个机制到底怎么工作 | CPU 推测执行、MESI 协议 | 它解决什么问题 → 机制本身 → 代价与边界 |
| **演进型** | 一条技术线为什么走到今天 | MHA→MQA→GQA→MLA、GC 算法演进 | 每一代**被什么逼出来的** → 改了什么 → 换来什么代价 |
| **辨析型** | 几个易混概念的区别 | 进程/线程/协程、幻读与不可重复读 | 先给判别式 → 逐个拆 → 对照表 |
| **全景型** | 一整块领域的地图 | 编译器从源码到机器码 | 全景图 → 每一站做什么 → 站与站之间传什么 |

选错类型比写得差影响更大：演进型写成原理型，就会丢掉「为什么会有这一代」这个最关键的线索。

### 2. 写草稿（scratchpad）

frontmatter：
```markdown
---
title: 注意力机制：从 MHA 到 MLA
field: LLM          # 取 vault 的 field 值；现有为 计算机体系结构 / AI-Agent，新建需说明
type: 演进型
tags: [Transformer, 注意力机制, KV-Cache, 推理优化]
created: 2026-09-14
updated: 2026-09-14
source: 与 Claude 的会话
confidence: 需核实   # 已核实 / 需核实（含未经查证的具体数字或论文信息时用后者）
---
```

正文分层，**这个分层是硬要求**：

```markdown
## 一句话
（30 字以内。半年后扫一眼就能想起来的那句话。）

## 为什么会有这东西
（不讲这个，后面全是背公式。演进型尤其要写清每一代是被什么逼出来的。）

## 够用版
（读完能跟人讲清楚、能看懂相关代码/论文摘要的程度。主体部分。）

## 深入
（推导、边界条件、实现细节。可以没有；宁可没有也别注水。）

## 我当时卡在哪
（会话里你真实追问过、绕过弯的点。逐条写「我以为 X → 实际是 Y → 因为 Z」。）

## 容易混的
（与相邻概念的边界。辨析型里这节前置成主体。）

## 出处与待核实
（论文名 + 年份 + arXiv 号、标准号、官方文档链接；以及标了「⚠️」的待核实项。）
```

用不上的章节直接删，但 `## 一句话`、`## 够用版`、`## 我当时卡在哪` 三节不许省。

### 3. 写作铁律

**关于准确性——这是这类文档的头号风险**
- AI（也就是你自己）在讲解时给出的**具体数字、论文名、发表年份、版本号、性能提升百分比**是幻觉高发区。
  凡是会话里没有可靠出处的这类内容，要么用 WebSearch 核实后补上出处，要么原样保留并标 `⚠️ 未核实`。
  **绝对不许为了文档好看，把不确定的东西写成肯定句。**
- 机制性描述（「MQA 让所有 head 共享同一份 K/V」）和量化断言（「KV cache 降到 1/8」）区别对待：
  前者错了容易被发现，后者错了会被当真。量化断言一律要出处。
- 全篇有任何一处标了 `⚠️`，frontmatter 的 `confidence` 就写 `需核实`。

**关于类比**
- 会话里那个让用户听懂的类比，**原样保留**，这是文档最不可替代的部分。
- 但每个类比后面补一句它在哪里失效（「这个类比在 X 上不成立，因为……」）。
  类比不标边界，半年后会变成错误认知的源头。

**关于结构**
- 按**概念的逻辑顺序**重组，不要按对话发生的顺序。对话是东问西答的，文档不能是。
- 数字、公式、量级、算式（KV cache 占用怎么算之类）必须留，这是「够用版」和「听个响」的分界线。
- 会话里画过的示意图 / ASCII 图 / 表格，保留。文字描述替代不了。
- 代码片段保留，但只留能说明机制的那几行，不要整段贴。

**关于「我当时卡在哪」**
- 这节最容易被偷懒省掉，但它是这篇文档区别于「随便一篇博客」的地方。
- 用户当时的困惑点，半年后大概率还会困惑。逐条写清「我以为 X → 实际是 Y → 因为 Z」。
- 用户没明说但反复追问了三次的点，也算卡住，要写。

**不要做的**
- 不要复述 AI 的客套、铺垫、「好问题！」这类话。
- 不要把整段对话原文粘进去——那是聊天记录。
- 不要补写会话里没聊到的内容来「让文档完整」。缺了就在末尾列「本篇没覆盖」。
- 不要为凑结构写空章节。

### 4. 发布前自检

- 事实核查：`⚠️` 标注是否都到位？量化断言是否都有出处？
- 分层检查：`## 一句话` 是不是真的一句话？「够用版」有没有滑进「深入」的细节里？
- 脱敏：这仓库在 GitHub 上。若讲解中夹带了公司内部系统、客户名、内网地址、token，一律删除或替换。
  纯公开技术知识通常无此问题，但混讲了内部实践时要留意。

### 5. 给用户看，等确认

汇报：文件路径、类型、`## 一句话`的内容、各章节大纲、**所有标了 `⚠️` 的待核实项**。
用户明确说推/发布，才进第 6 步。要改就改草稿，重新汇报。

### 6. 发布

```bash
bash /Users/moka/IdeaProjects/Knowrary/tools/tech-doc/publish-doc.sh \
  "<scratchpad 里的草稿路径>" \
  "doc/技术文档/LLM/注意力机制-从MHA到MLA.md" \
  "docs: 注意力机制从 MHA 到 MLA 的演进"
```

脚本自己做完这些：fetch 定基 → 造提交 → 推送（默认重试 6 次，本机 SSH 经代理有已知抖动）
→ **推送成功后才移动本地 main ref**。若推送期间远端前进导致非快进，自动基于最新 origin/main
重造提交再推（最多 3 次），不会把本地 main 搞成分叉。成功后打印 GitHub 链接，转给用户。

失败时脚本 exit 1，**本地分支没被动过，提交对象也还在对象库里**，稍后重跑同一条命令即可。
不要因为一次推送失败就断言"网络有问题"——先看脚本打印的最后一条错误再说。
本地 main 与 origin/main 已分叉时脚本会直接罢工并说明原因，这时该由用户决定怎么合，不要替他 merge。

只想落本地不推：`TECHDOC_NO_PUSH=1`。

### 7. 修订已有文档

同一主题聊到新东西时，**改原文件而不是新建一篇**：读回 main 上的旧版本 → 合并新内容 →
更新 frontmatter 的 `updated` → 用同一条命令发布（脚本按路径覆盖，内容没变则不产生空提交）。

```bash
git show main:"doc/技术文档/LLM/注意力机制-从MHA到MLA.md" > <scratchpad>/旧版.md
```

### 8. 收尾

提一句（不要自作主张执行）：这篇里的概念可以走 `knowrary-import` 拆成知识图谱节点。
两者分工：本 skill 产出**一篇连贯的讲解**（适合从头读一遍），knowrary-import 产出**可独立复习的节点**（适合按概念检索和串联）。
`field` 字段是刻意和 vault 的 `fields/` 对齐的，方便之后导入。

## 不做的事

- 不把草稿写进仓库工作区，不 `git add` 用户当前分支的任何东西。
- 不在用户确认前提交或推送。
- 不动 release/staging 等保护分支，不因为「顺手」去合并分支。
- 不把没核实的具体数字、论文名、年份写成肯定句。
