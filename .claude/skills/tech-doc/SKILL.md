# tech-doc：对话 → 技术文档 → 固定分支

## 固定路径

- 发布脚本：`/Users/moka/IdeaProjects/Knowrary/tools/tech-doc/publish-doc.sh`
- 目标分支：**main**（`TECHDOC_BRANCH` 可覆盖）
- 目标目录：`doc/技术文档/`
- 文件名：`YYYY-MM-DD-主题.md`，主题用中文短语，不超过 20 字，不带空格（例：`2026-09-14-连接池泄漏排查.md`）
- 草稿一律先写到本次会话的 scratchpad 目录，**不要**写进仓库工作区

## 为什么不直接 git add

用户会在各种 feature 分支上开发。脚本用 `hash-object` / `commit-tree` / `update-ref` 直接在 main 上造提交，
全程不切分支、不碰工作区、不碰仓库 index，当前分支有多少未提交改动都无所谓。
（若当时恰好 checkout 在 main 上，脚本自动改走「落盘 + 路径受限提交」，只提交这一个文件，其余脏改动不动。）

## 流程

### 1. 定范围
默认范围 = 本次会话里围绕某一个主题的完整过程。若会话里有多个不相干主题，**先问用户写哪个**，不要一锅端。
一次只产出一篇；两个主题就是两篇。

### 2. 定类型，选骨架
| 类型 | 用于 | 骨架 |
|---|---|---|
| 排查型 | 线上问题、bug、诡异现象 | 现象 → 结论 → 排查过程 → 根因 → 修复与验证 → 踩过的坑 |
| 方案型 | 设计、选型、架构讨论 | 背景与目标 → 结论（选了什么） → 候选方案对比 → 决策依据 → 实施步骤 → 遗留问题 |
| 梳理型 | 把某块知识/链路搞明白了 | 一句话概括 → 全景图 → 各部分详解 → 关键结论 → 易混淆点 |
| 手册型 | 可重复执行的操作 | 适用场景 → 前置条件 → 步骤（可复制命令） → 验证 → 失败时怎么办 |

### 3. 写草稿（scratchpad）

frontmatter 固定这几个字段：
```markdown
---
title: 连接池泄漏排查
date: 2026-09-14
type: 排查型
tags: [MySQL, 连接池, HikariCP]
source: 与 Claude 的会话
status: verified   # verified = 文中结论均已实测；draft = 含未验证推断
---
```

正文写作铁律：
- **结论前置**：正文第一段就是结论，一到三句话。别让读者读完排查过程才知道答案。
- **只写真实发生过的事**。会话里没验证的推断，必须显式标注「⚠️ 未验证」，不许写成肯定句。
- **命令、报错、代码原样保留**，用代码块；引用仓库代码写成 `path/to/file.java:120`。
- **补主语**。对话里靠上下文省略的东西（哪个服务、哪个环境、哪张表、哪个集群）在文档里必须写全——读者是半年后的你，没有上下文。
- **弯路要留，但要压缩**：走错的路写进「踩过的坑」，一条一行，写清「当时以为 X，实际是 Y，因为 Z」。中间无效的来回、寒暄、道歉一律删掉。
- **不编造**：会话里没出现的数字、版本号、结论，一个都不许补。缺了就写「未确认」。
- 篇幅按内容给，不注水；一次简单排查 100 行就够，别为凑结构写空章节——用不上的章节直接删。

### 4. 发布前脱敏自检（必做）
逐条扫一遍草稿，命中就改：
- token / password / AK / SK / 私钥 / cookie → 一律删除或替换成 `<REDACTED>`
- 内网 IP、内部域名、数据库连接串 → 保留结构，替换具体值（`10.x.x.x`、`<db-host>`）
- 客户名、候选人姓名、手机号、邮箱 → 匿名化（`某客户`、`候选人A`）
- 公司内部系统只留名字和原理，不留可直接调用的地址+凭证组合

仓库在 GitHub 上，这一步没得商量。

### 5. 给用户看，等确认
向用户汇报：文件名、类型、大纲（各级标题）、核心结论一句话、被标为「未验证」的点、脱敏改了什么。
**用户明确说推/发布，才进第 6 步。** 用户要改就改草稿，重新汇报。

### 6. 发布
```bash
bash /Users/moka/IdeaProjects/Knowrary/tools/tech-doc/publish-doc.sh \
  "<scratchpad 里的草稿路径>" \
  "doc/技术文档/2026-09-14-连接池泄漏排查.md" \
  "docs: 连接池泄漏排查记录"
```
脚本自己做完这些：fetch 定基 → 造提交 → 推送（默认重试 6 次，本机 SSH 经代理有已知抖动）
→ **推送成功后才移动本地 main ref**。若推送期间远端前进导致非快进，自动基于最新 origin/main
重造提交再推（最多 3 次），不会把本地 main 搞成分叉。成功后打印 GitHub 链接，转给用户。

失败时脚本 exit 1，**本地分支没被动过，提交对象也还在对象库里**，稍后重跑同一条命令即可。
不要因为一次推送失败就断言"网络有问题"——先看脚本打印的最后一条错误再说。
本地 main 与 origin/main 已分叉时脚本会直接罢工并说明原因，这时该由用户决定怎么合，不要替他 merge。

只想落本地不推：`TECHDOC_NO_PUSH=1`。

### 7. 收尾
提一句（不要自作主张执行）：这篇里的概念如果要拆成知识图谱节点，可以走 `knowrary-import`。

## 不做的事

- 不把草稿写进仓库工作区，不 `git add` 用户当前分支的任何东西。
- 不在用户确认前提交或推送。
- 不改 main 上的已有文档；同名文件已存在时，先告诉用户是覆盖还是换名。
- 不动 release/staging 等保护分支，不因为「顺手」去合并分支。
- 不把整段对话原文粘进文档——那是聊天记录，不是技术文档。
