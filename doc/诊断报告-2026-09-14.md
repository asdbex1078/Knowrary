## 二、做对的地方（不要动）

1. **你把 PARA + Zettelkasten 的完整流水线真的搭起来了**，只是没给它命名：
   - Fleeting（临时）＝ `day-info/pool`
   - Literature（文献）＝ `harness/`、`llm/`
   - Permanent（永久）＝ `nodes/`
   - MOC（内容地图）＝ `fields/`
   - Archive（归档）＝ `.knowrary/backup`、`doc/设计文档` 旧版

   这套分层是 PKM 里的标准答案，你的目录结构天然符合它。

2. **关系有方向、有类型、有族**，并且规范里明确"反链由解析器推导，不重复回填"。这条纪律能省掉后期大量的数据不一致。

3. **派生数据与源数据分离**：`index.json` 是缓存可以被删掉重建，`layout.json` 是视图状态，md 是内容。三者职责不混，这是很多知识库做几年之后烂掉的根本原因，你一开始就避开了。

4. **`day-info` 的"收集频率高、推送频率低"漏斗设计**是对的——替你消化信息，不替你生产焦虑。

## 三、问题清单

### P0 · 图谱被切成两座孤岛（跨领域边 = 0）

连通分量实测：

- 分量 1：**61 个节点**，全部属 `计算机体系结构`
- 分量 2：**10 个节点**，全部属 `AI-Agent`
- 分量 3：**1 个节点**，`fields/计算机体系结构.md`（见 P1）

`AI-Agent` 那 10 张卡（长程任务生命周期、取消语义、崩溃恢复、幂等键、事件日志、乐观锁…）与主图 **一条边都没有**。

这不只是"看起来散"，而是结构性的：跨领域连接恰恰是知识网产生新洞察的地方。你现在的图谱更像两本并排的书，而不是一张网。

**最自然的造桥点**（都是内容上本来就成立的）：

- `AI-Agent / 崩溃恢复` 依赖:: `OS`（进程与崩溃是 OS 层语义）
- `AI-Agent / 长程Agent最小架构` 参考:: `eBPF`（同为内核侧可控执行/观测）
- `AI-Agent / 乐观锁` 类比:: 并发控制（对应 `内存`/`程序的内存布局` 里的原子性话题）
- `AI-Agent / 任务暂停与恢复` 类比:: `栈帧`（都是"执行现场的快照与还原"）
- 或更省事：建一张跨域概念卡 `状态机`/`检查点`，两边各挂几条

同时 **`AI-Agent` 缺领域总览**（`fields/` 只有一个文件）。补一个 `fields/AI-Agent.md`，它天然就是这座桥。

### P1 · 领域总览（MOC）成了游离节点

`fields/计算机体系结构.md` 的度 = 0。原因很具体：**它把所有链接放进了一个 ``` 代码块里**。代码块里的 `[[ ]]` 不是链接，图谱解析器不认，Obsidian 的图谱视图也不认。

所以你在 Obsidian 里看到的这张"知识树"，其实是一段纯文本插图。它读起来很清楚，但对机器是完全空白的。

**修法**：保留代码块做"人读的树"，另外在下方补一个真正的 `## 关系` 列表作为"机器读的边"。两者并存不冲突：

```markdown
## 关系
- 包含:: [[图灵机]] — 整条链的根
- 包含:: [[计算机硬件]]
- 包含:: [[ISA]]
- 包含:: [[编译原理]]
```

这个文件一旦有边，它会立刻变成整张图的中枢节点。

### P1 · 13 处关系环（结构 / 依赖族出现方向矛盾）

实测 warning 全部是环，且集中在编译工具链：

- `ISA → LLVM → ISA`、`ISA → 编译器后端 → ISA`
- `GCC → ISA → GCC`、`GCC → 编译器前端 → GCC`
- `GraalVM → JIT → GraalVM`、`GraalVM → 解释器 → GraalVM`
- `IR → LLVM → IR`、`IR → eBPF → IR`
- `C语言 → 编译原理 → 汇编语言 → C语言`

**根因**：同一对节点上，一边用了"规格 ←实现— 实现者"，另一边又用了"实现者 —依赖→ 规格"（或 `包含` / `部件` 与 `实现` 混用）。例如 LLVM 既是"实现了某个 ISA 的后端"，又"依赖 ISA 的规格"，两条边一起写就成环。

**修法（一条规则就够）**：让"规格层"永远被动。ISA / IR 这类规格节点**只写出一条边指向自己的组成部分**，不再接收"依赖"类反向边；工具链节点（GCC / LLVM / GraalVM）统一用 `实现::` 或 `编译目标::` 指向规格。

环的代价不是洁癖问题——它会让拓扑排序、依赖影响分析、历史视图全部失效。

### P2 · 13 张卡"有节点、没连线"

关系区为空的节点：

`哈佛架构`、`数论`、`EPROM`、`Intel手册`、`RAM`、`总线`、`控制器`、`运算器`、`通用寄存器`、`数据段`、`字节码`、`harness`、`乐观锁`

最讽刺的是 `总线`——总览里你还专门记了"原图红字'缺乏总线'→ 已建 `[[总线]]`"，但总建成之后它自己没连任何东西。

**修法**：每张卡至少补 1 条出边，优先级：`属于::` 父节点 > `部件::` > `实例::`。这是机械劳动，10 分钟能补完 11 张。

### P2 · 13 处"正文有链接、关系区没有" → 两套连接视图不一致

例如 `高速缓存.md` 正文写了 `[[存储器层次结构]]`，但关系区只有 `相关:: [[内存]]`。

因为你规范里写明了"只有 `## 关系` 区块会被解析器读取"，后果是：

- Obsidian 图谱里 → 这条边**在**
- Knowrary 结构视图里 → 这条边**不在**

同一份知识两套连接事实，时间久了你会开始怀疑"到底哪个才是真的"。

值得注意的是，**`AI-Agent` 的 4 个节点几乎全靠正文链接互连**（`长程Agent最小架构`、`长程任务生命周期`、`Agent事件日志`、`外部副作用与幂等键`），这也解释了为什么它们内部看起来有关系但统计上成岛。

**修法**：定一条硬规则——**`[[ ]]` 只在 `## 关系` 区里出现**；正文提到别的概念时用纯文本（或 `aliases` 承载别名）。这样两套视图永远同源。

### P2 · 元数据补全率偏低

- `type`：**63 / 72 缺失**（88% 没有）
- `year`：仅 18 / 72
- `status`：只用在 stub 上

规范里 `type` 是可选字段，所以不算违规。但节点一过百，`type` 就是你唯一的"内容维度"筛选器（`AI-Agent` 那几个节点已经用了 `机制`/`模式`，说明你其实是想要这个维度的）。

建议先给 `AI-Agent` 和 `06-编译原理` 两块补——这两块概念类型最清晰。

### P3 · 规范文档与实践不一致（命名）

规范第 2 节写的是：

> 文件名使用小写英文、拼音或稳定的短横线标识，例如 `attention-mechanism.md`

实际是**全中文文件名**（`图灵机.md`、`高速缓存.md`），`id` 也是中文显示名。

中文文件名本身**完全没问题**（Obsidian 原生支持，对中文用户可读性更高）。问题是规范在骗人：未来某个 `knowrary check` 加上命名校验，71 个文件会全量报错；或者某天的你按规范把 71 个文件重命名一遍——纯亏。

**修法（推荐，成本最低）**：改规范承认现实——"id 用中文，英文 id 通过 `aliases` 承载"。而不是改 71 个文件。

### P3 · 子领域信息只活在目录路径里

目录按 `01-理论基础` … `07-高级语言` 分层（人工浏览很友好），但 frontmatter 的 `field` 62 个全是 `计算机体系结构`。

于是 `01-07` 这层**子领域语义只存在于文件路径**，没有进 md。后果：

- 把文件挪出目录，子领域信息就丢了
- `index.json` 的 `by_field` 只有 2 个桶，无法按子领域统计、筛选、上色
- 图谱上只能靠 `属于/包含` 边反推子领域，实际上很多节点没这条边

**修法**：加可选 `subfield` 字段（或 `field: 计算机体系结构/编译原理` 路径式），让目录与元数据同源。这样 `01-理论基础` 这种编号目录也能改成 `理论基础` 不带序号，序号交给工具生成。

### P3 · 漏斗中间层断裂（最需要长期注意的一条）

| 层 | 现状 |
| --- | --- |
| 收集池 `day-info/` | 每天 19:00 自动跑，已积累 3 天池 + 2 期周报 |
| 文献笔记 `harness/`、`llm/` | **2 个文件，`llm/` 是空目录** |
| 永久笔记 `nodes/` | 71 张（但 62 张的 `source` 是 `知识图谱zhis.jpg`，是**旧图迁移**来的） |
| MOC `fields/` | 1 个 |

也就是说，现在有两段互不相接的产线：

- **产线 A（一次性）**：手画的 `知识图谱zhis.jpg` → 迁移成 62 张卡
- **产线 B（在跑）**：`day-info` 每天收集 → ……这里断了……

`day-info` 每天在往里灌，`nodes/` 却没有一条从它长出来的新卡。收集池在膨胀，知识库没在增长——这是 PKM 里最典型、也最隐蔽的失败模式（**收集的爽感替代了消化的成就感**）。

**可执行的最小规则**：

> 每期周报必须产出 **≥ 1 张** `nodes/` 永久卡。

不要求读完再写，只要求"读到一个东西 → 用自己的话拆一张卡 → 挂到图上"。这样产线 B 就接上了。

### P4 · 小瑕疵

- `doc/设计文档/` 里第一版（27KB）与第二版（54KB）并存，第二版是唯一生效的 → 第一版移入 `doc/archive/` 或在开头标 `superseded`。
- 规范第 5 节枚举的族类型（依赖族只列了"依赖、基于、实现"）**漏了** `支撑/前提/控制/产出/使用/编译目标` —— 而 `relation-types.json` 里有，且 `使用`(16)、`产出`(11)、`控制`(9) 都是高频类型。规范滞后于数据。建议规范改成"类型枚举以 `relation-types.json` 为准"。
- 度 ≤ 2 的节点 15 个（含根节点 `图灵机` 度仅 2、`哈佛架构` 度 1）—— 边缘卡偏多，是 P0/P2 的副产品，修完前几项会自然缓解。
