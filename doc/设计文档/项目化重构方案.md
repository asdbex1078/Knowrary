## Context

现在的组织单元是「学习计划」（`plans.json`，3 份：Transformer 44 点、AI技术发展史 30 点、计组 0 点）。
要把组织单元升一级成「项目」：一个项目下有学习计划、考试、错题本、面试方案、一段对话，
由对话指挥 agent，系统提示词从项目配置生成，不同项目分开学。

真正的难题是**项目之间会重叠**。第一个项目 Transformer、第二个 CNN、
第三个 NLP——NLP 既是前两个的父级，CNN 和 Transformer 之间又有交集（反向传播、梯度下降）。

另外三个想法一并设计：学/考双态标记、项目独立画布 + 同步到全局、学习日历。
以及一个反复出现的疑问：**要不要上数据库**（§7）。

## 1. 核心判断：项目是「视角」，不是「容器」

推理链：

1. 知识图谱全局唯一——md 是唯一真值源，这是整个项目最硬的纪律。
2. **复习调度也必须全局唯一。** 同一个大脑不可能"在 NLP 项目里记得 Transformer、
   在 Transformer 项目里忘了"。这是生理事实，不是技术选择。
3. 所以项目**不能拥有节点，只能引用一组 node_id**。

一旦项目只是选集，下面三种情况**全部自动消解，不需要任何额外建模**：

| 场景 | 怎么自动成立 |
| --- | --- |
| **交集**（Transformer ∩ CNN = 反向传播、梯度下降） | 两个项目的清单里都列它，掌握度是同一个 |
| **子集**（NLP ⊃ Transformer） | NLP 的选集包含 Transformer 的全部点，**不需要显式父子** |
| **后来的父级**（先建 Transformer，再建 NLP） | 建 NLP 时把已有节点选进去，**不用重构已有项目** |

**已确认：不做显式父子关系。** 一旦有 parent 字段就要回答"子进度算不算父的、父改了子跟不跟、
能不能有两个父"，而这些答案选集重叠免费就给了。更重要的是——**层次本来就该在知识层表达**：
要说"NLP 包含 Transformer"，那是图上一条 `包含::` 边。在项目层再建一套层级 = 同一件事存两份，必然漂移。

**必须在界面上说清、否则会被当成 bug 的一条**：在 A 项目复习了 Transformer，B 项目里它也显示"已复习"。
这是对的——同一个大脑。今日清单按 node_id 去重（`core/coach.py` 已实现），不会重复出现。

## 2. 哪些建实体，哪些是派生视图

| 需求里的东西 | 做法 |
| --- | --- |
| 学习计划 | **实体**：项目 `lists` 里 `kind=学习` 的一条 |
| 领域地图 | **实体**：项目 `lists` 里 `kind=领域` 的一条（拆解口径不同，数据结构相同） |
| 面试方案 | **实体**：项目 `lists` 里 `kind=面试` 的一条（可以有多条，一家公司一条） |
| 考试 | **派生**：按项目范围调 `/api/quiz`，不建实体 |
| 错题本 | **派生**：`quiz-log` 按项目范围过滤聚合（复用 `core.wrong_nodes`） |
| 学习进度 | **派生**：`review-log` + `quiz-log` 现算（沿用 F10.2 的"progress 不落盘"） |
| 对话 | **实体**：按项目分文件的 JSONL（另一 session 实现，契约见 §8） |

**绝不给每个项目建自己的错题本。** 同一节点在两个项目里答错就会有两份记录，必然漂移——
和"进度派生不落盘"是同一条纪律。

## 3. 数据模型：`plans.json` → `projects.json`

```json
{
  "schema_version": 2,
  "revision": 11,
  "updated_at": "…",
  "projects": {
    "transformer": {
      "name": "Transformer", "goal": "三个月吃透…",
      "coach": "大模型", "field": "AI",
      "created": "2026-09-15", "target_date": null,
      "weekly_hours": 10, "daily_quota": 3,
      "lists": [
        { "kind": "学习", "name": "主线", "goal": "三个月吃透…",
          "stages": [ { "name": "…", "deadline": null, "points": [ {"id","name","why","load"} ] } ] },
        { "kind": "面试", "name": "字节一面", "goal": "JD 原文", "coach": "Java 后端开发",
          "stages": [ … ] },
        { "kind": "领域", "name": "NLP 全景", "stages": [ … ] }
      ]
    }
  }
}
```

- **`kind` 不取消，但降一层：它属于「清单」，不属于「项目」。**（2026-09-16 修订，见下）
- 一个项目下挂一个 `lists` 数组，每条是一份清单：学习主线、某一家的面试方案、某个领域的全景图。
  三者 `stages` 结构完全一致，所以 `progress_of` / `current_stage` 全部复用，只是传入不同的 stages。

> **为什么不是原来的「取消 kind + 内嵌一个 `interview`」（2026-09-16 修订）**
>
> 本方案初稿写于「学习 / 面试」两种口径的时代。2026-09-15 又落地了第三种：`kind: 领域`
> ——「初始化一个领域的所有点」并成了拆解口径之一，配第三份模板
> （`prompts/plan.md` / `plan-interview.md` / `plan-map.md`，见设计文档 F10.3b）。
> 于是「有没有 `interview`」这个二元判据不够用了：再加一个 `map` 内嵌槽就是三个并列具名槽，
> 而且答不了「能不能有两份面试方案（两家公司）」。
>
> 关键在于**看清 `kind` 到底决定什么**：它只决定两件事——**用哪份拆解模板**
> （`server/plans.py` 的 `TEMPLATES` / `OPS`）、**用哪套出题口径**（`server/quiz.py` 的 `STYLES`）。
> 它从来不是"项目的类型"，而是"这份清单是怎么拆出来的"。放在项目上是层级放错了。
>
> 代价是零：§9 本来就要把 `progress_of` / `current_stage` 从"收整个 plan"改成"收 stages"，
> 收成数组是同一次重构；而 `interview` 那个特例直接消失，少一条分支。

### 迁移（已确认：全部自动迁，先备份）

| 现有 | 迁成 |
| --- | --- |
| `新计划`（Transformer，kind=学习，44 点） | 项目 `transformer`，一条 `kind=学习` 的清单 |
| `新计划3`（AI技术发展史，kind=学习，30 点） | 项目 `ai-history`，同上 |
| `新计划2`（计组，kind=学习，0 阶段 0 点） | 项目 `arch`（保留空壳，由人决定删不删）——**id 只允许 ASCII**，见下 |
| 将来任何 `kind=面试` / `kind=领域` 的 | 项目 + `lists` 里对应 kind 的一条（`goal` 原样跟着走） |

- **项目 id 只允许 ASCII**（`[A-Za-z0-9_-]`），显示名另存 `name`。原因是 id 会成为
  `.knowrary/chat/<project_id>/` 的目录名（§8），中文目录名加上将来改名，迁起来纯属自找麻烦。
  所以 `计组` 迁成 `arch`，`name` 仍是「计组」。
- 迁移前整份备份到 `.knowrary/backup/migrate-projects-<时间戳>/`，可回滚。
- `load_projects` 读到 `schema_version: 1` 或顶层是 `plans` 时**在内存里就地升级**，
  沿用 `core/review.py` v1→v2 的做法：**读不写盘**，下次保存才落成 v2。
- **迁移时要报出来的数据问题**：`transformer` 项目的 `field` 是 `AI-Agent`，
  而这个领域今天已经被改名清空了（现在只有 `AI` / `Agent` / `计算机体系结构`）——
  这会让「建」按钮算错落脚点（与 2026-09-15 修过的「计划领域没参与落脚点计算」是同一类问题）。迁移脚本要检测并提示，不擅自改。

## 4. 学 / 考 双态标记

目标：每个点左边一个「学」、右边一个「考」，学完 / 考完各自变绿，一眼看出这个点卡在哪一步。

**这不是新数据，是五档掌握度的另一种编码**，更适合一眼扫。仍然全部派生：

| 标记 | 状态 | 判据 |
| --- | --- | --- |
| **学** | 灰 | 未建（图里没有这个 id） |
| | 红 | 只有壳（节点在、`status: stub`） |
| | 绿 | 有正文 |
| **考** | 灰 | 没考过（`review-log` 无记录，且错题本里没有） |
| | 红 | **错题本（`quiz-log`）里有它**，或 `review-log` 最近一次是「忘了」 |
| | 黄 | 最近一次是「模糊」，或已到期（`next_due ≤ today`） |
| | 绿 | 最近一次是「记得」、没到期，**且错题本里没有它** |

**判据的优先级必须写死：错题本压过自评。**（2026-09-16 补）「考」有两个数据源，而且它们**可以合法地互相矛盾**：
`review-log` 的三档来自**我自评**，`quiz-log` 里模型判的 `missed` / `wrong` 才是错题本
（`core.wrong_nodes` 聚合的就是它）。F9.4 定过**模型判分只许降级、且要我点一下才生效**——
所以完全可能出现「测验里模型判我答漏了，我自评点了『记得』」：`review-log` 绿，错题本里却躺着它。
这时显示绿就把错题盖住了，而错题本的全部价值恰恰在这里。所以只要错题本里有它，「考」就是红的。

**考必须有"红/黄"而不只是"绿/灰"**：考过但答错，和没考过是两回事——前者更该被拉回来重考。
直接"考完就变绿"会掩盖答错的情况，而错题本的价值恰恰在这里。

呈现位置：
- 项目面板每个点前（替换现有的五档 chip，信息量更大、更省横向空间）
- **画布节点上**：右上角现在已有"到期金色圆点"（`canvas/shapes.js:131`），扩成左下角两个小方块。
  缩小到簇卡片时不画（性能守则）。

### 「学完之后知识图谱自动扩展、自动收入」

理解为：一个点从「未建」变成「已建」时，自动上画布，不用手动拖。

现有链路已经有：`POST /api/place` 按邻居投票找位置，落下是 **draft（金色虚线）**，确认位置后「定稿」。
所以只需在"建完节点"之后自动调一次 place。**保持 draft 态**——不要直接 final，
位置是机器猜的，得由人确认（设计文档 4.1「程序只写 draft、只在分组内、不动 final」）。

### 「第二天进来能预览今天要学的点」

今日清单（`/api/coach/today`）已经算得出来，缺的是**开场就看见**。
加一张**晨间简报**：当天第一次打开时自动弹出（`localStorage` 记当天日期，一天只弹一次），内容：

```
今天 · 3 个新点 · 5 个待复习 · 2 个错题
建设：神经网络与反向传播 → 卷积 → 池化
复习：Transformer、CUDA、TPU…
预计 1.5 小时（按 weekly_hours 折算）
```

一天只弹一次、可关掉、能直接从上面开始动手。

## 5. 视图重排：对话全屏，图分全局与项目两层

> 2026-09-16 修订。首版把对话做成了 420px 的左抽屉（`panels/ChatPanel.vue`），
> 试用下来不对：**对话不是一个工具面板，它是主界面。** 挤在抽屉里既读不下长回答，
> 也看不见正在聊的那些点在图上是什么位置。

### 5.1 三个视图模式，不再是两个

现在 `App.vue` 的 `mode` 只有 `structure | history`（`:92`、`switchMode:370`，快捷键 1 / 2）。
改成四个，顶栏 tab 与快捷键一并扩：

| 模式 | 快捷键 | 内容 | 范围 |
| --- | --- | --- | --- |
| **对话** | 1 | 全屏聊天，右侧可收起的图 pane | **项目** |
| **项目图** | 2 | 该项目的画布（含未建的幽灵点） | **项目** |
| **全局图** | 3 | 现在的结构视图，一个字不改 | 全局 |
| **历史** | 4 | 现在的历史视图 | 全局 / 可按项目过滤 |

**默认落在「对话」**：启动成本最低的入口应该是默认入口。

### 5.2 对话屏的布局

```
┌──────────────────────────────────────────────────────────┐
│ [项目 ▾ Transformer]   对话 · 项目图 · 全局图 · 历史   [↗ 全局图] │  ← 顶栏
├───────────────────────────────┬──────────────────────────┤
│                               │  项目图（可收起）          │
│   对话流（全屏主体）            │  · 聊到的点自动高亮        │
│   · 变更卡内联展示 diff         │  · 点节点 → 把它带进对话    │
│   · 「写入」才落盘              │  · 未建的点画成幽灵        │
│                               │                          │
├───────────────────────────────┴──────────────────────────┤
│ [今天学什么] [考考我] [讲个概念] [这段学完了]   输入框      │
└──────────────────────────────────────────────────────────┘
```

三条交互把对话和图真正绑在一起——**这是全屏改造的全部理由，否则只是把抽屉拉宽**：

1. **聊到哪，图上亮哪。** 每轮回答里提到的 node_id（`chat` 返回里本来就有）在右侧图上高亮，
   复用 `canvas/render.js` 的 `highlightPath`（已有，今天刚修过它的还原逻辑）。
2. **点图上的节点 → 带进对话。** 把该节点的摘要与出入边塞进下一轮上下文，
   省掉"我想问 XX"这句打字。
3. **变更卡落盘后，图当场长出来。** 新节点按 §4「自动上画布」的规则落成 draft，
   右侧 pane 立刻能看见——这就是「学完之后知识图谱自动扩展」的实现位置。

图 pane 可收起（记 `localStorage`），收起后就是纯全屏对话。

### 5.3 顶栏的全局入口

顶栏右侧常驻一个 **「↗ 全局图」**：任何模式下点它都切到全局结构视图，
并**把当前项目的点在全局图上高亮**——回答"我学的这些东西，在整张图里是什么位置"。
这是项目视角与全局视角之间唯一需要的桥，不需要更多层级。

项目切换器放顶栏最左（`AppHeader.vue`），因为**它决定了下面三个模式看到的范围**，
不该藏在某个面板里。

### 5.4 对话面板与旧面板的关系

`ChatPanel.vue` 从 `Drawer` 里搬出来，变成一个占满 stage 的视图组件（`views/ChatView.vue`）。
左侧 ActivityBar 的 `chat` 图标**去掉**——它不再是工具窗口之一。
其余面板（今日 / 项目 / 素材 / 时间线）保持不动，在「项目图」「全局图」模式下照常用。

## 5A. 项目画布 + 同步到全局

目标：每个项目一张自己的画布，点「同步到全局」才并进全局视图。

**这不违反"一张全局图"的决策**（设计文档 4.1）。全局图仍然是唯一的成品图；
项目画布是**工作台**——新东西先在自己的小天地里长，成熟了再并进主图。
这正好呼应既有的三态设计：**项目画布 ≈ 一个按项目分组、可排版的 Inbox**。

动机是真的：一份 JD 拆 30 个点，直接掉进全局图会把主图冲垮。

### 做法（复用现有机制，不新增放置算法）

| | 全局画布 | 项目画布 |
| --- | --- | --- |
| 文件 | `.knowrary/layout.json`（不变） | `.knowrary/layouts/<project_id>.json` |
| 契约 | `LayoutDoc` | **同一个 `LayoutDoc`**，不新增契约 |
| 内容 | 全部已定稿节点 | 只有该项目的点（含「未建」的幽灵位） |
| 谁写 | 现有 PATCH | 同一套 PATCH，多一个 `?layout=<project>` |

- `server/layout_store.py` 现在硬编码单文件路径（`server/paths.py:31` `layout_path()`），
  改成接受一个 layout 名（默认 `layout`）。

**不止这一处——"唯一的结构性改动"这句话是低估的（2026-09-16 核过代码后修订）。** 一份 layout 变多份，
跟着要按 layout 分的至少还有三处：

| 地方 | 为什么跑不掉 |
| --- | --- |
| `knowrary layout check` CLI（`knowrary.py:278`） | 同样硬编码单文件，要加 `--layout` |
| **前端 undo/redo 与 patcher**（`App.vue:113` `createHistory()`、`:2299` `createPatcher`） | **单实例**。在项目画布上撤销，可能把补丁打到全局 layout 上——这是数据损坏级别，不是体验问题 |
| e2e 的 `ck.layout()` 助手 | 只认一份，跨 layout 的用例写不出来 |

反过来，**3D 视图不受影响**：它只读 `/api/index`，明确不碰 layout（`web3d/src/main.js:1`）。
四期的排期按"四处"估，不要按"一处"估。
- **「同步到全局」** = 对该项目中尚未出现在全局 layout 的节点，调现有的 `POST /api/place`
  （服务端按邻居投票找位置，落 draft）。已经在全局里的跳过。
- **不搬坐标**：项目画布里的排版是你为了想清楚而摆的，全局图有自己的结构。
  搬过去只会打乱主图——这条要在 UI 上明说，否则会被当成 bug。

### 去重要发生在写入之前，不是之后（2026-09-16 补）

上面的"已经在全局里的跳过"只按 **node_id 精确比对**，**近义重复一个都拦不住**。
这不是假想：2026-09-15 同一个 Transformer 目标被拆了两次，得到 `RNN` / `RNN与长程依赖`、
`BPE分词` / `子词分词-BPE`、`因果掩码` / `注意力掩码` 三对近义词，服务端的 id 去重全部放行
（见设计文档 F10.3b）。对话这条路更容易触发：聊完让它入库，它建一个「自注意力」，
而图里可能已经有「self-attention」。

能力其实都有了——`/api/suggest` 的重复候选、欠账清单的「重复候选」、`/api/merge`——
方案缺的只是**接在哪一步**。结论是：**接在写入之前。**

| 时机 | 后果 |
| --- | --- |
| 写入前（采纳） | 当场问一句"图里可能已有 X，改成连到它？"，图始终是干净的 |
| 写入后（欠账里捞） | 等于默认让图先脏一次，再指望人回头清——而"回头清"正是最容易不做的事 |

落点两处，都不新增接口：

1. **变更卡**（§8 契约 3）：展示 diff 的同时，对每个 `create_node` 跑一次重复候选检查，
   命中就在卡上标出来，并给一个"改成连到既有节点"的按钮（把 `create_node` 换成 `add_edge`）。
2. **「同步到全局」**（本节）：跳过的判据从"id 已存在"扩成"id 已存在**或**命中重复候选"，
   命中的不静默跳过，列出来让人选：合并过去、还是确实是两个东西。

**判据仍然只提议、不自动合并**（4.4）。自动合并两个看起来像的节点，
比让图里多一个重复节点严重得多——前者会悄悄吃掉一份正文。

### 「未建」的点怎么在项目画布上表示

画成**幽灵节点**：比 stub 更淡的灰虚线，点一下就开新建对话框（复用 `App.vue` 的 `buildPoint`）。
这样项目画布从第一天就是完整的施工图——你能看见还没建的东西在哪，而不是一片空白。
幽灵节点**只存在于项目画布**，绝不进全局 layout，也不进 vault（沿用"推测出来的东西不进真值源"）。

## 7. 关于数据库：现在还不用，但给出明确的触发条件

"东西越来越多、越来越像一个系统，是不是该上数据库了" —— 这个直觉有一半是对的，
但**要区分是哪一层**：

| 层 | 内容 | 判断 |
| --- | --- | --- |
| **知识层** | `nodes/*.md`、`layout.json`、`projects.json` | **永远不进数据库。** 它们要能被 Obsidian 打开、被 `git diff`、被手改、坏了能肉眼修。这是这个项目的立身之本 |
| **行为层** | `review-log`、`quiz-log`、`llm-usage`、将来的 chat / sessions | **候选**。追加型时序数据，没人会手改，也不需要 Obsidian 认识 |

### 诚实的反面证据

这个直觉不是没道理。2026-09-15 为了 rename 和 merge，专门写了两个模块去同步
**5 个文件里的同一个 node_id**（md 的 `[[链接]]`、layout 的 nodes/edges/refs/doc、
review-log、quiz-log、plans）——**这正是关系型数据库用外键免费解决的事**。

但代价换过来看：进了数据库，md 就不再是唯一真值源，Obsidian 打不开，git 看不见 diff，
而那才是这套东西真正值钱的地方。所以**宁可自己写 rename/merge，也不换掉 md**。

### 触发条件（满足任一条再重新评估行为层）

1. `quiz-log.json` 超过约 **1 万条**作答（现在个位数）；
2. 需要"按项目 × 按周 × 按掌握度"这类**交叉统计**，而不只是按 node_id 聚合；
3. 单次读取行为层文件超过 **50ms**，开始拖慢今日清单。

届时的迁移路径是收敛的：**只把行为层搬进 SQLite**（`.knowrary/behavior.db`），
知识层一个字节不动；`core/review.py`、`core/quiz.py`、`core/usage.py` 已经是
"load / save / 聚合"三段式，换存储只改这三个模块的内部，上层接口不变。

## 8. 对话的三条契约（已落地，核对用）

对话先于本方案落地，下面三条是当初定的契约，实现时已经遵守；重构时不许破坏：

1. **对话留档**：一行一轮 `{ts, role, text, node_ids}`，按月分文件。沿用 F10.7 已定的结论：
   **不建 SQLite、不做切分、不做 embedding**（门槛写在 F10.7：累计超 5 万轮，
   或反复出现"记得聊过但 grep 找不到"）。
   ✅ 已实现（`server/chat.py:186` `chat_log_path`），`.gitignore` 也已加 `.knowrary/chat/`
   ——留档是过程不是知识，不入库。
   ❌ **但"按项目分文件"这一条没有落地**：实现时项目还不存在，落盘路径是
   `.knowrary/chat/YYYY-MM.jsonl`，**没有项目那一层**。所以它不是"已遵守的契约"，
   而是**一期要补的迁移**：
   `.knowrary/chat/<project_id>/YYYY-MM.jsonl`，现有那份整体挪进 `_scratch/`（见下）。

   **未绑项目的对话去哪：`_scratch/`。** 这是一期必须回答的问题，因为 §5.1 把「对话」
   定成了默认视图——冷启动时一个项目都还没有，"随手问一句 CAS 的 ABA 怎么解决"必须有地方落。
   两条路：强制对话绑项目（那就得先逼人建项目，直接违背"启动成本最低的入口应该是默认入口"），
   或给一个兜底目录。**选兜底**：`.knowrary/chat/_scratch/YYYY-MM.jsonl`，
   界面上标成「未归档」，将来可以把某一段挪进某个项目，但**首版不做这个搬运功能**
   ——grep 找得到就够了，别为一个每月用一次的动作写 UI。
2. **系统提示词现场拼，不落盘**（落盘就是第二份真值）。材料全部来自项目配置与派生量：
   项目名 + **当前清单**的 `kind` / `goal`（面试清单就是 JD 原文）+ `coach` 侧写
   + 当前阶段及其各点的学/考双态
   + 最近错题 + `relation-types.json` 的类型表（供蒸馏用）。
3. **对话能触发的动作一律是现有接口的封装，且一律走确认**：
   建节点（`create_node` ChangeSet）、连边（`add_edge`）、出题（`/api/quiz`）、
   记复习（**只许降级不许升级**，F10.5 已定）。不新增绕过 ChangeSet 的写路径。
   ✅ 已实现为「变更卡」：模型给卡片、展示 diff、点「写入」才落盘。
   ⬜ **待补：卡上要标重复候选**（见 §5A「去重要发生在写入之前」）。
   现在模型被 prompt 要求"讲之前先 `search_nodes`"，但那是软约束；
   真建出一个「自注意力」而图里已有「self-attention」时，卡片上必须当场看得见。

**重构时新增的第 4 条**：对话回答里带回的 node_id 是 §5.2「聊到哪、图上亮哪」的输入，
所以 `/api/chat` 的返回必须继续带它——这从一个调试信息升级成了界面契约。

**§5A 说的那个隐患解掉了。** 前端 undo/redo 是单实例，跨画布撤销会把补丁打到错的文件上——
这是数据损坏级别，不是体验问题。做法是**切 layout 时先 flush、再清空撤销栈**
（`history.reset()`），而不是维护两套栈：栈里存的是"某一份 layout 的前后快照"，
两套栈同时活着只会让"现在该撤哪一份"变成新的 bug 来源。
patcher 则拿到一个 `getLayoutName()`，每次 PATCH 自己决定写去哪份文件。

**幽灵节点判定踩了一个自己挖的坑**：为了让幽灵显示出标题，渲染时给它合成了一个
`indexNode`，结果 `ghost = state === 'ghost' && !indexNode` 永远为假——样式压根没生效。
改成由调用方显式传 `ghost` 标志。这类"为了显示方便合成一个假对象，结果把判据打翻"
的错误，只有真浏览器跑一遍才看得见（e2e 直接读 `stroke-dasharray` 断言）。

**用例**：core 57、服务端 98（新增「项目画布与全局图互不影响」「同步到全局只放该放的且不搬坐标」
「同步前先把重复候选摆出来」）、e2e 118（项目画布只画本项目的点含幽灵、幽灵的线型、
动项目画布不碰全局 revision、同步按钮给出逐条结果、同步不搬坐标）。

**真实数据验证**：`transformer` 项目画布 44 个节点里 43 个是幽灵（这个项目确实才刚开始建），
孤立记录 0；对它点同步，结果是"43 个还没建出来、1 个已经在图上"，**全局 layout 一个字节没动**。

## 试用后的修补（2026-09-16，五期之后）

前四期做完实际点了一圈，暴露出三件事：

**1. 切项目后项目画布是空的（真 bug）。** `switchProject` 换了 `currentProject` 却没重新拉那份
layout——画的还是上一个项目的 `layoutDoc`，被新项目的 `only` 过滤一遍就什么都不剩。
更糟的是接下来的拖拽会拿着**旧 revision 去写新文件**，必 409。
修法：切项目时先 flush、清撤销栈、重新拉 layout，再 render。
用真浏览器复现出来的：服务端那份有 2 个节点，画布画了 0 个。

**2. 「全局/不绑项目」那条线在界面上没有入口。** 顶栏切换器永远选着一个项目，
于是 `_scratch`（§8 定的兜底）**根本走不到**。用户的体感是"在对话里切了个项目，
当前这段对话就被吃了"——其实是被换成了那个项目的线，而他原来那段在 `_scratch` 里再也回不去。
修法：切换器加一档「🌐 全局（不绑项目）」，空串是合法值。

**3. 记住上次看的哪个项目。** 刷新后总是回到第一个项目。这**不是数据库问题**，
是个界面偏好——`localStorage` 一行就够。注意空串（全局）是合法值，
所以要用 `null` 区分"没存过"，不能拿 `||` 兜底。

顺带落地了**对话里建项目**（`propose_project` 工具 + 项目卡）：
全局对话里说"帮我建个 NLP 项目"，模型出一张卡，点「创建」才写 `projects.json`。
**建完清单是空的**——拆点是另一步（prompt 里明说了别在同一条消息里全干完），
这样每一步都还是"提议 → 人点"，没有绕开 4.4。

**口径切换（2026-09-16，替代"多 agent"）**

「教练 / 面试 / 聊天」不做成三个 agent，做成**同一条链路上的三套提示词 + 三份工具白名单**——
和 F10.3b「拆解口径不同 ≠ 架构不同」是同一条判断。多开一套 agent 运行时要付会话路由、
上下文传递、状态同步、翻倍 token 的代价，而收益只是换一套系统提示词。

| 口径 | 工具 | 为什么 |
| --- | --- | --- |
| 教练 | 全套 | 盯进度：今天学什么、该复习了、来不来得及 |
| 面试 | 只读 + `quiz` + `record_review` | **不给入库和建项目**——边考边改图谱等于开卷，也打断面试节奏 |
| 聊天 | 只读 + `propose_changes` | 只把事情讲清楚；不给 `today` / `projects`，免得每句话都被催进度 |

两条实现上的要紧处：

1. **工具表从白名单渲染，不写死在提示词里。** 说明书和实际权限必须是同一份数据——
   "表里写着能用、调了却说没有"是最让人发火的那类 bug。带格式说明的两个写工具（建项目、入库）
   也跟着白名单一起渲染。
2. **换口径就新开一段。** 混在同一段里，前半截是面试后半截是闲聊，模型会被自己的历史带跑。

用量按口径分开记（`chat-教练` / `chat-面试` / `chat-聊天`），否则算不清备考烧了多少。

真正需要独立 agent 的信号只有三个：**要并行跑、要不同的工具权限、要互相审查**。
第二个用白名单就解决了；第三个其实已经有了，就是 `learn` / `review` 双角色 provider。
等出现"一边模拟面试、一边让另一个模型实时判卷"这种**必须并行**的场景再说。

**顺手修掉的三个 UI 问题**（都是试用时发现的）：

- **两个「全局图」**：顶栏 tab 一个、右边按钮又一个，文案一样。合并掉——
  选着项目时切到全局图 tab 会顺手高亮那些点，桥就是 tab 本身，不另设控件。
- **`nextTick` 没 import**（真 bug，藏得很深）：`switchMode` 和 `toggleGraphPane` 里
  `await nextTick()` 抛 ReferenceError，**把后面的代码整段吞掉**——表现是"切到全局图不高亮"
  和"收起图 pane 后画布不重新量宽"，而控制台里只有一句被 toast 吞掉的报错。
  查法：往 `window.__kg` 上挂 mode / project / projectIds 几个 getter，
  再在函数里逐段打桩，才定位到是哪一行断的。这几个 getter 留下了——
  排查"为什么没高亮 / 为什么画布是空的"这类问题，没有句柄就只能靠猜。
- 切模式后的 `await nextTick()` 现在包在 try/catch 里：**渲染期一个报错不该把后面的事全断掉**。

**第二轮试用修补（2026-09-16）**

1. **「点对话没反应，看着像还在全局图」——真 bug，而且藏在 CSS 里。**
   画布一直是 `position: absolute; inset: 0` 铺满 stage 的，所以三期加的 flex 分栏对它**完全无效**：
   对话视图和画布在同一块区域上重叠，画布在上层，于是点了对话就像什么都没发生。
   量出来才看得见：对话 `[x=52, w=900]`、画布 `[x=52, w=1548]`。
   改成 `position: relative; flex: 1` 之后是 `[52,900]` + `[952,648]`，真正的左右分栏。
   **教训**：用 `getBoundingClientRect` + `elementFromPoint` 断言"没被盖住"，
   光断言"元素存在、宽度大于 0"是抓不到这种问题的——e2e 之前就是这么漏过去的。

2. **左侧栏按作用域分段。** 项目级（项目、今日）在上，全局级（Inbox、欠账、日历、素材）在下，
   中间一条分隔线，tip 上写明是哪一级。顺带修了个真问题：三期把模式从 2 个扩到 4 个之后，
   `structureOnly` 这个旧判据让 Inbox / 项目 / 素材在「项目图」和「对话」模式下**整个消失**。
   现在每个条目声明自己在哪几个模式下有意义。

3. **切项目跟着切对话线**（本来就实现了，这轮补了用例）：换项目 = 换一条对话线，
   上一段没丢，它一直在 `.knowrary/chat/<项目>/` 里。

4. 首屏用例的顺序得调：默认模式是对话，画布只占右边一条，**auto-LOD 会把分组折叠成簇卡片**，
   这时数不到 `kg-node`。所以先关简报、切到全局图，再断言首屏渲染。

**"建项目要不要上 agent"（2026-09-16）**

问题原话：「需要考察已有内容，需要做出规划，并不是几个提示词就能搞定的」。**这句是对的**，
而且它推翻了我先前"做口径就够了"那句话的一半——但结论不是"再开一个 agent"：

**对话本身已经是一个 agent**：`server/chat.py` 是标准的工具循环（模型调工具 → 服务端执行 →
结果回灌 → 再想）。所以真正的问题是"这个循环够不够用"。查下来三处不够，都补了：

| 不够在哪 | 改法 |
| --- | --- |
| **看不见已有项目**：系统提示词里只有节点数和领域，一个项目都没提 | 概况里加「我已经有的项目」：id、名字、每份清单的口径与点数、目标一句话 |
| **步数上限 4 太少**：看项目 → 搜图 → 读节点 → 提议 → 拆点，走不完 | 放宽到 8。同参调用本来就会被短路（`seen_calls`），放宽不会变成原地打转 |
| **拆点不是对话能做的事**：建完项目就断了，得自己去面板点「让 AI 拆一份」 | 新增 `propose_points` 工具，**走面板同一条链路**（同一套模板、同一份时间账、同样标注"别的项目已列过"），同样出卡片 |

外加两处"看得见重叠"：

- **建项目时**：服务端算出名字 / 目标跟已有项目撞车的（`near`），卡片上标出来，
  话术里也要求先问一句"独立一个项目，还是在那个项目里加一份清单"。
- **拆点时**：把**别的项目已经列过的点**一起喂给模型（不喂就会在每个项目里
  把「自注意力」各拆一遍近义词），回来的提议上标「Transformer 里有」（`in_projects`）。
  **只标不拦**——项目是视角，重叠合法且免费：同一个点属于两个项目，掌握度还是同一个，
  今日清单里也只出现一次（§1）。

教练口径的提示词里写死了这条工作流：先看已有 → 再搜图谱 → 提议项目 →
**他点了创建之后**再拆点，拆之前先确认目标日期和每周投入（没有这两个就排不出阶段截止日）。
**每一步的产物都是卡片，都要人点**——多走几步不等于多一分越权。

什么时候才真的需要第二个 agent：**要并行跑、要不同的上下文、要互相审查**。
建项目是纯顺序任务，共享上下文反而是优点；权限用白名单就收窄了；
互相审查已经有了（`learn` / `review` 双角色 provider）。

**第三轮试用修补（2026-09-16）**

1. **`search_nodes` 看不见"计划里还没建的点"——这是"没发现 Transformer 里已有"的真原因。**
   一个项目常常 40 个点里 39 个还没建（它们只活在 `projects.json` 里，不在索引里），
   于是问"图里有没有多头注意力"得到零命中，而 Transformer 项目里明明列着它。
   实测那次对话里模型只能说"注意力相关的很可能在里面用别的名字存着"——它是对的，但它看不见。
   改法：`search_nodes` 同时搜项目清单，命中的标「计划里有、还没建（在 X 项目·某清单）」。
   一搜就抓出了真正的重复：`多头注意力`（Transformer 项目）和 `MHA`（AI技术发展史项目）是同一个东西。
   **计划里的点和已建节点是同一件事的两个阶段，搜的时候不该只看后一半。**

2. **卡片点了「创建」之后直接把人送到那一项**：切到该项目 + 打开项目面板。
   建完还要自己去左侧栏找面板、再在下拉里挑一遍，这一步的摩擦比建项目本身还大。
   `openPanel` 加了 `force`——程序主动带人过去时，不能让它变成"再点一次就关掉"。

3. **失败的轮次在留档里也留记号。** 之前只在开头记提问、结尾记回答，
   模型不通时就只剩一条孤零零的提问；连试五次就攒出五条没人答的问题，
   下次接着聊全被读回去当上下文（真实留档里就是这样五条一模一样的）。
   现在失败会追加一行「（这一轮没答成：…）」。

4. **顶栏也按作用域分两组**（和左侧栏同一套语法）：
   `[对话 · 项目图]` 是跟着当前项目走的，`[全局图 · 历史]` 是整个图谱层面的，中间一道竖线隔开。
   混在一排里，人不知道自己在看哪个范围——这和左侧栏那次是同一个毛病，只是我当时只修了一半。
   选了「🌐 全局」时「项目图」置灰（不绑项目就没有项目画布），
   正停在项目图上时切到「全局」会**自动退到全局图**，而不是留在一个空模式里。

5. **报错带上是哪个角色、哪个 provider、哪个模型**：
   `[learn 角色 · provider \`gpt\` · 模型 gpt-5-codex] LLM 请求失败 HTTP 503…`。
   provider 的原话一个字不改，只是前面告诉你该去改配置的哪一行。

**第四轮试用修补（2026-09-16）：作用域要一以贯之**

一句话概括这一轮：**"我在某个项目下"应该是一个贯穿整屏的状态，而不是只影响某几处。**

| 原来 | 现在 |
| --- | --- |
| 左侧栏把项目级和全局级工具摆在一起，只用一条分隔线隔开 | **按作用域只给该给的**：项目下＝清单 / 今日 / 素材；全局下＝项目管理 / Inbox / 欠账 / 日历。作用域**跟着视图走**（全局图和历史本来就是全局视图，那时照给全局工具，否则"历史视图里调不出时间线面板"） |
| 清单面板里有项目切换器，能翻到别的项目 | 项目下不给切换器、不给新建（那些去「🌐 全局」做），面板标题也从「项目」变「清单」 |
| 今日清单只按项目过滤**建设项**，到期复习和错题仍是全局的 | **整屏都按项目过滤**，但别处还欠着多少要**如实报**（`elsewhere`），面板上写一句"另有 N 个在别的项目，切到全局一起看" |
| 对话模式右边那块图永远是全局图 | 也用**项目画布**——你聊的点多半还没建，只在项目画布上有幽灵占位；不这样"聊到哪、图上亮哪"直接失灵 |
| 切项目只重拉对话 | 判据改成"**这一屏该画哪份 layout** 变了没有"，而不是"现在是不是项目图模式"——后者会漏掉对话模式那块图 |

**「今日只看本项目」不违反 §1「复习调度全局唯一」。** 间隔、掌握度、`next_due` 仍然只有一份，
同一个点在哪个项目里看都是同一个状态；过滤的只是**今天这一屏摆谁**。
但**不能藏**：藏起来的复习等于没有复习，所以 `elsewhere` 必须如实报出来。
（真实数据上：站在 transformer 项目里是「到期 1、未建 3」，同时明说"另有 11 个到期在别的项目"。）

**重新组织：三个维度各归各位（2026-09-16）**

试用后发现原来的组织方式把三件事挤在了两个字段上。证据：`field` 77 个节点里 **65 个是同一个值**
「计算机体系结构」——而这个名字**本身就是一个抽象层的名字**；与此同时 `nodes/` 的目录
（`01-理论基础 … 07-高级语言`）其实已经是分层了，只是没有字段承载它。

| 维度 | 回答什么 | 存在哪 | 改成什么 |
| --- | --- | --- | --- |
| 主题 | 这属于哪一块 | `field` | `计算机系统`（65 个，从「计算机体系结构」改名）/ `AI` / `Agent` |
| 层次 | 这在栈的哪一层 | `layer` | 7 层，74/77 已标（3 个 stub 留空） |
| 排版 | 画布上摆哪儿 | layout 分组 | 顶层 = 主题（3 个），二级 = 层 |

- **`field` 改名的理由不是好听**：`计算机体系结构` 和 `layer: 体系结构` 撞车，
  一个词同时当主题和层用，两个维度就永远分不开。
- **`layout init --by layer`**：二级分组按 `LAYERS` 的固定次序（底层在前），不按字典序。
  顺手修了一个一直存在的破坏性行为——`layout init --force` 会把**便签 / 贴图 / 引用卡 /
  手工边拐点**一起清掉。重排的是分组和位置，那几样是另一类用户数据，现在会原样带过去。
- 分层之后历史视图才真的能读：理论 4、硬件 5、体系结构 4、汇编接口 2、系统软件 6、
  高级语言 1、AI应用 1（带 year 的）。**高级语言和 AI应用各只有 1 个**——
  这正说明下一步该补的是数据，不是视图。

**顺带修的两个 UI bug**：

- **刷新后跳回全局图**：挂载时第一次 `fetchLayout` 就要知道拉哪一份，而 `currentProject`
  那时还是空的（要等 `refreshPlans` 回来）。改成**开局就从 localStorage 读**；
  存的项目要是已经没了，404 时退回全局图而不是整屏"加载失败"。
- **清单里「建」按钮被挤没了**：`why` 常常是一整句话，和按钮挤在同一行，
  一长就把按钮推出可视区——按钮等于不存在。改成 `why` 单独占一行、动作钉在最右边，
  e2e 用 `getBoundingClientRect` 断言按钮确实在行内（"元素存在"是查不出这种问题的）。

**边聊边完善 md（2026-09-16）**

问题原话：「我还没创建 NPU，但我跟 AI 聊到了 NPU，他应该给我自动创建，然后基于我的认知不断完善 md，
边聊天边完善，或者最后来一个按钮梳理整理知识」。零件大半是现成的，缺三处：

1. **模型不知道能改已有节点的正文。** `update_body` 在写回层一直支持，但**从没写进工具说明**——
   所以它只会新建，不会往你已有的那篇里补。现在写进去了，并附一条硬约束：
   **`update_body` 是整段替换，不是追加**，所以改之前必须先 `read_node` 把原文一字不落带上，
   否则会把你以前记的抹掉。
2. **没有"回头整理这一段"的入口。** 会话条上加了「梳理这段」：它不是新链路，
   就是一条写死的指令——让模型回头看整段对话，分清哪些该新建、哪些该往已有节点里补、
   这次聊到的关系连上，出**一张**卡。一直摆着（聊之前是灰的）：藏起来的入口等于没有入口。
3. **聊到"计划里有、还没建"的点时不主动认领。** 教练口径的规矩里补了三分支：
   图里有正文 → 补；计划里有、还没建 → 直说"这个在 X 项目清单里，聊完给你建出来"；
   哪儿都没有 → 先问一句再建。

**「自动创建」这一条没照做，只做到"一键"。** 4.4 之外还有个更实际的理由：
新建的节点**立刻进复习队列**。如果它是背着你生成的，你并没有学过它，
掌握度从第一天就是假的——这套东西的全部价值建立在记录诚实上。卡片就是那一下确认。

**顺带修了两个真 bug，都是拿真模型跑一次才暴露的**：

- **`today` 工具直接抛 KeyError**：一期把 `today["plans"]` 改名成 `projects` 时漏了这一处。
  模型只好在回答里说一句"today 挂了"接着聊——它没崩，但教练看不见今日清单了。
  顺手让它跟着当前项目走（在某个项目里聊天，就该看这个项目的今天）。
- **`layer` 写不进新建的节点**：加了字段、加了校验、加了泳道，却忘了开 `writer.py` 的
  `EDITABLE_FIELDS` 白名单。**这个 bug 是模型自己发现并写进正文的**——
  它在 body 里留了一句"待补：`layer: 硬件` 现在写不进去，是 writer.py 白名单漏了 layer"。

**学技术发展史这个场景，还差三处（2026-09-16）**

问题原话：「跟 AI 讨论完之后，他应该能自动识别我的项目，并且把时间、名称、发展方向都整理好」。
"识别项目"本来就有（对话带着当前项目），但另外三样是真缺的：

1. **关系类型表从没喂给模型**——§8 契约 2 里定过，一直漏着。后果是它只能**猜类型名**：
   真实对话里它写过 `提出者::`，那个类型没登记，解析时落进「弱关联」还带一条警告。
   而**「发展方向」全靠 `演化` 那一族**（`演化为` 同线下一步、`被激活` 跨层点燃），
   不给表就连不对。现在按族列进提示词，并说明**方向从早指向晚**、年份写括号里。
   `canonical` 的反向写法（`源自` / `属于`）不给模型看——两种写法混用只会让归一化白忙。
2. **新建的点不会进项目清单**。节点建出来了、清单却没列它，于是**项目进度不认它**，
   今日清单也不会再提它——因为清单只按 id 引用，没列就不算数。
   现在变更卡带一个 `into`：**服务端算**（当前项目的第一份清单、已列过的不重复加），
   卡上写明"写入后同时加进「X·主线」"，**一次点击两件事一起落**。
3. **发展史节点缺 `year` / `layer` / 演化边就等于白建**——历史视图上少一块。
   教练口径里写成了硬要求，并附一句：**填错的年份比没有年份更糟**，
   它会在时间轴上把整条线带偏。

**教练侧写：把人能改的那部分挪进 vault（2026-09-16）**

问题原话：「是不是需要那种 workspace 的 agent，有 soul、agents.md 这些文件更好一点？」
**那套约定里该抄的只有一半。**

抄的那一半——**把"人可以改的部分"从代码里提出来**：

| 文件 | 是什么 | 谁改 |
| --- | --- | --- |
| `tools/knowrary/prompts/chat*.md` | **程序行为**：工具协议、纪律、卡片规则 | 改了要跟代码一起测 |
| `.knowrary/coach.md` | **我的数据**：我是谁、要什么口气、笔记想长成什么样 | 随便改，坏了只影响口气 |
| `.knowrary/coaches/<项目>.md` | 某个项目单独的规矩，接在全局之后（覆盖全局） | 同上 |

这条分界是"md 是真值源、程序是程序"那条纪律的延伸。侧写**每次现读不缓存**——
你会在服务跑着的时候改它，改完下一句话就该生效。

不抄的那一半——**多 agent 注册表 / 每个 agent 一个目录**。F10.3b 已经否过同类设计：
教练 / 面试 / 领域看着是三个东西，其实是同一条链路上的三套提示词 + 三份工具白名单。
真正需要独立 agent 的信号（并行、独立上下文、互相审查）一个都还没出现，
多一层 agent 定义文件只多一层间接，不多一分能力。

**口述的年份怎么矫正（2026-09-16）**

问题原话：「"把 NPU 记进图谱，year 2017"——万一我写错了怎么办？会有矫正逻辑吗？」
查下来**基本没有**：`_validate_years` 只管"是不是四位整数"和"区间别反转"，
写成 1917 照样过。补了三层，**从硬到软**：

| 层 | 做法 | 可靠性 |
| --- | --- | --- |
| **结构性校验** | 演化族边两端倒挂（`A 演化为 B` 而 A 比 B 晚）→ 警告 | **完全可靠**：不依赖任何外部知识，只问"这条线自己自洽吗" |
| **常识性校验** | 年份落在未来 → 警告（真要记规划中的标准也可能，所以不报错） | 可靠，但只能抓一类笔误 |
| **模型质疑** | 教练口径：我口述的年份和它知道的不一致时**当场说出分歧让我定**，既不照抄也不默默改 | 不保证，但覆盖面最广 |

第一层是关键：**口述一句"year 填 2017"没人能核，但"它比它的前身还早"是能算的。**
年份写错时，十有八九会和图里已有的某条演化关系撞上——撞上了就让它自己冒出来。
警告同时进 `knowrary check` 和欠账面板的新分类「年份可疑」，不是只躺在 index 的 warnings 里。

三层都是**警告不是错误**：先让我把东西记下来，别拦着；可疑的攒在欠账里回头清。

**第五轮试用修补（2026-09-16）**

1. **「对话没记忆」是误会，但截断是真问题。** 产品本身把**整段历史**随每次请求发过去
   （前端持有会话，`messages` 全量发；用假模型抓过第二次请求，前两轮都在）——
   我之前的真实测试是单条 curl，那是测试脚本的形状，不是产品行为。
   真缺口在**超长对话**：原来 `MAX_MESSAGES=60` 硬截断，多的直接丢，模型不知道自己少了东西。
   现在两道闸（条数 + 24000 字），**并且把截断这件事告诉模型**：
   「之前还有 N 轮没带过来，缺的别猜，先去图里找或者问我」。
   模型不知道自己失忆时会拿半截记忆当完整的用，比直说"我没看到"糟得多。
   真正的长期记忆本来就不该是上下文窗口——聊清楚的东西该进 md。

2. **出错流水 `.knowrary/issues.jsonl`。** 原来错误分散在三处：LLM 失败进用量账本、
   工具失败只在那一轮闪一下、写回被拒只弹个 toast，于是"这东西为什么老出问题"
   没有任何地方能回答（`layer` 白名单那个 bug 就这么藏了一阵）。
   现在三处都记一笔，欠账面板新增「最近出的错」分类，按类型分组。
   同 F10.7 的纪律：追加 JSONL、只留最近 500 条、记不上绝不拖垮正经操作。

3. **项目画布原来是半瘫的（真 bug）。** `writable()` 和 `openMenu()` 都只认 `structure`——
   所以在项目画布上**拖节点不落盘、右键不出菜单、连边不行**，而它看着完全正常。
   两处判据必须一起改，只改一处会出现"拖得动却右键不出菜单"这种更迷惑的半瘫状态。
4. **幽灵占位的右键菜单单独一套**：给「现在把它建出来」和「从这块画布上去掉（不动清单）」，
   **不给「建立关系」**——关系行要写进源节点的 md，而它连 md 都还没有。
   （反过来，**连到**幽灵是可以的：那会成为虚拟 stub，等它建出来自然接上。）
5. **在项目下新建的点自动归到这个项目的清单**——比"建完再校验它属不属于本项目"直接：
   建的时候就归属。
6. **对话有了关闭按钮**。原来只能去顶栏点「项目图」，而"我要关掉这个东西"
   和"我要切到那个视图"在脑子里不是一回事。

## 再一轮试用修补（2026-09-16，难度档）

1. **`.section.stage` 撞上画布的 `.stage`（真 bug，找了两轮才找到根）。**
   画布那个 `.stage` 是 `display:flex; overflow:hidden; flex:1` 的横向容器，
   清单里每个阶段也叫 `section stage`，于是**阶段头和点列表被排成一行、超出的部分被裁掉**——
   之前报的「列表太宽、字显示不全、「建」按钮没了」都是它。改名 `.section.plan-stage`。
   e2e 里钉死几何：阶段头高度 < 60px、点列表在它下方。
   教训：全局 class 名撞车不会报错，只会让布局悄悄错位；工具类必须带作用域前缀。

2. **加知识点的输入框收起来了。** 每个阶段常驻一行两输入框 + 一个按钮，五个阶段白占五行，
   而"加点"是偶发动作。现在阶段头上一个 `+`，点开才出现，就贴在阶段名下面，
   展开自动聚焦、回车连着加、Esc 收起。

3. **难度档 `level`：一个维度决定三件事。**
   「AI 发展史只要了解，NPU 要精通」是常态，而原来出题只有一档（一律往深里问），
   聊天只有一种详细度，拆点只有一种粒度。现在：
   - 档位是**数据**（`core.LEVELS = 了解 / 会用 / 精通`，参与校验和存盘），
     三段口径文本是**行为**（`server/levels.py`，一个档 × quiz/chat/plan 三栏）。
     混在一起的话，调一句提示词就得动数据模型。
   - 每一档绑一句**可判定**的标准（「说得出是什么」/「讲得清机制」/「经得起追问」），
     不用"深入一点"这种形容词——换个模型就换一种理解。
   - 放在**项目**上，**清单可以覆盖**（`level` 为空 = 跟项目，`core.level_of` 一套优先级）。
     对话按项目的档（一次对话不属于某一份清单），出题与拆点按清单的档。
   - 检查器、今日清单那些不带档位的「考一下」，落到**当前项目**的档：
     「只想了解的历史」被按精通考一遍，人就再也不点这个按钮了。

4. **出一次题是花了钱的，不能说没就没（真 bug）。**
   原来出完题只活在前端内存里：关掉对话框、刷新页面、点错一下，题就蒸发，
   而那次调用已经计费。现在出题成功即存 `.knowrary/quiz-open.json`，
   今日清单顶上一条「上次还有 N 题没交卷 · 接着答 / 丢掉」，交卷或明确放弃才清。
   **只存题面，不存作答**——作答是事件流，仍然只在交卷时进 `quiz-log.json`。

5. **模型没给出合法 JSON 时留痕。** `parse_json` 原来静静返回 `{}`，
   界面上只剩一句「这轮没出出题来」，下次遇到照样两眼一抹黑。现在：
   - 先按花括号配对**从夹带的话里抠出 JSON**（模型爱加「好的，这是题目：」）；
   - 还是不行就记进 `.knowrary/issues.jsonl`（含原文前 600 字），
     并把原文开头放进 `warnings` 让人当场看见。
   顺带把 `core.record_issue` 的 `detail` 放宽到也认字符串——
   旁路因为调用方写法不同就抛异常，正好违背它存在的理由（这次就抛了一次）。

6. **md 一变，清单进度跟着重算。** 点「建」之后清单上那个点还写着「未建」，
   非得手动刷新页面。进度是服务端按 index 现算的派生数据，
   所以 `reloadIndex()` 里跟着刷一次项目——派生不落盘的代价就是源数据一变就得让它重算。

## 又一轮试用修补（2026-09-16，图文与题库）

1. **过程和答案分开（真 bug 级的体验问题）。** 原来 `answer = "\n\n".join(said)`——
   把**每一步**的话都拼进正文，于是「我先查一下」「today 工具挂了」「找到了这些」
   和最后那几句有营养的混成一段，每次都得整段淘一遍。
   现在：**不再调工具的那一步才是答案**，前面的进 `trace`，界面折叠成一行
   「过程 · N 步（搜图谱、出题）」，点开才展开；留档也分两栏（`text` / `trace`），
   回看历史时同样不用重读过程。

2. **一图胜万言：对话渲染 Markdown + mermaid。**
   - **先转义再解析**：源文里的 `<` `>` 一律变实体，模型写什么都变不成真 HTML，
     也就没有 XSS 那条路——比引一个消毒库更彻底，代价是模型不能写 HTML（它本来也不该写）。
   - mermaid **按需加载**，不画图的对话一个字节都不下；画不出来（流式只到一半、语法错）
     就退回代码块，不让整条消息空掉。
   - 提示词里告诉教练：讲结构、流程、发展史优先画图，`graph LR` / `sequenceDiagram` / `timeline`。
   - **代价说在前面**：`web/dist` 是入库的，mermaid 把它从 896K 撑到 6MB
     （其中 elk 布局 1.5MB —— mermaid 12 的 flowchart 默认走它，stub 掉就画不出图，试过了）。
     这些是懒加载分片，只有真画图时才下载；嫌大就把 mermaid 摘掉，Markdown 那部分不受影响。

3. **题库：把教练随口问的检验题攒起来（`.knowrary/question-pool.json`）。**
   教练每轮末尾那个「检验我是否真懂」的问题，是**在我刚学完那一刻、对着我当时的理解**
   提的，比事后让模型看着 md 现编的贴身得多；而且它已经生成过一次了，
   出题时再编一遍等于为同一件事付两次钱。
   - 模型用 ```check 围栏标出题干和考点，服务端摘进题库（题干仍留在正文里，
     摘掉的只是围栏——那句问话本来就是对话的一部分）。
   - 出题时**先用题库**：够 `count` 就一次模型都不调（warnings 里说明），
     不够就只让模型补差额。
   - 交卷时按题面回填：答对打「学会」，答错摘掉。
   - **这里不存复习调度**：什么时候抽查仍由节点的 review-log 说了算（第四份契约）。
     题目再自带一套间隔就是第二份调度真值，两边迟早对不上。
     「学会」只是排序提示——先紧着没把握的问，不是从此不考。

4. **孤点落进对应的抽象层泳道。** 一条边都没有的节点原来只按 `field` 找顶层框，
   分组改成按层切开之后，它会落在**父框里、所有泳道之外**。
   现在按 `field` → `layer` 逐层找同名子框（没填 layer 的落「未分层」那条），
   连子框都没有才退回父框。同名的「硬件」在别的领域下面不会把点吸过去。

## 表单这一层的统一（2026-09-16）

「一眼望上去不知道该填什么、哪些是重点」——查下来是**样式根本没生效**：
`.fld / .lb / .hint / .two` 这一套只写在 `.node-dialog` 作用域里，
而清单面板、检查器用的是同样的 class，于是标签和输入框挤在一行、没有字重、没有间距。

现在这一套是**全局**的（style.css 第 6b 节），三条规矩：

1. **标签独占一行，在输入框上方**，11.5px / 650。补充说明（可选 / 项目级 / id xxx）
   做成小标签，因为它们是注解不是标题的一部分；`必填` 用红色那一档。
2. **下拉自己画箭头。** 系统原生那个在两套主题下颜色和大小都不受控，
   而且没有箭头时下拉框和只读文本长得一模一样，根本看不出这里能点。
   坑：`.fld > select { background: … }` 会把箭头一起清掉，必须写 `background-color`
   （`.plan-switch` / `.proj-switch` / `.sess-pick` 三处都踩了同一个坑）。
3. **重点字段一条左边线 + 标签变色**（`.fld.key`），只给"决定模型怎么干活"的那几个：
   怎么拆、学到什么份上、目标。全都高亮等于都不高亮。

顺手把话说清楚：「口径」→「怎么拆」，选项写成「学习 · 按依赖顺序」；
对话条上的口径下拉写成「口径 · 教练」（光两个字看不出那是干嘛的）；
每个字段补一句说明，说的是**填了会怎样**而不是它叫什么。

e2e 里钉死的是几何与属性（标签在输入框上方、输入框占满整行、下拉有箭头且留出了位置），
不钉颜色——颜色随主题走，量它只会让测试天天红。

## 梳理游标与正文增量（2026-09-17）

问题原话：「我第二天点击还会重新梳理一下吗？这不浪费算力吗？能否加一个游标？当我采纳内容，
并且成功落文件之后，再更新游标」「我这个本身就是 md 笔记，能丰富 body 内容是吧？
比如梳理之后，给我不断完善笔记内容，而不是单纯只有技术点名字」。两条都成立，共四处改动。

**1. 梳理游标（`.knowrary/chat/<项目>/tidied.json`）**

原来「梳理这段」每次都把整段对话重发一遍：第二天重开页面，`history()` 把这一段从留档读回来，
chatLog 又是满的，再点一次就是把昨天那笔钱原样再付一遍——而梳理恰好是这里**最贵的一次动作**
（`MAX_STEPS` 的工具循环，每一步都把累积的 messages 再发一次）。

游标是**和 `titles.json` 同族的一张贴纸，不是真值**：删掉它只会退回全量重梳，一个字的知识都不丢。
两条纪律：

- **只在变更卡真写进 md 之后才推进**（`applyChatCard` 写盘成功那一行之后）。
  梳理过但没点写入的不算整理过——放在梳理那一轮结束时推，会让"看了一眼没采纳"变成永久跳过。
- **只进不退**：一次对话里先写后面那张卡、再回头写前面那张，游标不该被拖回去。
  比较按时间不按字符串——留档的 ts 带本地时区偏移，跨时区/夏令时之后字符串序和时间序不是一回事。

坐标用留档行的 `ts`，所以 `/api/chat/history` 的每条消息和 `done` 事件都把 ts 带回前端
（原来前端的消息是"没有坐标"的）。界面上两个效果：游标之后没有新内容时**按钮直接置灰**
（零成本的那一半收益），有新内容时**这一轮只发游标之后那几条**，前面用一句
「前 N 条已经梳理入库过了，当时开头问的是 …」带上话题锚——不给锚的话，模型看着半截对话
不知道这是在聊什么，搜出来的节点和连出来的边都会跑偏。

**2. `read_node` 不再把正文截到 1200 字**

这是个**会吃掉笔记的数**：模型拿到截断过的原文，再用 `update_body`（整段替换）写回去，
超出那 1200 字的后半截就被永久删掉了。而"不断完善 body"这个需求本身就是把所有节点
往那条线外推。现在预算 8000 字，真截断时结果里会直说「这个节点只准 `append_body`」。

**3. 新增 `append_body`：只追加不替换**

`update_body` 要求把原文一字不落带回来——但往笔记里补一段本来就不需要读全篇。
`append_body` 只往 `## 关系` 之前的正文尾部接一段，从根上免掉"带少了就等于删"的风险，
现在是补内容的默认路径。`update_body` 留给真要重写/合并的场合，并且加了最后一道人眼防线：
**正文缩水超过四成时，卡片上直接写一行 ⚠️**（diff 里看得见，但卡片上的一行字更看得见）。

**4. 正文骨架 + `read_node` 一次读多个**

「只有技术点名字」的直接原因是给模型的格式说明里 body 只有一句"正文：讲清楚这个概念"。
现在给了骨架：是什么 / 为什么需要它 / 怎么运作 / 容易搞混的 / 我当时怎么想通的，
并且**「没懂：…」要原样留着，不许替我编圆**——这套东西的价值建立在记录诚实上，
正文里的空白和复习记录里的"忘了"是同一件事。

`read_node` 支持 `ids`（一次最多 5 个，总预算 16000 字）则是骨架能落地的前提：
一轮只有 `MAX_STEPS` 步，要往 5 个已有节点补内容，一个一个读是 search + 5×read + propose = 7 步，
几乎顶格，模型会读到第三个就放弃后面两个。

## 对话里的图：实测代价与两个真 bug（2026-09-17）

问题原话：「我就是想让模型输出可视化的图，光是文字不太形象，会造成卡顿啥的？」

**先说结论：不卡。** 用无头 Chrome + `__kg.fakeReply` 实测（`web/tests/e2e_canvas.py` 同一套 harness）：

| 场景 | 耗时 | 新下载 | JS 堆 |
|---|---|---|---|
| 首屏（没画过图） | — | 972 KB | 6.5 MB |
| 第一张图（含懒加载引擎） | 263 ms | 2196 KB | 17.6 MB |
| 第二张图（引擎已热） | 39 ms | 117 KB | +0 |
| 31 个节点的大图 | 140 ms | 0 | +3.8 MB |

`dist` 是 6.1 MB，但首屏只下 972 KB——`Markdown.vue` 里 `await import('mermaid')` 是真懒加载，
**不画图的对话一个字节都不下**，而且服务跑在本机，那 2.2 MB 是本地磁盘读。

那 2.2 MB 里有 1.4 MB 是 elkjs：mermaid 12 的顶层 `defaultConfig.layout` 就是 `"elk"`，
所以画一张 `flowchart TD A-->B` 也会把它拉下来。**没改**——本地加载无感，
换成 dagre 的代价是所有流程图的版式都变。

**但量出两个真 bug，都和性能无关：**

1. **深色主题下图还是浅色的。** 引擎只 `initialize` 一次，主题在那一刻定死；
   之后切深色，新画的图仍然是浅色底那张惨白的（实测填充色 `rgb(236,236,255)`）。
   改成模块级 MutationObserver 盯 `<html data-theme>`，变了就重新 initialize 并整条重画。

2. **流式期间每来一个增量就把整条消息的图全部重画。** watch 里无条件清空缓存，
   而每个 delta 都会重新赋值 `reply.content`——已经画好的图会消失一下再出现（闪），
   每张图 15~140 ms 全是白烧的。claude-cli 是**块级**增量所以只闪几下；
   一旦把 `roles.learn` 换成逐 token 的 provider（`llm_backend.py` 里 anthropic / openai
   两条都是 `on_delta(piece)`），就是几百次重画，直接卡死。
   改成**按图的源文本身做缓存 key**：源文没变就命中缓存，正文再长也不重画。

**改完踩到的坑，比 bug 本身更值得记：** 按源文缓存等于去掉了原实现里隐含的"无限重试"——
原来每次 text 变都清空重画，一次没画成下次自然重来；改完之后一张图只有一次机会，
那一发没成就永远停在"还在画…"。全套 e2e 因此变成 flaky（同一份 dist 一次 185/188 一次 190/191）。
补了三处才稳：`await boot()` 移进 try（引擎拉不下来要记错误，不能静默挂住）、
`render` 加 10 秒超时（卡住不 resolve 时也留下痕迹）、失败的 key 只缓存到源文变化为止。

**两条新断言第一版都是假通过的**，这件事要专门记一笔：「图没被重画」写成了比较两个 svg id 数组，
而一张图都没画出来时 `[] == []` 恒真；「主题换了」写成 `fill != 浅色`，而重画那一瞬间取到的是
`no-rect`，也 `!=` 浅色。**断言必须先确认被测对象真的存在**，否则它只会在功能坏掉时更容易"通过"。
收紧后连跑三轮全套，191/191 × 3。

为了能验第 2 条，给 `__kg` 加了 `growReply(text)`：往最后那条回复上接一段，形状和流式增量一样。
生产构建里 `__vueParentComponent` 是不挂的，不加这个入口就只能靠"看代码觉得对"。
