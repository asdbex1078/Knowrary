## Context

现在的组织单元是「学习计划」（`plans.json`，3 份：Transformer 44 点、AI技术发展史 30 点、计组 0 点）。
要把组织单元升一级成「项目」：一个项目下有学习计划、考试、错题本、面试方案、一段对话，
由对话指挥 agent，系统提示词从项目配置生成，不同项目分开学。

真正的难题是**项目之间会重叠**。第一个项目 Transformer、第二个 CNN、
第三个 NLP——NLP 既是前两个的父级，CNN 和 Transformer 之间又有交集（反向传播、梯度下降）。

另外三个想法一并设计：学/考双态标记、项目独立画布 + 同步到全局、学习日历。
以及一个反复出现的疑问：**要不要上数据库**（§7）。

## 1. 核心判断：项目是「视角」，不是「容器」

推理链：

1. 知识图谱全局唯一——md 是唯一真值源，这是整个项目最硬的纪律。
2. **复习调度也必须全局唯一。** 同一个大脑不可能"在 NLP 项目里记得 Transformer、
   在 Transformer 项目里忘了"。这是生理事实，不是技术选择。
3. 所以项目**不能拥有节点，只能引用一组 node_id**。

一旦项目只是选集，下面三种情况**全部自动消解，不需要任何额外建模**：

| 场景 | 怎么自动成立 |
| --- | --- |
| **交集**（Transformer ∩ CNN = 反向传播、梯度下降） | 两个项目的清单里都列它，掌握度是同一个 |
| **子集**（NLP ⊃ Transformer） | NLP 的选集包含 Transformer 的全部点，**不需要显式父子** |
| **后来的父级**（先建 Transformer，再建 NLP） | 建 NLP 时把已有节点选进去，**不用重构已有项目** |

**已确认：不做显式父子关系。** 一旦有 parent 字段就要回答"子进度算不算父的、父改了子跟不跟、
能不能有两个父"，而这些答案选集重叠免费就给了。更重要的是——**层次本来就该在知识层表达**：
要说"NLP 包含 Transformer"，那是图上一条 `包含::` 边。在项目层再建一套层级 = 同一件事存两份，必然漂移。

**必须在界面上说清、否则会被当成 bug 的一条**：在 A 项目复习了 Transformer，B 项目里它也显示"已复习"。
这是对的——同一个大脑。今日清单按 node_id 去重（`core/coach.py` 已实现），不会重复出现。

## 2. 哪些建实体，哪些是派生视图

| 需求里的东西 | 做法 |
| --- | --- |
| 学习计划 | **实体**：项目 `lists` 里 `kind=学习` 的一条 |
| 领域地图 | **实体**：项目 `lists` 里 `kind=领域` 的一条（拆解口径不同，数据结构相同） |
| 面试方案 | **实体**：项目 `lists` 里 `kind=面试` 的一条（可以有多条，一家公司一条） |
| 考试 | **派生**：按项目范围调 `/api/quiz`，不建实体 |
| 错题本 | **派生**：`quiz-log` 按项目范围过滤聚合（复用 `core.wrong_nodes`） |
| 学习进度 | **派生**：`review-log` + `quiz-log` 现算（沿用 F10.2 的"progress 不落盘"） |
| 对话 | **实体**：按项目分文件的 JSONL（另一 session 实现，契约见 §8） |

**绝不给每个项目建自己的错题本。** 同一节点在两个项目里答错就会有两份记录，必然漂移——
和"进度派生不落盘"是同一条纪律。

## 3. 数据模型：`plans.json` → `projects.json`

```json
{
  "schema_version": 2,
  "revision": 11,
  "updated_at": "…",
  "projects": {
    "transformer": {
      "name": "Transformer", "goal": "三个月吃透…",
      "coach": "大模型", "field": "AI",
      "created": "2026-09-15", "target_date": null,
      "weekly_hours": 10, "daily_quota": 3,
      "lists": [
        { "kind": "学习", "name": "主线", "goal": "三个月吃透…",
          "stages": [ { "name": "…", "deadline": null, "points": [ {"id","name","why","load"} ] } ] },
        { "kind": "面试", "name": "字节一面", "goal": "JD 原文", "coach": "Java 后端开发",
          "stages": [ … ] },
        { "kind": "领域", "name": "NLP 全景", "stages": [ … ] }
      ]
    }
  }
}
```

- **`kind` 不取消，但降一层：它属于「清单」，不属于「项目」。**（2026-09-16 修订，见下）
- 一个项目下挂一个 `lists` 数组，每条是一份清单：学习主线、某一家的面试方案、某个领域的全景图。
  三者 `stages` 结构完全一致，所以 `progress_of` / `current_stage` 全部复用，只是传入不同的 stages。

> **为什么不是原来的「取消 kind + 内嵌一个 `interview`」（2026-09-16 修订）**
>
> 本方案初稿写于「学习 / 面试」两种口径的时代。2026-09-15 又落地了第三种：`kind: 领域`
> ——「初始化一个领域的所有点」并成了拆解口径之一，配第三份模板
> （`prompts/plan.md` / `plan-interview.md` / `plan-map.md`，见设计文档 F10.3b）。
> 于是「有没有 `interview`」这个二元判据不够用了：再加一个 `map` 内嵌槽就是三个并列具名槽，
> 而且答不了「能不能有两份面试方案（两家公司）」。
>
> 关键在于**看清 `kind` 到底决定什么**：它只决定两件事——**用哪份拆解模板**
> （`server/plans.py` 的 `TEMPLATES` / `OPS`）、**用哪套出题口径**（`server/quiz.py` 的 `STYLES`）。
> 它从来不是"项目的类型"，而是"这份清单是怎么拆出来的"。放在项目上是层级放错了。
>
> 代价是零：§9 本来就要把 `progress_of` / `current_stage` 从"收整个 plan"改成"收 stages"，
> 收成数组是同一次重构；而 `interview` 那个特例直接消失，少一条分支。

### 迁移（已确认：全部自动迁，先备份）

| 现有 | 迁成 |
| --- | --- |
| `新计划`（Transformer，kind=学习，44 点） | 项目 `transformer`，一条 `kind=学习` 的清单 |
| `新计划3`（AI技术发展史，kind=学习，30 点） | 项目 `ai-history`，同上 |
| `新计划2`（计组，kind=学习，0 阶段 0 点） | 项目 `arch`（保留空壳，由人决定删不删）——**id 只允许 ASCII**，见下 |
| 将来任何 `kind=面试` / `kind=领域` 的 | 项目 + `lists` 里对应 kind 的一条（`goal` 原样跟着走） |

- **项目 id 只允许 ASCII**（`[A-Za-z0-9_-]`），显示名另存 `name`。原因是 id 会成为
  `.knowrary/chat/<project_id>/` 的目录名（§8），中文目录名加上将来改名，迁起来纯属自找麻烦。
  所以 `计组` 迁成 `arch`，`name` 仍是「计组」。
- 迁移前整份备份到 `.knowrary/backup/migrate-projects-<时间戳>/`，可回滚。
- `load_projects` 读到 `schema_version: 1` 或顶层是 `plans` 时**在内存里就地升级**，
  沿用 `core/review.py` v1→v2 的做法：**读不写盘**，下次保存才落成 v2。
- **迁移时要报出来的数据问题**：`transformer` 项目的 `field` 是 `AI-Agent`，
  而这个领域今天已经被改名清空了（现在只有 `AI` / `Agent` / `计算机体系结构`）——
  这会让「建」按钮算错落脚点（与 2026-09-15 修过的「计划领域没参与落脚点计算」是同一类问题）。迁移脚本要检测并提示，不擅自改。

## 4. 学 / 考 双态标记

目标：每个点左边一个「学」、右边一个「考」，学完 / 考完各自变绿，一眼看出这个点卡在哪一步。

**这不是新数据，是五档掌握度的另一种编码**，更适合一眼扫。仍然全部派生：

| 标记 | 状态 | 判据 |
| --- | --- | --- |
| **学** | 灰 | 未建（图里没有这个 id） |
| | 红 | 只有壳（节点在、`status: stub`） |
| | 绿 | 有正文 |
| **考** | 灰 | 没考过（`review-log` 无记录，且错题本里没有） |
| | 红 | **错题本（`quiz-log`）里有它**，或 `review-log` 最近一次是「忘了」 |
| | 黄 | 最近一次是「模糊」，或已到期（`next_due ≤ today`） |
| | 绿 | 最近一次是「记得」、没到期，**且错题本里没有它** |

**判据的优先级必须写死：错题本压过自评。**（2026-09-16 补）「考」有两个数据源，而且它们**可以合法地互相矛盾**：
`review-log` 的三档来自**我自评**，`quiz-log` 里模型判的 `missed` / `wrong` 才是错题本
（`core.wrong_nodes` 聚合的就是它）。F9.4 定过**模型判分只许降级、且要我点一下才生效**——
所以完全可能出现「测验里模型判我答漏了，我自评点了『记得』」：`review-log` 绿，错题本里却躺着它。
这时显示绿就把错题盖住了，而错题本的全部价值恰恰在这里。所以只要错题本里有它，「考」就是红的。

**考必须有"红/黄"而不只是"绿/灰"**：考过但答错，和没考过是两回事——前者更该被拉回来重考。
直接"考完就变绿"会掩盖答错的情况，而错题本的价值恰恰在这里。

呈现位置：
- 项目面板每个点前（替换现有的五档 chip，信息量更大、更省横向空间）
- **画布节点上**：右上角现在已有"到期金色圆点"（`canvas/shapes.js:131`），扩成左下角两个小方块。
  缩小到簇卡片时不画（性能守则）。

### 「学完之后知识图谱自动扩展、自动收入」

理解为：一个点从「未建」变成「已建」时，自动上画布，不用手动拖。

现有链路已经有：`POST /api/place` 按邻居投票找位置，落下是 **draft（金色虚线）**，确认位置后「定稿」。
所以只需在"建完节点"之后自动调一次 place。**保持 draft 态**——不要直接 final，
位置是机器猜的，得由人确认（设计文档 4.1「程序只写 draft、只在分组内、不动 final」）。

### 「第二天进来能预览今天要学的点」

今日清单（`/api/coach/today`）已经算得出来，缺的是**开场就看见**。
加一张**晨间简报**：当天第一次打开时自动弹出（`localStorage` 记当天日期，一天只弹一次），内容：

```
今天 · 3 个新点 · 5 个待复习 · 2 个错题
建设：神经网络与反向传播 → 卷积 → 池化
复习：Transformer、CUDA、TPU…
预计 1.5 小时（按 weekly_hours 折算）
```

一天只弹一次、可关掉、能直接从上面开始动手。

## 5. 视图重排：对话全屏，图分全局与项目两层

> 2026-09-16 修订。首版把对话做成了 420px 的左抽屉（`panels/ChatPanel.vue`），
> 试用下来不对：**对话不是一个工具面板，它是主界面。** 挤在抽屉里既读不下长回答，
> 也看不见正在聊的那些点在图上是什么位置。

### 5.1 三个视图模式，不再是两个

现在 `App.vue` 的 `mode` 只有 `structure | history`（`:92`、`switchMode:370`，快捷键 1 / 2）。
改成四个，顶栏 tab 与快捷键一并扩：

| 模式 | 快捷键 | 内容 | 范围 |
| --- | --- | --- | --- |
| **对话** | 1 | 全屏聊天，右侧可收起的图 pane | **项目** |
| **项目图** | 2 | 该项目的画布（含未建的幽灵点） | **项目** |
| **全局图** | 3 | 现在的结构视图，一个字不改 | 全局 |
| **历史** | 4 | 现在的历史视图 | 全局 / 可按项目过滤 |

**默认落在「对话」**：启动成本最低的入口应该是默认入口。

### 5.2 对话屏的布局

```
┌──────────────────────────────────────────────────────────┐
│ [项目 ▾ Transformer]   对话 · 项目图 · 全局图 · 历史   [↗ 全局图] │  ← 顶栏
├───────────────────────────────┬──────────────────────────┤
│                               │  项目图（可收起）          │
│   对话流（全屏主体）            │  · 聊到的点自动高亮        │
│   · 变更卡内联展示 diff         │  · 点节点 → 把它带进对话    │
│   · 「写入」才落盘              │  · 未建的点画成幽灵        │
│                               │                          │
├───────────────────────────────┴──────────────────────────┤
│ [今天学什么] [考考我] [讲个概念] [这段学完了]   输入框      │
└──────────────────────────────────────────────────────────┘
```

三条交互把对话和图真正绑在一起——**这是全屏改造的全部理由，否则只是把抽屉拉宽**：

1. **聊到哪，图上亮哪。** 每轮回答里提到的 node_id（`chat` 返回里本来就有）在右侧图上高亮，
   复用 `canvas/render.js` 的 `highlightPath`（已有，今天刚修过它的还原逻辑）。
2. **点图上的节点 → 带进对话。** 把该节点的摘要与出入边塞进下一轮上下文，
   省掉"我想问 XX"这句打字。
3. **变更卡落盘后，图当场长出来。** 新节点按 §4「自动上画布」的规则落成 draft，
   右侧 pane 立刻能看见——这就是「学完之后知识图谱自动扩展」的实现位置。

图 pane 可收起（记 `localStorage`），收起后就是纯全屏对话。

### 5.3 顶栏的全局入口

顶栏右侧常驻一个 **「↗ 全局图」**：任何模式下点它都切到全局结构视图，
并**把当前项目的点在全局图上高亮**——回答"我学的这些东西，在整张图里是什么位置"。
这是项目视角与全局视角之间唯一需要的桥，不需要更多层级。

项目切换器放顶栏最左（`AppHeader.vue`），因为**它决定了下面三个模式看到的范围**，
不该藏在某个面板里。

### 5.4 对话面板与旧面板的关系

`ChatPanel.vue` 从 `Drawer` 里搬出来，变成一个占满 stage 的视图组件（`views/ChatView.vue`）。
左侧 ActivityBar 的 `chat` 图标**去掉**——它不再是工具窗口之一。
其余面板（今日 / 项目 / 素材 / 时间线）保持不动，在「项目图」「全局图」模式下照常用。

## 5A. 项目画布 + 同步到全局

目标：每个项目一张自己的画布，点「同步到全局」才并进全局视图。

**这不违反"一张全局图"的决策**（设计文档 4.1）。全局图仍然是唯一的成品图；
项目画布是**工作台**——新东西先在自己的小天地里长，成熟了再并进主图。
这正好呼应既有的三态设计：**项目画布 ≈ 一个按项目分组、可排版的 Inbox**。

动机是真的：一份 JD 拆 30 个点，直接掉进全局图会把主图冲垮。

### 做法（复用现有机制，不新增放置算法）

| | 全局画布 | 项目画布 |
| --- | --- | --- |
| 文件 | `.knowrary/layout.json`（不变） | `.knowrary/layouts/<project_id>.json` |
| 契约 | `LayoutDoc` | **同一个 `LayoutDoc`**，不新增契约 |
| 内容 | 全部已定稿节点 | 只有该项目的点（含「未建」的幽灵位） |
| 谁写 | 现有 PATCH | 同一套 PATCH，多一个 `?layout=<project>` |

- `server/layout_store.py` 现在硬编码单文件路径（`server/paths.py:31` `layout_path()`），
  改成接受一个 layout 名（默认 `layout`）。

**不止这一处——"唯一的结构性改动"这句话是低估的（2026-09-16 核过代码后修订）。** 一份 layout 变多份，
跟着要按 layout 分的至少还有三处：

| 地方 | 为什么跑不掉 |
| --- | --- |
| `knowrary layout check` CLI（`knowrary.py:278`） | 同样硬编码单文件，要加 `--layout` |
| **前端 undo/redo 与 patcher**（`App.vue:113` `createHistory()`、`:2299` `createPatcher`） | **单实例**。在项目画布上撤销，可能把补丁打到全局 layout 上——这是数据损坏级别，不是体验问题 |
| e2e 的 `ck.layout()` 助手 | 只认一份，跨 layout 的用例写不出来 |

反过来，**3D 视图不受影响**：它只读 `/api/index`，明确不碰 layout（`web3d/src/main.js:1`）。
四期的排期按"四处"估，不要按"一处"估。
- **「同步到全局」** = 对该项目中尚未出现在全局 layout 的节点，调现有的 `POST /api/place`
  （服务端按邻居投票找位置，落 draft）。已经在全局里的跳过。
- **不搬坐标**：项目画布里的排版是你为了想清楚而摆的，全局图有自己的结构。
  搬过去只会打乱主图——这条要在 UI 上明说，否则会被当成 bug。

### 去重要发生在写入之前，不是之后（2026-09-16 补）

上面的"已经在全局里的跳过"只按 **node_id 精确比对**，**近义重复一个都拦不住**。
这不是假想：2026-09-15 同一个 Transformer 目标被拆了两次，得到 `RNN` / `RNN与长程依赖`、
`BPE分词` / `子词分词-BPE`、`因果掩码` / `注意力掩码` 三对近义词，服务端的 id 去重全部放行
（见设计文档 F10.3b）。对话这条路更容易触发：聊完让它入库，它建一个「自注意力」，
而图里可能已经有「self-attention」。

能力其实都有了——`/api/suggest` 的重复候选、欠账清单的「重复候选」、`/api/merge`——
方案缺的只是**接在哪一步**。结论是：**接在写入之前。**

| 时机 | 后果 |
| --- | --- |
| 写入前（采纳） | 当场问一句"图里可能已有 X，改成连到它？"，图始终是干净的 |
| 写入后（欠账里捞） | 等于默认让图先脏一次，再指望人回头清——而"回头清"正是最容易不做的事 |

落点两处，都不新增接口：

1. **变更卡**（§8 契约 3）：展示 diff 的同时，对每个 `create_node` 跑一次重复候选检查，
   命中就在卡上标出来，并给一个"改成连到既有节点"的按钮（把 `create_node` 换成 `add_edge`）。
2. **「同步到全局」**（本节）：跳过的判据从"id 已存在"扩成"id 已存在**或**命中重复候选"，
   命中的不静默跳过，列出来让人选：合并过去、还是确实是两个东西。

**判据仍然只提议、不自动合并**（4.4）。自动合并两个看起来像的节点，
比让图里多一个重复节点严重得多——前者会悄悄吃掉一份正文。

### 「未建」的点怎么在项目画布上表示

画成**幽灵节点**：比 stub 更淡的灰虚线，点一下就开新建对话框（复用 `App.vue` 的 `buildPoint`）。
这样项目画布从第一天就是完整的施工图——你能看见还没建的东西在哪，而不是一片空白。
幽灵节点**只存在于项目画布**，绝不进全局 layout，也不进 vault（沿用"推测出来的东西不进真值源"）。

## 7. 关于数据库：现在还不用，但给出明确的触发条件

"东西越来越多、越来越像一个系统，是不是该上数据库了" —— 这个直觉有一半是对的，
但**要区分是哪一层**：

| 层 | 内容 | 判断 |
| --- | --- | --- |
| **知识层** | `nodes/*.md`、`layout.json`、`projects.json` | **永远不进数据库。** 它们要能被 Obsidian 打开、被 `git diff`、被手改、坏了能肉眼修。这是这个项目的立身之本 |
| **行为层** | `review-log`、`quiz-log`、`llm-usage`、将来的 chat / sessions | **候选**。追加型时序数据，没人会手改，也不需要 Obsidian 认识 |

### 诚实的反面证据

这个直觉不是没道理。2026-09-15 为了 rename 和 merge，专门写了两个模块去同步
**5 个文件里的同一个 node_id**（md 的 `[[链接]]`、layout 的 nodes/edges/refs/doc、
review-log、quiz-log、plans）——**这正是关系型数据库用外键免费解决的事**。

但代价换过来看：进了数据库，md 就不再是唯一真值源，Obsidian 打不开，git 看不见 diff，
而那才是这套东西真正值钱的地方。所以**宁可自己写 rename/merge，也不换掉 md**。

### 触发条件（满足任一条再重新评估行为层）

1. `quiz-log.json` 超过约 **1 万条**作答（现在个位数）；
2. 需要"按项目 × 按周 × 按掌握度"这类**交叉统计**，而不只是按 node_id 聚合；
3. 单次读取行为层文件超过 **50ms**，开始拖慢今日清单。

届时的迁移路径是收敛的：**只把行为层搬进 SQLite**（`.knowrary/behavior.db`），
知识层一个字节不动；`core/review.py`、`core/quiz.py`、`core/usage.py` 已经是
"load / save / 聚合"三段式，换存储只改这三个模块的内部，上层接口不变。

## 8. 对话的三条契约（已落地，核对用）

对话先于本方案落地，下面三条是当初定的契约，实现时已经遵守；重构时不许破坏：

1. **对话留档**：一行一轮 `{ts, role, text, node_ids}`，按月分文件。沿用 F10.7 已定的结论：
   **不建 SQLite、不做切分、不做 embedding**（门槛写在 F10.7：累计超 5 万轮，
   或反复出现"记得聊过但 grep 找不到"）。
   ✅ 已实现（`server/chat.py:186` `chat_log_path`），`.gitignore` 也已加 `.knowrary/chat/`
   ——留档是过程不是知识，不入库。
   ❌ **但"按项目分文件"这一条没有落地**：实现时项目还不存在，落盘路径是
   `.knowrary/chat/YYYY-MM.jsonl`，**没有项目那一层**。所以它不是"已遵守的契约"，
   而是**一期要补的迁移**：
   `.knowrary/chat/<project_id>/YYYY-MM.jsonl`，现有那份整体挪进 `_scratch/`（见下）。

   **未绑项目的对话去哪：`_scratch/`。** 这是一期必须回答的问题，因为 §5.1 把「对话」
   定成了默认视图——冷启动时一个项目都还没有，"随手问一句 CAS 的 ABA 怎么解决"必须有地方落。
   两条路：强制对话绑项目（那就得先逼人建项目，直接违背"启动成本最低的入口应该是默认入口"），
   或给一个兜底目录。**选兜底**：`.knowrary/chat/_scratch/YYYY-MM.jsonl`，
   界面上标成「未归档」，将来可以把某一段挪进某个项目，但**首版不做这个搬运功能**
   ——grep 找得到就够了，别为一个每月用一次的动作写 UI。
2. **系统提示词现场拼，不落盘**（落盘就是第二份真值）。材料全部来自项目配置与派生量：
   项目名 + **当前清单**的 `kind` / `goal`（面试清单就是 JD 原文）+ `coach` 侧写
   + 当前阶段及其各点的学/考双态
   + 最近错题 + `relation-types.json` 的类型表（供蒸馏用）。
3. **对话能触发的动作一律是现有接口的封装，且一律走确认**：
   建节点（`create_node` ChangeSet）、连边（`add_edge`）、出题（`/api/quiz`）、
   记复习（**只许降级不许升级**，F10.5 已定）。不新增绕过 ChangeSet 的写路径。
   ✅ 已实现为「变更卡」：模型给卡片、展示 diff、点「写入」才落盘。
   ⬜ **待补：卡上要标重复候选**（见 §5A「去重要发生在写入之前」）。
   现在模型被 prompt 要求"讲之前先 `search_nodes`"，但那是软约束；
   真建出一个「自注意力」而图里已有「self-attention」时，卡片上必须当场看得见。

**重构时新增的第 4 条**：对话回答里带回的 node_id 是 §5.2「聊到哪、图上亮哪」的输入，
所以 `/api/chat` 的返回必须继续带它——这从一个调试信息升级成了界面契约。

**§5A 说的那个隐患解掉了。** 前端 undo/redo 是单实例，跨画布撤销会把补丁打到错的文件上——
这是数据损坏级别，不是体验问题。做法是**切 layout 时先 flush、再清空撤销栈**
（`history.reset()`），而不是维护两套栈：栈里存的是"某一份 layout 的前后快照"，
两套栈同时活着只会让"现在该撤哪一份"变成新的 bug 来源。
patcher 则拿到一个 `getLayoutName()`，每次 PATCH 自己决定写去哪份文件。

**幽灵节点判定踩了一个自己挖的坑**：为了让幽灵显示出标题，渲染时给它合成了一个
`indexNode`，结果 `ghost = state === 'ghost' && !indexNode` 永远为假——样式压根没生效。
改成由调用方显式传 `ghost` 标志。这类"为了显示方便合成一个假对象，结果把判据打翻"
的错误，只有真浏览器跑一遍才看得见（e2e 直接读 `stroke-dasharray` 断言）。

**用例**：core 57、服务端 98（新增「项目画布与全局图互不影响」「同步到全局只放该放的且不搬坐标」
「同步前先把重复候选摆出来」）、e2e 118（项目画布只画本项目的点含幽灵、幽灵的线型、
动项目画布不碰全局 revision、同步按钮给出逐条结果、同步不搬坐标）。

**真实数据验证**：`transformer` 项目画布 44 个节点里 43 个是幽灵（这个项目确实才刚开始建），
孤立记录 0；对它点同步，结果是"43 个还没建出来、1 个已经在图上"，**全局 layout 一个字节没动**。

## 试用后的修补（2026-09-16，五期之后）

前四期做完实际点了一圈，暴露出三件事：

**1. 切项目后项目画布是空的（真 bug）。** `switchProject` 换了 `currentProject` 却没重新拉那份
layout——画的还是上一个项目的 `layoutDoc`，被新项目的 `only` 过滤一遍就什么都不剩。
更糟的是接下来的拖拽会拿着**旧 revision 去写新文件**，必 409。
修法：切项目时先 flush、清撤销栈、重新拉 layout，再 render。
用真浏览器复现出来的：服务端那份有 2 个节点，画布画了 0 个。

**2. 「全局/不绑项目」那条线在界面上没有入口。** 顶栏切换器永远选着一个项目，
于是 `_scratch`（§8 定的兜底）**根本走不到**。用户的体感是"在对话里切了个项目，
当前这段对话就被吃了"——其实是被换成了那个项目的线，而他原来那段在 `_scratch` 里再也回不去。
修法：切换器加一档「🌐 全局（不绑项目）」，空串是合法值。

**3. 记住上次看的哪个项目。** 刷新后总是回到第一个项目。这**不是数据库问题**，
是个界面偏好——`localStorage` 一行就够。注意空串（全局）是合法值，
所以要用 `null` 区分"没存过"，不能拿 `||` 兜底。

顺带落地了**对话里建项目**（`propose_project` 工具 + 项目卡）：
全局对话里说"帮我建个 NLP 项目"，模型出一张卡，点「创建」才写 `projects.json`。
**建完清单是空的**——拆点是另一步（prompt 里明说了别在同一条消息里全干完），
这样每一步都还是"提议 → 人点"，没有绕开 4.4。

**口径切换（2026-09-16，替代"多 agent"）**

「教练 / 面试 / 聊天」不做成三个 agent，做成**同一条链路上的三套提示词 + 三份工具白名单**——
和 F10.3b「拆解口径不同 ≠ 架构不同」是同一条判断。多开一套 agent 运行时要付会话路由、
上下文传递、状态同步、翻倍 token 的代价，而收益只是换一套系统提示词。

| 口径 | 工具 | 为什么 |
| --- | --- | --- |
| 教练 | 全套 | 盯进度：今天学什么、该复习了、来不来得及 |
| 面试 | 只读 + `quiz` + `record_review` | **不给入库和建项目**——边考边改图谱等于开卷，也打断面试节奏 |
| 聊天 | 只读 + `propose_changes` | 只把事情讲清楚；不给 `today` / `projects`，免得每句话都被催进度 |

两条实现上的要紧处：

1. **工具表从白名单渲染，不写死在提示词里。** 说明书和实际权限必须是同一份数据——
   "表里写着能用、调了却说没有"是最让人发火的那类 bug。带格式说明的两个写工具（建项目、入库）
   也跟着白名单一起渲染。
2. **换口径就新开一段。** 混在同一段里，前半截是面试后半截是闲聊，模型会被自己的历史带跑。

用量按口径分开记（`chat-教练` / `chat-面试` / `chat-聊天`），否则算不清备考烧了多少。

真正需要独立 agent 的信号只有三个：**要并行跑、要不同的工具权限、要互相审查**。
第二个用白名单就解决了；第三个其实已经有了，就是 `learn` / `review` 双角色 provider。
等出现"一边模拟面试、一边让另一个模型实时判卷"这种**必须并行**的场景再说。

**顺手修掉的三个 UI 问题**（都是试用时发现的）：

- **两个「全局图」**：顶栏 tab 一个、右边按钮又一个，文案一样。合并掉——
  选着项目时切到全局图 tab 会顺手高亮那些点，桥就是 tab 本身，不另设控件。
- **`nextTick` 没 import**（真 bug，藏得很深）：`switchMode` 和 `toggleGraphPane` 里
  `await nextTick()` 抛 ReferenceError，**把后面的代码整段吞掉**——表现是"切到全局图不高亮"
  和"收起图 pane 后画布不重新量宽"，而控制台里只有一句被 toast 吞掉的报错。
  查法：往 `window.__kg` 上挂 mode / project / projectIds 几个 getter，
  再在函数里逐段打桩，才定位到是哪一行断的。这几个 getter 留下了——
  排查"为什么没高亮 / 为什么画布是空的"这类问题，没有句柄就只能靠猜。
- 切模式后的 `await nextTick()` 现在包在 try/catch 里：**渲染期一个报错不该把后面的事全断掉**。
