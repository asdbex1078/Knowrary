散在五份设计文档里的「要不要上 X」，判据其实是同一套。
这份文档把判据立在一处，具体决策各自成篇——**这样以后每遇到一次新选型，
加一篇文章、往总表加一行，而不是往某份大文档里再塞一节。**

## 1. 四条约束

这个项目有四条贯穿始终的约束。它们不是偏好，是产品本身：

| # | 约束 | 一句话 | 出处 |
|---|---|---|---|
| **约束 1** | **md 是唯一真值源** | 要能被 Obsidian 打开、被 `git diff`、被手改、坏了能肉眼修 | 《项目化重构方案》§7 |
| **约束 2** | **能力边界写在服务端** | 提示词会被绕过，工具白名单不会 | 《Agent架构与选型》§0 |
| **约束 3** | **上界由代码封顶** | 图谱再大、笔记再长，单轮 prompt 与单屏渲染的上界不变 | 《上下文分层加载》 |
| **约束 4** | **消息列表只增不改** | 三种后端的省钱手段要的都是同一件事：前面那一截一个字都别动 | 《Agent架构与选型》§3.8 |

## 2. 主判据：数一数冲几条

**把一个现成方案的默认行为，和这四条对一遍，数它冲几条。**

- **冲 0～1 条** → **用现成的。** FastAPI、X6、Vue、marked 都是这么进来的。
- **冲 2 条以上** → **自己写。** 因为这时候你不是"用框架"，是"绕着框架写"——
  而绕的成本不会一次付清，它跟着框架每次升级再来一遍。

这条判据的好处是**可证伪**，而且是双向的：《[被接受的依赖](被接受的依赖.md)》列了进来的那些，
《[MCP](MCP.md)》则是唯一一篇结论为"**该做，还没做**"的。
如果判据只会输出"都自己写"，那它就不是判据，是偏好。

### 2.1 一个推论

翻回去看被接受的那几个，共同点很齐：**它们都是"某一层的实现"，不是"整体的组织方式"。**

一个依赖越想决定你的代码怎么组织，它和四条约束撞上的概率就越大。
所以同样是"第三方的 LLM 相关代码"，SDK 进来了、框架没有——
**SDK 是"帮你发一个 HTTP 请求"，框架是"帮你跑一个循环"**，前者不碰消息列表的形状，
后者的全部价值就在于碰它。

## 3. 副判据：规模，以及一条能验证的触发线

向量库、数据库这类不是"对不对"的问题，是"到量没到量"的问题。

所以：**凡是以"现在还不需要"为理由拒掉的，必须同时写下一条能验证的触发线。**
否则"现在还不需要"会变成一句永远正确、永远不重新评估的话——
而那种话在一份设计文档里比说错还糟，它看起来像结论，实际上只是没想。

## 5. 每篇文章的固定格式

新加一篇时照这个来：

| 段 | 内容 | 能不能省 |
|---|---|---|
| **结论** | 一句话，写在标题下面第一行 | 不能 |
| **冲突点** | 冲四条约束里的哪几条，或者"不冲，纯规模问题" | 不能 |
| **代码级对照** | 现成方案怎么写 / 现在怎么写 / 卡在哪 | **还没真撞上就留空，别编** |
| **触发线** | 什么条件下重新评估 | 以"现在还不需要"拒掉的，必填 |
| **代价** | 放弃了什么、补了什么替代物 | 不能 |

**"代码级对照"允许留空，"代价"不允许。**
没撞过墙的选型写不出真对照，硬写就是编；但"放弃了什么"任何时候都答得上来，
答不上来说明这个决策还没想清楚。
