# 选型对照：MCP

> **结论：分两个方向。作 client 不做；作 server 该做，还没做。**
> 冲突：作 client 冲**约束 3**（多一跳换不来上界）；作 server 冲 **0 条硬约束**，
> 但会把"卡片那层软护栏"交到别人的客户端手里（§4）。
> 触发线：**出现第二个客户端。** 只要还只有 Claude Code 一家，现在这套手搓协议就够用。
> 代码：`server/chat.py`（`TOOLS` / `_invoke`）、`tools/knowrary/knowrary.py`（`context` / `apply`）、
> `.claude/skills/knowrary-import/SKILL.md`。
> 判据与总表：《[选型判据](选型判据.md)》。相关：《Agent架构与选型》§1、§9。

《Agent架构与选型》§9 里 MCP 那一行只有一句话——"工具全在自己进程里，跨进程协议纯属额外一跳"。
**这句话只回答了一半。** 它回答的是"教练 agent 要不要通过 MCP 调自己的工具"，
没回答"要不要把 Knowrary 暴露给别的 agent 客户端"——
而后者是同一节另一行明确点过名的方向。

**所以这一篇的第一件事是把两个方向拆开。** 它们的答案相反。

---

## 1. 两个方向

| 方向 | 谁调谁 | 现在是什么 | 结论 |
|---|---|---|---|
| **作 client** | 教练 agent 通过 MCP 调 Knowrary 自己的 11 个工具 | `TOOLS[name](vault, args)`，同进程函数调用 | **不做。** 纯属额外一跳 |
| **作 server** | 别的 agent 客户端（Claude Code / Cursor / …）调 Knowrary | 一份 skill + 两条 CLI 子命令 + 硬编码绝对路径 | **该做，还没做。** 现在这套能用，但只对一个客户端能用 |

混着谈会得出"MCP 没必要"这个错结论——**它对内没必要，对外是正解。**

---

## 2. 作 client：不做

### 2.1 现在是什么

`_invoke`（`server/chat.py:1486`）里，一次工具调用就是一次函数调用：

```python
fn = TOOLS.get(name) if name in allowed else None
if fn is None:
    return f"这一档口径下没有 `{name}` 这个工具。可用的是：{'、'.join(sorted(allowed))}。", {}
```

11 个工具全在同一个 Python 进程里，和 `current_index(vault)`、`curation.preview()`、
`core.add_question()` 共享同一份内存里的索引。

### 2.2 换成 MCP 会怎样

每次 `search_nodes` 变成：序列化参数 → 写 stdio / 发 HTTP → 对面反序列化 →
**重新加载一次索引**（或者自己再维护一份缓存）→ 序列化结果 → 读回来 → 反序列化。

换来什么？**什么都没有。** 调用方和被调方是同一个人写的、同一个进程、同一次部署。

### 2.3 而且会弄丢三件现成的东西

| 现在能做 | 走 MCP 之后 |
|---|---|
| `_invoke` 三条非正常路径**都说给模型听**（表外工具 / 同参重复 / 工具炸了），对话不中断 | MCP 的错误是协议级的 `isError`，要在客户端侧再翻译回"人话 + 可用清单" |
| 工具结果里夹带**给模型的纪律**（"这不是全文，只准 `append_body`"、"别再调工具了"） | 能塞，但得自己在 content 里拼——等于把现在这套原样搬过去，白搭一层协议 |
| `_tool_propose` 内部 `yield` 出 `card` 事件，前端当场渲染 diff | MCP 的返回是一次性的结构化结果，**推不了中途事件**（见《[Agent框架](Agent框架.md)》§5 同款问题） |

**这一跳的成本是确定的，收益是零。** 对着判据看：它不冲约束 1、2、4，但冲**约束 3**——
上界由代码封顶意味着每一层都得挣到自己的位置，挣不到就不该在那儿。

---

## 3. 作 server：该做，还没做

### 3.1 现在这套其实已经是一个手搓的 MCP

这是写这一篇时才对上的一件事。看 `knowrary-import` skill 实际在干什么：

```bash
# 读：拿上下文（可用关系类型 / 可链 id 子集 / 相关节点，封顶 200 个）
python3 /Users/moka/.../knowrary.py context --vault <vault> --article <文章> --field <领域>

# 预览：方案 JSON → 变更集 → 每个文件的 diff
python3 /Users/moka/.../knowrary.py apply plan.json --vault <vault> --field <f> --dry-run

# 写：去掉 --dry-run，落盘前自动备份
python3 /Users/moka/.../knowrary.py apply plan.json --vault <vault> --field <f>
```

**一个读工具、一个预览工具、一个写工具，外加一份讲清楚怎么用的说明书。**
这就是 MCP server 的全部形状。两条子命令的 help 里甚至直接写着"**供 skill 使用**"——
它们从来就不是给人敲的。

差别只在**协议是什么**：

| | 现在 | MCP |
|---|---|---|
| 工具怎么被发现 | SKILL.md 里写死 `python3 /Users/moka/IdeaProjects/Knowrary/tools/knowrary/knowrary.py` | `tools/list` |
| 参数长什么样 | 散文描述 + `--flag`，模型照着拼命令行 | JSON Schema |
| 结果怎么回来 | stdout 文本，模型自己读 | 结构化 content |
| 换台机器 | **改 SKILL.md 里四处绝对路径** | 改一行配置 |
| 换个客户端 | **重写一份 skill** | 不用改 |

**最后两行是全部理由。** 现在这套的隐含前提是"用的人是我、机器是这台、客户端是 Claude Code"——
三条全成立时它一点毛病没有，**任何一条不成立就得重写**。

### 3.2 §9 已经点过名

> 真要给别的 agent 客户端用，该做的是把 CLI 暴露成 MCP，
> 而不是让完整能力只长在某一个客户端里。
> ——《Agent架构与选型》§9，"借通用 agent 客户端跑导入"那一行

这句话是 2026-09-20 收回导入能力时说的。当天做的事是**把导入的完整能力从 skill 里搬回
CLI 和网页**（三个入口共用一条流水线，skill 降级成可选的第三个入口）。

**搬回来之后，"暴露给别人"才重新成为一个干净的问题**——
因为现在有一条不依赖任何客户端的流水线摆在那儿了，MCP 只是给它加一个协议门面。
反过来如果能力还长在 skill 里，做 MCP 就是把一团乱麻换个接口再暴露一次。

### 3.3 暴露哪些

不是把 11 个教练工具原样搬出去。按"**输入集合能不能提前算出来**"这条老判据分：

| 暴露 | 为什么 |
|---|---|
| `context`（读：类型表 / 可链 id / 相关节点） | 已经是为外部调用设计的，封顶 200 个 id，天生适合当 MCP tool |
| `apply --dry-run`（预览：变更集 + 每文件 diff） | 只读，不落盘，diff 和 `/api/changes` 的 dry_run 同源 |
| `apply`（写） | 走 writer 现成的四层闸 + 自动备份 |
| `search_nodes` / `read_node` / `outline` | 只读，别的客户端最想要的就是这三个 |
| `overview` / `digest` | 只读 |

**不暴露**：`propose_*` 四个。它们的产物是卡片，而卡片要前端渲染、要人点那一下——
这是下一节的事。

## 4. 作 server 的真冲突点：卡片那层护栏过不去

硬闸和软闸要分开看。

**硬闸全在服务端，MCP 一个字都动不了**：乐观锁（`base_revision` 对不上 409）、
文件指纹（md 被外部改过就拒绝覆盖）、字段白名单（`id` 和画布坐标永远改不了）、
路径白名单（只能落 `nodes/` 和 `fields/`）、落盘前自动备份。
**这一层是安全的**——它长在写回通道上，不管请求从哪来。

**软闸过不去**：

| 现在 | 到了别的客户端 |
|---|---|
| 变更卡带每个文件的 diff，红绿上色，人点「写入」 | 变成一段文本 diff + 客户端自己的 approve 按钮 |
| 一轮可以同时摆三张卡，互不相关的事分开提 | 一次工具调用一个结果，"分开提"这个纪律没有载体 |
| 卡片流水记「提出 / 采纳」，能算采纳率 | 别人客户端点的，记不到 |
| 口径白名单（教练 / 面试 / 聊天各一套工具） | **MCP server 不知道 stance** |

最后一行是真问题，值得单独记：

> **约束 2 说"能力边界写在服务端"，而 MCP 的授权模型是"客户端决定调哪个工具"。**
> 这两条不冲突（服务端仍可拒绝），但**"面试口径不给入库工具"这种口径级的边界，
> 在 MCP 那一侧没有对应物**——除非把 stance 做成连接参数，每档起一个 server。
>
> 这也是为什么 §3.3 的结论在这里仍然成立：**口径差异用提示词解决，不用架构解决。**
> 真要暴露，暴露的应该是**没有口径的那一半**（读 + 导入），
> 教练那套带口径的工具留在自己进程里。

## 5. 触发线

**出现第二个客户端。** 具体讲，满足任一条：

1. 想在 Claude Code 之外的 agent 客户端里用（Cursor、别人的 CLI、自己写的脚本）；
2. 换了台机器，发现 SKILL.md 里四处绝对路径都要改；
3. **别人真的来用这个仓库**——这是开源那条线上迟早要撞的，
   因为 skill 里写死的是 `/Users/moka/IdeaProjects/Knowrary`。

第 3 条最可能先到。2026-09-20 那天两件事（原生 tool use、导入入口拉平）都是冲着
"开源之后别人怎么用"去的，**MCP 是同一条线上还没做的那一段**。

---

## 6. 代价

先记着，真做的时候回来对：

- **多一份协议要测。** 现在 CLI 那两条子命令的行为由服务端用例覆盖，
  加一层 MCP 就多一层"协议翻译对不对"要验——和 `llm_backend` 里两套工具协议同款的账。
- **版本兼容。** CLI 的 `--flag` 改了只影响自己的 skill；MCP tool 的 schema 改了影响所有客户端。
- **`--vault` 这个参数不知道该怎么办。** 现在每次调用都显式传路径（skill 里写死的那个），
  MCP server 一般在启动时定死工作目录。这是好事（少一个能被搞错的参数），
  但意味着"一个 server 服务一个 vault"，多 vault 要起多个。
- **软闸那一半要接受"到不了"**（§4）。能做的是让 dry-run 的 diff 尽量自解释，
  因为到了别人的客户端，那段文本就是全部的界面。

## 7. 顺带记一条：这一篇为什么值得先写

它是这个系列里**唯一一篇结论是"该做"的**。

前面六篇都在回答"为什么没上"，容易读成一种偏好。
但同一把尺子量到 MCP 作 server 这一格时，量出来的是"冲 0 条硬约束、
而且解决一个真实存在的耦合（能力绑在一个客户端上）"——**所以判据说做。**

**判据能说"不做"也能说"做"，它才是判据。**
