# Knowrary：多语言设计（界面语言切换）

> 状态：**设计定稿，未开发**（2026-09-22）。
> 范围已按讨论收窄：**只做界面语言**。模型产出（教练回话、出题、判分、导入写的笔记正文）
> 这一轮不动，仍然是中文——见 §2 的四层划分与 §8「这一轮不做什么」。
> 上游：`web/src/**`（界面文案）、`server/*.py`（错误文案）、`tools/knowrary/relation-types.v2.json`
> 与 `core/projects.py:LEVELS`（数据枚举的显示名）。

## Context

现在整个界面是中文硬编码。要支持用户切换语言，第一反应是"把中文抠出来做 i18n"，
但这个项目里的"中文"**不是一坨**：有一部分中文是**磁盘上文件的字节**——
vault 里躺的是 `- 依赖:: [[Transformer]]`，`## 速查` 是 parser 认的锚点。
这些跟着界面语言变，等于每换一次语言就换一套文件格式。

所以这份设计的第一件事不是选 i18n 框架，是**先把四层分开、把不能动的那层钉死**。

现状体量（2026-09-22 实测）：

| 位置 | 含中文行 | 去掉纯注释行 |
| --- | --- | --- |
| `web/src/**`（60 个 vue/js） | 3197 | 1734（模板区约 349 处） |
| `server/*.py` | —— | 1400+（`chat.py` 525、`contracts.py` 260、`app.py` 139 居前） |
| `tools/knowrary/prompts/*.md` | 14 个文件 790 行 | 全是 prompt |

这三个数字里，**真正要搬进 i18n 表的只有第一行的一部分**。下面逐层说清楚为什么。

---

## 1. 核心判断：key 与 label 必须分家

推理链：

1. Markdown 是唯一真值源——这是整个项目最硬的纪律。
2. 关系类型名会被**写进 md 正文**（`- 依赖:: [[X]]`），family 会被**当成对象 key 索引样式**
   （`canvas/shapes.js:103` 那张 `{ 结构: {...}, 依赖: {...} }` 表），
   档位名会被**存进 projects.json 并参与校验**（`core/projects.py:311`）。
3. 所以这些中文串**不是文案，是标识符**。翻译它们 = 老库解析全废、跨库抄知识点断掉、
   别人的参考库读不进来。

**结论：这类串永远保持中文 key 不变，只额外挂一张显示名表。**
界面显示 `depends on`，写回 md 的仍然是 `依赖::`。

这条一旦破了，后面每一步都会歪，所以它是第 0 步。

---

## 2. 四层划分：哪层翻、哪层碰不得

| 层 | 内容 | 举例 | 处理 |
| --- | --- | --- | --- |
| **L1 数据标识符** | 关系类型（~28 个）、family（5 个）、固定章节名、档位名 | `依赖`、`结构`、`## 速查`、`会用` | **不翻**。key 不动，加 `labels` 显示名表 |
| **L2 界面文案** | 60 个组件里人眼能读到的串 | 按钮、标题、占位符、提示 | 搬进 vue-i18n |
| **L3 服务端人话** | 错误提示、变更卡摘要 | `速查里没有 X 这一行，删不掉` | 改成 `{code, params}`，人话交给前端 |
| **L4 模型产出** | prompt 模板 + 模型写出来的内容 | `prompts/*.md`、教练回话、题目、笔记正文 | **这一轮不做**（§8） |

还有**第五类容易被误伤的东西**，不属于以上任何一层：

**启发式匹配规则。** `canvas/shapes.js:78-84` 那组图标正则——
`[/CPU|寄存器|内存|总线|缓存/, '🔧']`——匹配的是**节点名**，而节点名是用户用中文写的。
把这些正则翻成英文，中文库的图标会全部消失。它们跟界面语言无关，跟**库内容的语言**有关，
一个字都不要动。

---

## 3. L1：显示名表怎么加

### 3.1 关系类型与 family

`tools/knowrary/relation-types.v2.json` 里每个类型挂一张 `labels`：

```json
"依赖": { "family": "依赖", "inverse": "支撑", "labels": { "en": "depends on" } }
```

`families` 从字符串数组扩成带显示名的形态（或在同文件加一张 `family_labels`）。
没有 `labels.en` 就回落到 key 本身（显示中文），**不阻塞、不报错**——
显示名表允许不全，这和 L2 的文案表不一样（那边缺 key 是 bug）。

### 3.2 档位名

`core/projects.py:304` 的 `LEVELS = ("了解", "会用", "精通")` 是数据，不动。
显示名现在散在 `server/levels.py` 的 `LEVEL_PROMPTS[x]["label"]`（`levels.py:85` 取它）——
那个 label 是**中文显示名**，扩成 `labels: {zh, en}`，取值时按请求语言挑。

### 3.3 前端必须有两个函数，不能合并

```
t('chat.send')        // 界面文案，查 i18n 表
label('relation','依赖') // 数据显示名，查 L1 表，查不到回落 key
```

**合并了迟早出事**：只要有一处把 `t()` 的返回值写回服务端，那一刻 vault 就脏了。
两个名字分开，code review 时一眼能看出越界。

## 4. L2：界面文案

### 4.1 选型：vue-i18n

已确认用 `vue-i18n`，不自撸。理由是工具链能扫漏、插值和回落是现成的；
代价是多一个依赖、`web/dist` 体积 +~20KB，可接受。

### 4.2 语言存哪

存 `localStorage['knowrary-lang']`，**和主题同级**。

理由沿用 `core/settings.py` 开头那条既定分界：「这台机器上怎么看图」留浏览器，
「后端也要读的开关」才进 `~/.knowrary/settings.json`。界面语言纯属前者——
后端这一轮不需要知道界面是什么语言（L3 出的是 code，不是人话）。

首次进入跟 `navigator.language`，认不出回落 `zh-CN`。
`web/index.html` 的 `lang="zh-CN"` 是写死的，切换时要跟着改 `document.documentElement.lang`。

开关放 `SettingsDialog.vue`（位置现成）。

### 4.3 key 命名

按组件/模块分命名空间的英文 key：`chat.send`、`projects.empty`、`quiz.judging`。

**不要拿中文原文当 key。** 看着省事，但有两个硬伤：英文 locale 缺项时回落会直接漏出中文
（漏了也发现不了）；改一个错别字要同步动所有 locale 文件。

### 4.4 搬运顺序（按"人看得见"排，不按行数）

1. **外壳**：`App.vue`、`AppHeader`、`ActivityBar`、`StatusBar`、`ZoomBar`、`CanvasTools`
2. **对话与学习**：`ChatView`、`useChat`、`StudyPanel`、`QuizDialog`、`DigestPanel`
3. **面板**：`Projects` / `Import` / `Timeline` / `Stats` / `Calendar` / `Compare` / `InboxTray`
4. **对话框**：`Node` / `Relation` / `Rename` / `Merge` / `Copy` / `Year` / `CompareFill` / `Usage` / `Help` / `Settings`
5. **画布 `canvas/*.js`（最后做，最危险）**

第 5 批单独说：`render.js`、`shapes.js`、`timeline.js`、`menus.js`、`lineage.js` 里，
画在图上的串和参与判断的数据串是**混在一起**的。典型的两个不能碰的例子：

- `render.js:69`：`const gold = e.type === '被激活'` —— 拿类型名做相等判断
- `shapes.js:103`：`结构: { stroke: ... }` —— family 当样式表的 key

这批必须逐条甄别，不能批量替换。建议这批开工前先把 §3 的 `label()` 铺好，
改的时候同时完成"显示走 label()、判断走原 key"的拆分。

## 5. L3：服务端错误 code 化

### 5.1 现状

`web/src/api.js:3-11` 的 `request()` 是唯一出口（另有 272 行一处同样形状）：
`res.ok` 为假就把 body 原样塞进 `err.body` 抛出。服务端现在往里放的是中文句子。

### 5.2 做法

- 新建 `server/errors.py`：`ApiError(code, params)` + FastAPI 统一 exception handler，
  出 `{ error: { code, params } }`
- core 层的 `ChangeRejected`（`core/writer.py` 那类）一并带上 code
- `api.js` 统一解包，前端 `t('err.' + code, params)`

### 5.3 边界：只搬"人会在屏幕上读到"的

服务端的中文有一大半**不是给人看的**：

- `chat.py` 那 525 行，绝大部分是系统提示词和给模型看的工具返回
  （例如 `read_node` 截断时那句"只准用 append_body"）
- `contracts.py` 那 260 行几乎全是 docstring 和字段注释

这些属于 L4 / 注释，**这一轮一个字不动**。判据很简单：
**这句话最终是渲染在页面上给人读，还是塞进 prompt 给模型读？** 前者才搬。

## 6. 会踩的坑

1. **`web/dist` 是入库的。** 改完不 rebuild，打开还是旧界面——2026-09-22 刚踩过一次
   （读源码推理，漏了 dist 与 src 不同步）。每批搬完都要构建 + 浏览器实点。
2. **英文比中文长 1.5–2 倍。** 画布节点卡片（`GROUP_MIN_W = 200`、卡片宽 160）、
   活动栏、定宽按钮会炸版。搬的时候顺手量紧的地方，别等英文包做完才发现布局要重排。
3. **日期格式风险低但要核。** 时间轴、历史视图用的是**纯年份数字**，不是 `2026年9月`，
   基本不受影响；要核的是 `CalendarPanel`（按周铺、周一在上）和 `MorningBrief` 里的日期串，
   这些走 `Intl.DateTimeFormat`，不要字符串拼。
4. **防回潮。** 收尾加一个 grep 脚本盯 `.vue` 模板区的中文并接进 `web/tests`，
   否则后面新写的组件又会硬编码回去。

## 8. 这一轮不做什么

### 8.1 不做 L4（模型产出语言）

**已确认的选择，连带后果要认**：切成英文后，界面是英文，但教练用中文回话、出的题是中文、
导入写进节点的正文也是中文。对一个纯英文用户来说，这是**半个产品**。

接受它的理由是这一轮只想先把界面骨架立起来。**架构上不挡后路**：
第 0 步那张显示名表就是以后接 L4 的地基——真要做 L4 时，
最省的路子是在系统提示词末尾统一注入一句 `Respond in {{lang}}`（覆盖八成场景），
只有 `quiz.md` / `quiz-review.md` 这种判分口径严的才值得单独出英文模板；
那时候内容语言要存进 `~/.knowrary/settings.json`（后端拼 prompt 要读），
**和界面语言分成两个独立开关**——"界面英文、笔记中文"是真实需求，不能合并成一个。

### 8.2 永不自动翻译 vault 已有内容

切语言**不翻译**任何已经写下的笔记。

**库的内容语言是库的属性，界面语言是人的属性，这两件事独立。**
半年前用中文写的笔记，换个界面语言就该还是中文——它是你写的东西，不是界面的一部分。

### 8.3 不翻译启发式规则

§2 末尾那条：`shapes.js` 的图标匹配正则匹配的是中文节点名，翻了中文库图标全丢。

### 8.4 不做服务端语言协商

这一轮服务端不需要知道界面是什么语言（出的是 code 不是人话），
所以**不引入 `Accept-Language` 处理**。等 L4 上马、后端真要按语言拼 prompt 时再说。
