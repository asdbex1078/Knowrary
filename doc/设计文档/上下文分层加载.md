# Knowrary：上下文分层加载（模型什么时候看什么）

> 状态：**已实现（2026-09-18）**。代码：`server/chat.py`（`_tool_search` / `_read_one` / `_read_outline` / `_read_section`）、
> `tools/knowrary/core/sections.py`、`tools/knowrary/core/article.py`（`select_linkable`）、`server/quiz.py`。
> 上游：第二版设计文档（一节点一 md、frontmatter + 正文 + `## 关系`）、项目化重构方案 §5（对话式教练）。

## 1. 问题

vault 是 md 文件，模型的上下文是有限的。节点越多、正文越长，有两条路会把 prompt 撑爆：
一是把全图元数据一次性喂进去（随节点数线性长），二是把整篇正文喂进去（随笔记长度线性长）。
Prompt-Caching 一篇 1.8 万字，整篇读一次就吃掉一轮预算的大半。

原则一句话：**模型不直接碰文件。它只能通过工具拿到分层的片段，每层拿什么、拿多少由代码封顶，拿哪个由模型决定。**

## 2. 一个 md 文件的三段，各干什么

```
---            ┐
name / desc    │ ① 元数据（frontmatter）：索引层。建索引时解析进 index.json，对话时不读文件。
field / tags   │    作用：让模型「知道有这个点」并判断相关，几十字一个点。
year / layer   ┘
# 标题
## 描述        ┐
## 为什么需要它 │ ② 正文：笔记层。只有模型点名读某个节点时才打开文件。
## 怎么运作    │    作用：给模型引用、补充、出题、批改用的事实。不许精简。
## 我的理解    │
## 线头        ┘   （线头同时抄进 tags，是正文和元数据之间的桥）
## 关系        ┐ ③ 尾部：图层。`## 关系` 建索引时抽成边；`## 参考资料` / `## 待办` 写回时原样保留。
## 参考资料    │    作用：关系决定图的形状和「相关节点」的一跳邻居；参考资料、待办只对人有用，
## 待办        ┘    模型整篇读时才看到，其他任何路径都不带。
```

## 3. 四层加载，一层比一层贵

| 层 | 工具 / 路径 | 模型拿到什么 | 上限 | 什么时候用 |
|---|---|---|---|---|
| L0 概况 | `overview` | 节点数、领域分布、项目一行摘要 | 零正文 | 开场、建项目前 |
| L1 元数据 | `search_nodes`、导入 prompt 的相关节点 | 命中行的 id / name / desc / field，长笔记加一行字数提示 | 默认 8 条、最多 20 条；导入侧相关节点 60 个、可链 id 200 个 | 判断「图里有没有」「该链谁」 |
| L2 目录 | `read_node` + `outline: true` | desc、正文字数、全部小标题、关系 | 几百字 | 长笔记动手前先看结构 |
| L3 正文 | `read_node`（可带 `section`） | 全文，或某一节及其子节，附关系 | 单节点 8000 字、一次 5 个共 16000 字 | 要引用、补充、重写时 |

出题和批改走单独的窄口径：出题每节点正文摘录 1200 字，批改补标准答案每节点 700 字。它们只需要「够出题 / 够对答案」，不需要全文。

## 4. 什么时候加载什么

**只要元数据（L1）**：回答「我图里有没有 X」、决定链到哪个 id、给导入方案挑相关节点。这一层永远不读正文，节点再多也只按命中数付费。

**加载全文（L3 不带 section）**：节点不超过 8000 字（现在 89 篇里 88 篇如此），且模型要引用它或要 `update_body` 整篇重写。整篇重写的前提就是「读到过全文」，这是唯一必须全文的场景。

**只加载标题（L2）**：搜索结果标了「长笔记」，或模型只想知道一篇笔记的结构。花几百字换整篇的地图，目录从整个文件算，8000 字之后的标题也在。

**混合（L2 → L3 带 section）**：长笔记要补某一节、或回答的问题只落在某一节。先看目录挑标题，再只读那一节。Prompt-Caching 一篇：整篇读 8000 字只看到前半，目录 772 字加第七节 1069 字就拿到了要的东西。

**兜底**：模型没看目录直接整篇读了一篇长笔记，代码截断后把目录附在结果里，并告诉它下一步带 `section` 来读。不会白跑一轮。

## 5. 按标题取节是怎么切的

模型说的是**标题**，不是段号。段号在正文改一句之后就全错，标题对人和模型都稳定。

1. 代码从整个文件现算目录：`##` 到 `######` 都算，跳过 fenced code 里的 `#` 注释行。不需要手写目录。
2. 匹配时去掉空白和标点比对，先找完全一致的，再找包含的。「案例1」能对上「案例 1【claude-cli 路】…」，「案例 2」不会被「案例 1」抢走。
3. 从命中标题所在行切到下一个同级或更高级标题之前。子节一起带上，后面的同级不带。
4. 标题写错不报错，把目录还给模型让它重选。
5. 一篇通篇没有 `##` 的笔记没有目录，只能整篇读。导入和教练写正文都要求分节，就是为这条留的路。

## 6. 准确度靠什么保证

**写回分两条路，读了多少决定能走哪条。** `append_body` 只往正文尾部接一段，不需要持有全文，所以截断、只看目录、只读一节都允许。`update_body` 整篇替换，只有不带 section 且没被截断地读到全文才允许。每一次部分读取的结果里都明写「不是全文，只准 append_body」，写回时正文缩水超过四成还会在卡片上喊出来。这条纪律是从事故里长出来的：早先正文截到 1200 字，模型整篇写回，后半篇就没了。

**不编造。** 说「你图里有 X」之前必须 `search_nodes` 或 `read_node` 确认过，这是提示词的硬规矩。L1 便宜到可以随手查，所以不给「凭印象」留借口。

**链接只认列出来的 id。** 导入 prompt 里的可链 id 是筛过的子集（相关节点、它们的一跳邻居、目标领域的节点），并明说图里别的节点不在列表里。链到不存在的 id 会补成 stub 等人确认，不会悄悄接错。

**读过的内容留在历史里。** 工具结果和对话一样进历史，受 60 条、24000 字双闸。同一轮里读过就不用再读，聊久了被挤出去再读一次即可。

## 7. 省下来的账

| 场景 | 改前 | 改后 |
|---|---|---|
| 导入 prompt 的 id 栏 | 全部 id，随节点数线性长 | 相关 + 邻居 + 同领域，封顶 200；89 个节点时列 20 个 |
| 读 1.8 万字笔记的某一节 | 8000 字且只看到前半 | 目录 772 字 + 一节约 1000 字 |
| 出题 / 批改 | 同上限 | 1200 / 700 字摘录，从来不整篇 |

元数据层随图谱增长的只剩 `search_nodes` 的命中数，有上限；正文层随笔记长度增长的只剩 L3 全文，有上限且有目录兜底。**图谱再大、笔记再长，单轮 prompt 的上界不变。**

## 8. 没做的和以后可能做的

- 可链 id 子集没有「按名字模糊匹配」这一路。如果导入时 stub 误报变多，加这一路或调大 200 的上限。
- 目录只到三级、最多 40 行。更深的层级和更长的目录暂时截掉，目前没有一篇触到。
- 出题、批改的摘录取的是正文开头。长笔记的重点如果在后面，将来可以改成按目录挑节。
