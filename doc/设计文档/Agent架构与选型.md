# Knowrary：Agent 架构与选型

> 状态：**已实现**，对齐到 2026-09-20 的代码。
> 主要代码：`server/chat.py`（agent 循环）、`server/turns.py`（对话续接缓存）、
> `tools/knowrary/llm_backend.py`（后端 + 原生工具协议翻译 + 缓存布局）、`server/llm_call.py`（角色路由 + 记账）、
> `tools/knowrary/core/llmjson.py`（JSON 容错）、`tools/knowrary/core/proposal.py`（导入三级匹配）、
> `tools/knowrary/prompts/`（提示词）、`server/levels.py`（档位口径）、`tools/knowrary/core/writer.py`（唯一写盘入口）。
> 上游：第二版设计文档、项目化重构方案 §5、`上下文分层加载.md`。

这篇回答一件事：**这个知识库本身就是个 agent 产品，它的 agent 是怎么搭的、为什么这么选。**
不讲图谱的产品逻辑（那在另外两份设计文档里），只讲模型、工具、上下文、护栏和账单。

**正文写的是现在的样子。** 中间走过的弯路不单独成章，而是贴在它改变了的那条决策下面——
一条规矩为什么长这样，往往只有那次事故解释得清。最后一节（§11）是回头对着真实使用记录
做的复盘，只留还欠着的和方法上的教训。

## 0. 一句话结论

**一个自研的 agent 循环（约 1500 行 Python，零 agent 框架，原生 tool use），加一圈长在服务端的护栏，
加一批故意不做成 agent 的单次调用。** 模型能做的只有"提议"，落盘永远是人按的那一下。

四条贯穿始终的主线：

1. **能力边界写在服务端，不写在提示词里。** 提示词会被绕过，工具白名单不会。
2. **口径的差异用提示词解决，不用架构解决。** 三档人格 = 三份提示词 + 三份白名单，不是三个 agent。
3. **上下文的上界由代码封顶，拿哪一块由模型决定。** 图谱再大、笔记再长，单轮 prompt 的上界不变。
4. **消息列表只增不改。** 三种后端的省钱手段（claude-cli 续会话、anthropic 缓存断点、
   openai 自动前缀缓存）要的都是同一件事：前面那一截一个字都别动。

第 4 条是最晚才想明白的，也是代价最大的一条——见 §3.8 和 §3.10。

> **2026-09-20 改了两件事，都是冲着"开源之后别人怎么用"去的**（§3.1、§1）：
> 工具协议加了原生 tool use 那一套，按 provider 能力自动挑（claude-cli 仍走围栏，
> 零配置那条路没断）；命令行导入补齐到和网页同级，三个入口里只有 Claude Code skill 是可选的。

## 1. 这个项目里其实有三种 agent，只有一种是自己写的

| | 是什么 | 谁在跑循环 | 干什么 | 代码 |
|---|---|---|---|---|
| **A. 对话式教练** | 自研 agent 循环 | `server/chat.py` 的 `_run` | 聊着学、搜图、读节点、出题、提议入库、提议改清单 | 自己写的 1471 行 |
| **B. 导入** | **不是 agent**，是固定流水线 | 没有循环 | 把一篇文章拆成节点、dry-run、写盘、校验 | `core.proposal` + `server/importing.py` + `knowrary.py article`（skill 是可选的第三个入口） |
| **C. 单次调用** | **不是 agent** | 没有循环 | 出题、批改、拆计划、连边建议、概括、补年份 | `quiz.py` / `projects.py` / `suggest.py` / `summarize.py` / `years.py` |

**B 曾经是个刻意的偷懒：借 Claude Code 当通用 agent 跑导入。** 2026-09-20 把它收了回来——
理由不是那样跑得不好，而是**"换个模型怎么办、开源之后别人怎么用"**：借来的 agent 意味着
导入的完整能力绑在一个特定客户端上。

收回来之后按 C 的判据重新审了一遍：导入的**输入集合能提前算出来**（上下文由 `context` 算好、
文章是给定的、输出是一份 JSON），所以它根本不该是 agent，是条固定流水线：

```
context（算可链 id / 相关节点） → 一次 LLM 调用出方案 JSON → 三级匹配（认领 / 撞脸 / 孤立）
  → translate → plan → diff → 人看过 → commit → check
```

**三个入口共用这一条**：命令行 `knowrary.py article`、网页「导入」面板
（`/api/import/propose` → 审核卡 → `/api/import`）、Claude Code skill。
同一份提示词（`prompts/article.md`）、同一个长度闸、同一套三级匹配（`core.proposal`）、
同一份 JSON 容错（`core.llmjson`）、同一条写回通道。**前两个不依赖 Claude Code，
也不依赖任何一家模型**——配一个 DeepSeek / 通义 / Ollama 就能全功能跑；
skill 是第三个可选入口，给"人已经在 Claude Code 里了"那种时候。

> 之前命令行那条比网页矮一头（没有项目认领、不提醒撞名、不报孤立、不留 JSON 解析失败的痕），
> 因为这三级只长在服务层。**入口不同不该改变结论**，所以判定整体下沉到了 `core.proposal`。

**C 不做成 agent 是主动的选择，不是没来得及做。** "出三道题"这种活儿，输入是确定的
（节点正文摘录 + 关系 + 档位口径），输出是确定的（一份 JSON），没有任何需要模型自己探索的余地。
给它一个循环只会多出几次工具往返和一堆"我先看看"的废话。判据很简单：
**任务的输入集合能不能提前算出来**——能，就是单次调用；不能（"聊着聊着看要不要读这个节点"），才需要循环。

> 一个有意思的旁证：这个 vault 的 Claude Code 会话目录里堆了 **505 个 session**，
> 其中真人开发会话只有 **32 个**，剩下 473 个全是应用自己发起的 `claude -p` 调用
> （394 次单次调用类、62 段教练对话、10 次出题批改、7 次拆计划）。
> 默认 provider 走本机 Claude Code 登录，于是应用的每一次模型调用都在这里留了一份完整的档。

## 2. 教练 agent：一条消息的完整回合

### 2.1 循环本身

```
用户一句话
   ↓
_fit_history（60 条 / 24000 字双闸，从最早的开始丢）
   ↓
_assemble：能续就续，续不上才重建
   ├─ turns.resume 命中 →  上一轮的完整内部列表（含工具往返） + [这句新话]
   └─ 没命中         →  [顶层 system(静态)] + [截断提醒?] + 前端回传的可见轮次
   ↓
   图谱快照：**变了才追加一条队尾 system**，没变就不贴（贴一条就动一次前缀）
   ↓
┌── for step in range(MAX_STEPS=8) ──────────────────────────┐
│  流式问模型 → 边出边 yield delta 给 SSE                     │
│  _parse_tool()：正文里有没有 ```knowrary {...}``` 块？      │
│     没有 → 这段就是答案，break                              │
│     有   → 白名单校验 → seen_calls 去重 → 执行 → yield 事件  │
│           messages += [assistant 原文, "[工具 X 的结果]…"]  │
└────────────────────────────────────────────────────────────┘
   ↓
pull_checks()：摘出 ```check 围栏 → 进题库
_mentioned()：这一轮提到哪些节点 → 图上高亮 + 留档标注
turns.remember()：把这一轮结束时的完整列表存下来，下一轮好接着发
append_log()：一行一轮写进 .knowrary/chat/<项目>/YYYY-MM.jsonl
```

**"不再调工具"就是终止条件。** 没有 finish 工具、没有 final answer 标记。
配套的一条是：**中途那些"我先查一下"的话不进正文**（它们进 `trace`，界面上折叠成过程条）。
早先把过程和答案拼在一起，真实使用里最费时间的事变成了"在一堆过程里找那几句有营养的"。

**SSE 事件是有类型的**：`delta`（正文增量）、`tool`（调了什么）、`card`（变更卡）、
`project`（项目卡）、`points`（拆点卡）、`list_edit`（清单卡）、`review`（记了一次复习）、
`question`（进题库的检验题）、`done`（答案 + trace + usage + node_ids + 两条留档的 ts）。
前端按类型渲染，不靠解析文本——**唯一需要前后端各写一遍的正则是工具块的形状**，
所以两边特意用了同一个形状（`strip_tools` ↔ `stripToolBlocks`），
否则会出现"聊天记录里没有、屏幕上闪过一段 JSON"。

### 2.2 循环里的几个数字，每一个都有故事

| 常量 | 值 | 为什么是这个值 |
|---|---|---|
| `MAX_STEPS` | 8 | 原来是 4。"帮我建个项目"要走：看已有 → 搜图 → 读几个点 → 提议项目 → 拆点，4 步走不完，人被迫自己去面板接着干 |
| `MAX_MESSAGES` / `MAX_HISTORY_CHARS` | 60 / 24000 | 两道闸都要过。只看条数的话，20 条里夹几段长正文就能把 prompt 撑爆 |
| `READ_CHARS` | 8000 | **原来是 1200，那是个会吃笔记的数**：模型拿到截断过的原文，再 `update_body` 整段写回，后半截永久没了 |
| `READ_BUDGET` / `READ_MAX_IDS` | 16000 / 5 | 一次读多个节点省步数，但省步数不能换来把 prompt 撑爆 |
| `SEARCH_TOP` | 8 | 搜索只给元数据（id/name/desc/field），便宜到可以随手查 |
| `turns.MAX_KEYS` / `MAX_CHARS` | 8 段 / 20 万字 | 续接缓存的上限。超了就不缓存这一段：省钱不值得拿内存和磁盘去换 |

还有三个不是数字的机制：

- **`seen_calls`：同参调用只真跑一次。** 真实对话里观察到模型会用一模一样的参数再搜一遍，
  每重复一次就白烧一个完整来回。第二次直接把上次的结果还回去，并附一句
  "**直接用这个结果回答，不要再调工具了**"。这也是 `MAX_STEPS` 敢从 4 放宽到 8 的前提。
- **截断要说出来。** 历史被丢掉几轮时，插一条消息明确告诉模型"你缺了 N 轮，
  别猜，先 `search_nodes` / `read_node` 去图里找，找不到就问我"。
  模型不知道自己少了上下文时，会拿半截记忆当完整的用，比直接说"我没看到"糟得多。
  顺带一提，**真正的长期记忆本来就不该是上下文窗口**——聊清楚的东西应该已经进 md 了。
- **图谱快照只增不改。** 它是队尾那条会变的 system。以前每轮重贴一份、位置还随历史长度漂；
  现在内容没变就不贴，变了就在队尾**追加**一条新的，旧的原地不动（§3.10 讲为什么这很值钱）。

## 3. 十一个选型决策

每条的格式：**选了什么 → 备选是什么 → 为什么 → 代价**。

### 3.1 工具协议：两套实现，按 provider 能力自动挑

**对上只有一个契约**：`llm_backend.chat()` 收一份工具 schema，返回结构化的 `calls`。
底下两套实现，由 `supports_tools(provider)` 自动选：

| provider | 协议 | 怎么来的 |
|---|---|---|
| anthropic / openai | 原生 tool use / tool_calls | schema 进 payload，调用以结构化字段回来 |
| claude-cli | 文本围栏适配 | schema 渲染成一段提示词，回答里用正则捞 ```` ```knowrary ```` 块 |

内部消息形状是中立的，provider 差异只在翻译层
（`_to_anthropic` / `_to_openai` / `_render_transcript`）：

```
{"role": "assistant", "content": str, "tool_calls": [{"id", "name", "args"}]}
{"role": "tool", "tool_call_id": str, "name": str, "content": str}
```

**适配层放在 `llm_backend`，不放在 agent 循环里。** 这是这条决策里最要紧的一句：
`_run` 永远把 schema 传下来、永远拿结构化的 `calls` 回去，**一行 `if 围栏 else 原生` 都没有**。
协议差异全关在 `_chat_claude_cli` 一个函数内（渲染说明 → 跑 → 捞围栏 → 剥干净正文）。
放进循环里的话，每加一个工具、每改一次事件流，都要在两套协议下各想一遍。

**为什么原生是默认**：围栏把守协议的责任全压在模型的指令遵循上，**而且失败是静默的**——
`_parse_fence` 捞不到合法 JSON 就返回空，循环当它没调工具，那段话**直接被当成答案**吐给用户，
留档上看不出任何异常。Claude 守得住，换个小一点的模型未必，而你不会知道。
原生协议里参数写坏了仍然算"调过这个工具"：带空参数交给工具，工具的报错原样喂回去让它重写。

**为什么围栏没被删掉**：它是 claude-cli 唯一能走的路，而 claude-cli 是**零配置的默认 provider**
——复用本机 Claude Code 登录，不用填任何密钥。砍掉它等于"想聊天先去开个 API key"。
一度真的砍过（2026-09-20 当天），当天又加了回来：**能力该由配置决定，不该由一次架构选择替用户决定。**

**原生那侧多出来的两样**：schema 校验，以及**并行工具调用**——"搜一下再读三个节点"
从四个来回变成两个。围栏那侧仍然是一次一个（一个块、然后停下），这是它的固有限制，
写在 `_fence_spec` 的说明里。

**两侧共享的一份数据**：`TOOLS_SPEC` 同时渲染说明书、JSON Schema 和白名单（§3.4）。
围栏那段说明**只讲怎么调，不重复抄工具表**——表已经在 `prompts/chat.md` 里渲染过一份，
再抄一遍等于花钱买重复，还会和那份打架。

> `strip_tools`（服务端）/ `stripToolBlocks`（前端）这对正则**两条路都要留着**：
> 围栏那侧是协议的一部分，原生那侧是兜底——模型见过太多围栏写法，偶尔仍会手写一个出来，
> 它不会被执行，但也不该让人在屏幕上看见一段 JSON。

### 3.2 不用 agent 框架

会话记录里出现过一次原话："**是否需要用 langchain？**"（2026-09-15）。结论是不用。

**为什么**：这个 agent 需要的东西——循环、工具分发、上下文裁剪、流式——加起来是 `_run` 那一百多行。
而框架会带来它自己的抽象（Chain / Memory / Retriever），这些抽象和本项目的核心约束
（**只提议不写盘**、**工具白名单跟着口径走**、**缓存断点要手工摆在特定位置**、
**消息列表只增不改**）全都不对齐，最后一定是绕着框架写代码。

**代价**：没有开箱的追踪面板、没有现成的重试策略。这两样都自己补了一份更小的：
用量账本（`llm-usage.json`）+ 出错流水（`issues.jsonl`）。

> **六处代码级对照**（循环 / 工具白名单 / 缓存断点 / 消息只增不改 / 流式事件 / claude-cli 后端），
> 以及"什么时候 LangChain 是对的"，见《选型对照/[Agent框架](选型对照/Agent框架.md)》。
> 这个项目的其他选型（向量库、数据库、测试框架、LLM SDK、画布节点）同系列各有一篇，
> 判据与总表在《选型对照/[选型判据](选型对照/选型判据.md)》。

### 3.3 三档口径 ≠ 三个 agent

`STANCES` 就三行：

```python
"教练": {"file": "chat-coach",     "tools": 全部 11 个},
"面试": {"file": "chat-interview", "tools": 只读 3 个 + quiz + record_review},   # 不给入库
"聊天": {"file": "chat-talk",      "tools": 只读 3 个 + propose_changes},        # 不给调度
```

**面试口径不给入库和改清单的工具，因为边考边改图谱等于开卷**；聊天口径不给 `today`/`projects`，
因为不想每句话都被催进度。

**为什么不开三个 agent**：多开一套运行时要付会话路由、上下文传递、状态同步和翻倍 token 的代价，
而收益只是换一套系统提示词。同一条链路、同一张图、同一套复习记录，换的只是提示词和工具白名单。

**配套的一条纪律：换口径就新开一段对话。** 混在同一段里，前半截是面试后半截是闲聊，
模型会被自己的历史带跑。（口径也是续接缓存那把钥匙的一部分，见 §3.8。）

### 3.4 工具白名单 = 说明书 = JSON Schema（同一份数据）

`TOOLS_SPEC` 是唯一的那一份，三个用途全从它渲染：

```python
tools  = tools_of(stance, vault)     # 复习那一档关掉时这里已经少了 quiz / record_review
table  = "\n".join(f"| `{t}` | {TOOL_DOC[t]} |" for t in tools)   # 说明书（TOOL_DOC 由 spec 派生）
schema = tool_schemas(tools)                                      # 发给模型的工具定义
formats = "\n\n".join(FORMAT_DOC[t] for t in tools)               # "要写东西"那几个的格式说明
```

**schema 说得清形状，说不清纪律。** 类型、必填、参数含义交给 schema；
"什么时候该 `append_body` 什么时候该 `update_body`"、"互不相关的几件事要拆成几张卡"、
"正文要写到什么份上"——这些只能用散文写，所以 `FORMAT_DOC` 没有被 schema 取代。

**为什么**："表里写着能用、调了却说没有"是最让人发火的那种 bug。两边各写一遍迟早对不上。
所以说明书和实际权限是同一份数据；调了表外的工具，服务端回一句
"这一档口径下没有 `X` 这个工具，可用的是：…"，对话继续，不报错。

同一条原则也落在复习开关上（§3.6）：关掉那一档时，`<!--review-->` 包起来的提示词段落
**整段不渲染**，`quiz` / `record_review` 两个工具**真的被收走**——说明书里没有、schema 里也没有，
而不是留着工具再叮嘱一句"别用"。
手段还在手里、只靠一句话拦着，那是压制不是关闭。

> 关掉时只补**一句事实**，不补"不要做 X"——规矩已经不渲染、工具已经收走，
> 再写一串禁令就是在提醒它有这回事。留那一句是为了他真开口问"考我一下"时，
> 模型能答清楚现在是什么状态，而不是干巴巴甩一句"没有这个工具"。

### 3.5 Agent 只提议，不写盘

这是整个产品最硬的一条边界。模型能调的写类工具有四个，**全部只出卡片**：

| 工具 | 产物 | 落盘要走 |
|---|---|---|
| `propose_changes` | 变更卡（含每个文件的 diff） | 人点「写入」→ `POST /api/changes` |
| `propose_project` | 项目卡 | 人点「创建」→ `PUT /api/projects` |
| `propose_points` | 拆点卡 | 人点「采纳」 |
| `propose_list_edit` | 清单卡（改已有条目：换 id / 删 / 改字段） | 人点「应用」 |

**卡片的 diff 是真的**：`_tool_propose` 直接调 `curation.preview()`，
和 `/api/changes` 的 dry_run **是同一份代码**。所以卡片上看到的就是会写进去的。

写盘那一侧还有四层独立的闸，**全都在服务端，模型碰不到**：

1. **乐观锁**：`base_revision` 对不上当前索引 → 409。
2. **文件指纹**：md 在索引生成之后被外部改过（Obsidian 里手改了）→ 拒绝覆盖。
3. **字段白名单**：`EDITABLE_FIELDS` 14 个字段可改；`id` 和画布坐标 **永远改不了**，提了整批退回。
4. **路径白名单**：新节点只能落在 `nodes/` 和 `fields/` 两棵树下；正文上限 40000 字。

落盘前自动备份（`.knowrary/backup/`）。写回被拒会进 `issues.jsonl`——
**写回被拒往往说明工具本身有问题**（字段白名单漏一项这种），不是人手滑，攒起来才看得出规律。

> **`propose_list_edit` 是后补的，补的是一个"能加不能改"的缺口。** 真实使用里撞了两次墙：
> 同一个概念在两份清单里写成了两个 id（节点已建成 `MHA`，清单里还写着 `多头注意力`，
> 于是那条永远显示「未建」）；一条被拆成两条之后，旧的合并项还躺在清单里。
> 两次模型都只能说"那条得你自己去面板改"——**而它的提示词里明写着"不许把要不要做丢回来问我"**。
> 不是它不听话，是工具表里没有这条路。补一条仍然出卡、仍然人点的路径就够了。

### 3.6 复习：两个开关，以及只许降级

**判定只许降级。** 对话里看出我答错了，模型可以直接 `record_review` 记「忘了」；
看出我答对了**不准**记「记得」。理由是不对称的：判严了最多多复习一次，
判宽了会让一个其实已经忘了的点**从此再不出现**。同一族的还有一条：
**错题本压过自评**——测验里答漏了，就算自评点了「记得」，节点上的「考」也是红的。

**开关是两档，不是一档**（`.knowrary/settings.json`）：

```
review_enabled   总闸：复习这一整套在不在（「今日」分栏的到期与错题、日历、画布金点）
  └ review_in_chat  教练会不会考我 / 催我。总闸关了它一律当关
```

**为什么要拆**：这两件事原来是一个开关，于是"别在聊天里考我"只能靠关总闸达成——
而总闸一关，`curation.coach_today` 会在服务端把到期与错题从今日清单里摘掉，
**「今日」分栏跟着一起空**。那恰恰是专心复习的地方。
（摘在服务端而不是前端过滤是对的：今日清单同时是教练 `today` 工具的数据源，
只在前端挡住的话，界面安静了、教练一调工具照样看见一串欠账然后开口催。
错的不是"摘在哪一层"，是"一个开关管了两件事"。）

**两种关法要说两句不同的事实**，不能共用一句：整套关着是"功能不在"，
只关聊天那一档是"功能还在，只是不该由你来考"。说成同一句的话，
他问一句"我不是能在今日面板复习吗"，模型会跟着答"复习关着"，等于凭空多一次误导。

### 3.7 上下文：四层加载，代码封顶

细节见 `上下文分层加载.md`，这里只记结论和它在 agent 里的位置：

| 层 | 工具 | 拿到什么 | 上限 |
|---|---|---|---|
| L0 概况 | `overview` | 节点数、领域分布、项目一行摘要 | 零正文 |
| L1 元数据 | `search_nodes` | 命中行的 id/name/desc/field，长笔记加一行字数提示 | 默认 8 条 |
| L2 目录 | `read_node` + `outline` | desc、字数、全部小标题、关系 | 几百字 |
| L3 正文 | `read_node`（可带 `section`） | 全文或某一节 | 单点 8000 / 一次 16000 |

**读了多少决定能写什么**：`append_body` 只往尾部接一段，截断 / 只看目录 / 只读一节都允许；
`update_body` 整段替换，**只有不带 section 且没被截断地读到全文才允许**。
每一次部分读取的结果里都明写"不是全文，只准 append_body"。
这条纪律是从事故里长出来的：早先正文截到 1200 字，模型整篇写回，后半篇就没了。

另外 `search_nodes` 会**按词拆**再匹配（空格、顿号、逗号、斜杠、加号都算词边界）。
不拆词等于只认字面全串——问一句「符号主义 连接主义」必然零命中，
模型拿着这个假阴性下"图里没有"的结论，再跑去翻全量项目和今日清单核对，白烧两个来回。

> **这一节封的是"会不会炸"，不是"贵不贵"。** 单轮 prompt 有上界，跟图谱多大无关；
> 但账单的主要驱动不在这里，而在"开了多少次新前缀"（§3.10）。两件事别混。

### 3.8 会话状态：前端持可见轮次，服务端持一份可丢的缓存

对话的**真值**是留档：`.knowrary/chat/<项目>/YYYY-MM.jsonl`，一行一轮，按项目分目录、按月分文件。
**不建库、不切分、不做 embedding**——量级差两个数量级，找旧对话用 `rg` 是毫秒级的。
会话列表、标题、梳理游标全是从留档行**聚合**出来的贴纸，不是第二份真值。

前端每一轮把**可见轮次**发过来（`role` + `content`，assistant 那条只有正文、没有工具往返）。
服务端另外按 `project|session|stance` 存一份**完整内部消息列表**（含工具往返、含 assistant 原文），
在 `server/turns.py` 里：

```
turns.resume(key, 这一轮发来的可见轮次)
   ├ 存下来的可见投影 == 发来的前 n-1 条  →  返回完整列表，只把新的那句话追加上去
   └ 对不上（改过 / 删过 / 换了一段）     →  None，退回整段重建
```

**为什么需要这一份**：前端那份和服务端内部那份**构造性地对不上**——
只要上一轮调过工具，内部列表里就多了几条前端不会回传的消息。而三种后端的省钱手段
全都认逐字节前缀（§3.10），前缀一断就白白退回全量重发，**而且不报错**。
真实使用记录里，67 段教练会话有 54 段只有一次模型往返 —— 即几乎每轮都在重开新前缀。

**它是缓存，不是真值。** 随时可以删，丢了只是下一轮多花一次全量重发的钱。所以：
不做 schema 迁移、形状对不上就整份丢掉；**前缀对不上就重建，绝不猜**——
续错一段（模型看着别人的上下文答题）比多花那点钱糟得多。

**为什么不上数据库**：单段对话总文本中位 11 KB、最大 32 KB，留最近 8 段约 0.2 MB，
和 `index.json`（87 KB）同级。访问形状是单进程、一次只读一个 key、每轮整文件替换——
数据库在这里只能卖给我们并发锁和索引，两样都用不上。代码注释里钉了三条触发线，
**到了任意一条再说，别凭感觉升级**：① 多进程 / 多端同时写；② 需要跨对话检索
（现在这活是 `rg` 干的）；③ 它不再可丢。

**"梳理这段"只发游标之后那一段**：前面的已经采纳入库了，再喂一遍纯粹是重复付钱。
游标**只在变更卡真写进 md 之后才推进**——梳理是这个应用里最贵的一次动作
（MAX_STEPS 的工具循环），第二天打开同一段再点一次，没有游标就是把昨天那笔钱原样再付一遍。

### 3.9 Provider：三种类型 × 两个角色

```
providers: claude-cli（复用本机 Claude Code 登录，零配置）—— 工具走围栏（§3.1）
           anthropic （官方 API，走 SDK 或 REST）
           openai    （OpenAI 兼容协议：OpenAI / DeepSeek / 通义 / Ollama / vLLM 都是它）
roles:     learn  = 聊天、拆文章、拆计划、概括
           review = 校验、去重、出题、判分
```

**两个角色是故意的**：可以指向不同模型，用第二个模型审第一个的产出，减少单一模型的偏差。
密钥只在 `.knowrary/llm.local.json`（被 gitignore），
`knowrary check` 会在任何 `*.local.json` 被 git 跟踪时报错。

**三种都能对话，配置说了算**（§3.1）：`claude -p` 没有结构化工具接口，所以它那条路上
工具协议自动退回文本围栏；`supports_tools()` 判的是**协议能力**，不是模型强弱。
上层（`llm_call` / `server/chat.py`）看不见这个区别，契约是同一个。

**所有 LLM 调用都从 `llm_call.py` 过**，所以四件事各写一遍就够：

1. **记账**：成功和失败都记（失败照样烧了时间、也可能已经计费）。记账是旁路，记不上绝不能拖垮正经调用。
2. **报错带上下文**：`[learn 角色 · provider gpt · 模型 gpt-5-codex] HTTP 503`。
   原来只有一句"HTTP 503（某个 url）"，配了多个 provider 时第一件事就是猜"到底是谁炸了"。
3. **异常类型转换**：`llm_backend` 是先有 CLI 后有服务的，报错一路用 `SystemExit`——
   在命令行里那是对的，但 `SystemExit` 是 `BaseException`，**Starlette 的异常中间件只接 `Exception`**，
   于是它会一路穿过请求处理层：客户端拿到的不是"模型挂了"，而是连接莫名其妙断掉。
   在这一处换成 `LLMFailed` 就够，不必去每条路由上补 try。
4. **会话表落盘位置**：`vault` 在哪只有服务层知道，而 `llm_backend` 是 CLI 也在用的下层，
   不该反过来依赖服务层的目录约定，所以路径从这里注入进去。

JSON 容错也在这里：先剥围栏，再**按花括号配对扫一遍**抠出第一个完整对象（跳过字符串里的括号和转义）。
解析失败**必须留痕**——调用已经花了钱，界面上只剩一句"没出出题来"的话，下次遇到照样两眼一抹黑，
所以原文前 600 字进 `issues.jsonl`。

### 3.10 缓存布局：这是账单上最大的一笔

一个用户回合里常常夹着三四次工具往返，**那几次才是账单的大头**，而它们之间只差末尾几百个字。
所以缓存怎么摆，直接决定这个产品能不能用。

**布局（anthropic 后端）**：

```
顶层 system  ←── 静态那一万一千字（工具表 + 格式说明 + 关系类型表 + 教练侧写 + 档位口径）
              └─ 打一个 cache_control 断点

messages     ←── 历史 + 这一轮的工具往返
              └─ 在最后一条【非 system】消息上再打一个断点

队尾 system  ←── 图谱快照（节点数、边数、领域分布、已有项目）——会变的那 276 字
```

**为什么图谱快照要挂在队尾**：它原来写在 `prompts/chat.md` 中间。问题是这几个数字**会变**——
教练的整个用途就是聊着聊着把新点入库，一采纳变更卡节点数就变了。
而提示词缓存认的是**逐字节的前缀**：中间插一个会变的数字，等于图谱每动一次，
它后面那一万多字静态指令全部作废重买。

第一版把它拆成第二条顶层 system，断点打在两者之间。但**顶层 system 整体排在所有 messages 之前**，
静态那块保住了，图谱一动整段对话的缓存照样全丢。
所以现在它是 **mid-conversation system message**，坐在历史之后——变了只作废它自己那 276 字，
而且**没变就根本不贴**。

> 顺带一个安全性收益：user 消息里的「（系统提示）」谁都能伪造，`role: "system"` 不能，
> 它是不可冒充的操作指令通道。

**兼容性怎么处理**：`Sonnet 5 不支持 mid-conversation system message`（400），Opus 5 / 4.8 / Fable 5 支持。
与其维护一张"哪个模型行"的表（它一定会过期），不如**撞上 400 再退一步**：
把中途的 system 折成 `<system-reminder>` 并进前一条 user 重发一次。
退化的是安全性和缓存，对话本身照常。

**工具表也要打断点**：它和顶层 system 一样是逐字不变的一大块（十来个工具的 schema），
而且在 anthropic 的 prompt 里**排在 system 之前**——不标它，system 那个断点前面就永远躺着
一段没缓存的内容。断点打在最后一个工具上，覆盖到此为止的整张表。

**claude-cli 那一路是另一套招**：`claude -p` 每次都是新进程、没有服务端会话，
所以原来每一轮都把整段对话拍平重发。实测（haiku，约 40k token 上下文）：

```
重发全文   第二轮 $0.0673，cache_write 22242
--resume   第二轮 $0.0061，cache_write   423
```

**差在 cache_write：重发全文 = 每一轮都重新写一遍缓存，而缓存写比读贵得多。**
只在**能证明前缀没变**时才续（sha256 指纹校验），指纹对不上就老老实实开新的一段；
会话表落在 `.knowrary/cli-sessions.json`（`uvicorn --reload` 一天几十次，
只放进程内存等于每次重启全额重付；存的只是 uuid + 指纹 + 发到第几条，没有对话正文）。

> 指纹现在按**渲染后的转录**算，不是按 `role + content`：消息里可能带 `tool_calls`，
> 两条 assistant 正文一样、调的工具不一样，只看 content 会算出同一个指纹——
> 于是"续"上一段其实不同的上下文。渲染后的文本里有围栏块，两者自然分得开。

**这三条路要的是同一件事，所以有了那条总纲：消息列表只增不改。** 具体落成三条规矩：

1. **续接优先**（§3.8）：上一轮的完整列表原样留着，新的一句追加在后面。
2. **图谱快照追加，不替换**：变了就在队尾添一条新的，旧的原地不动。
3. **没有"重排"这个动作**。早先有个 `_hoist_system`，把中途的 system 搬回开头，
   本意是"让它别动"——**结果它正是最大的那个动源**：队尾添一条快照，
   下一次 hoist 就把它挪到头部，后面所有消息的位置整体位移，前缀必断。这个函数已经删掉。

**怎么知道它真的生效**：看账本的缓存读写比（`core.usage.cache_health`，只看今天、只看多轮的那几个 op，
样本不足不判）。健康的多轮循环在 5–10×，低于 3 就该去查前缀是不是又断了。

### 3.11 检验问题用轻量围栏，不用工具

> 工具协议换成原生之后，这一条**反而更值得单拎出来说**：不是"这里还没来得及换"，
> 而是这件事本来就不该是工具调用。

教练每轮末尾会主动问一个能检验是否真懂的问题（`review_in_chat` 开着时），
用 ```` ```check ```` 围栏包起来，服务端摘出来攒进题库（`question-pool.json`）。

**为什么不让它调工具**：调工具要多一个来回（多一次计费、多等几秒），
而这件事没有任何需要服务端算的东西。

**为什么值得攒**：这些题是在我刚学完那一刻、对着我当时的理解提出来的，
比事后让模型看着 md 现编的题贴身得多；而且它已经生成过一次了，别再付第二次钱。

**去重用的是一把量出来的尺子。** 人没答的时候，教练下一轮会换个说法再问一次——
规整后的题面当然不一样，于是每问一次就攒一条。而考点那一栏也靠不住：
它是按当轮提到的节点算的，图在长、集合就在变。真正稳定的信号是题面本身：

| | 相似度（`SequenceMatcher` 打在规整后的题面上） |
|---|---|
| 真实题库里那组同义改写，两两之间 | **0.68 ～ 0.97** |
| 同主题但确实是另一道题 | 0.30 ～ 0.41 |
| 跨主题、该判成不同的那些，最高 | **0.19** |

中间那段空白很宽，阈值取 **0.6**。`source="chat"`、没答过、相似度过线就算同一道，
留最新措辞、考点取并集。**只对 chat 那一路生效**——出题那一路一轮本来就会围绕
同几个节点出好几道不同的题，两条路共用一把尺子会把一整轮测验并成一道。

> 题库里**不存复习调度**。什么时候该抽查由节点的 review-log 说了算（第四份契约）——
> 题目再自带一套间隔，就成了第二份调度真值，两边迟早对不上。
> 同理 `ref_answer`（来自我自己写的正文，可信）和 `full_answer`（批改时模型补的，可能有幻觉）
> **是两份数据，不许合并**。

## 4. 工具表：返回值是写给模型看的提示词

11 个工具，5 个只读、2 个改状态、4 个只出卡片。

| 工具 | 类别 | 教练 | 面试 | 聊天 |
|---|---|:-:|:-:|:-:|
| `search_nodes` / `read_node` / `overview` | 只读·图谱 | ✅ | ✅ | ✅ |
| `today` / `projects` | 只读·调度 | ✅ | — | — |
| `quiz` / `record_review` | 改复习状态 | ✅ | ✅ | — |
| `propose_changes` | 出卡片·改 md | ✅ | — | ✅ |
| `propose_project` / `propose_points` / `propose_list_edit` | 出卡片·改 projects.json | ✅ | — | — |

**一个容易被忽略的设计点：工具的返回文本本身就是提示词。** 例子：

- `propose_changes` 返回的不只是"成功"，而是
  "变更卡已经摆在他面前了（N 个文件）。**还没有写盘**，等他点「写入」。你不要再说已经存好了。
  **还有别的事要提就接着提**——一轮里可以摆好几张卡。"
  最后那句是专门为"一轮一张卡"解锁的：链路本来就支持一轮摆好几张，
  但上一版的措辞只说"等他点写入"，模型读完就收尾了，于是互不相关的几件事被迫拆成好几轮。
- `propose_project` 在撞到同名/同目标的已有项目时，返回里会带一段
  "**他已经有「X」，看起来和这个是一回事**——先问一句是独立一个项目还是加一份清单"。
  这个判断（`_near_projects`）是**服务端算的，不是模型猜的**。
- `propose_list_edit` 的退回也是教学：新 id 在这份清单里已经存在时，不是简单报错，
  而是说"**那这俩是重复，该 `drop` 一条而不是改名**"。删空一份清单时，
  卡上标红、返回里也提醒它在卡外面说清楚为什么要清空。
- `propose_changes` 落地时**服务端顺手把新建的点补进当前项目的清单**，并在返回里告诉模型
  卡上会写着加到哪。不补的话：节点建出来了、项目进度却不认它。这件事也不问模型，服务端算。
- 工具执行失败时，错误原文**回给模型**（"工具 X 执行失败：…"），对话继续，同时记一笔 `issues.jsonl`。
  工具出错原来只在那一轮对话里闪一下，"这东西为什么老出问题"没有任何地方能回答。

## 5. 护栏总表

| 护栏 | 在哪一层 | 挡住什么 |
|---|---|---|
| 工具白名单 | 服务端分发 | 调了表外的工具 → 退回，不执行 |
| 只提议不写盘 | 工具实现 | 模型没有任何一条能写 md / projects.json 的路径 |
| dry-run 与写入同一份代码 | `curation.preview` | 卡片上的 diff 和真正写进去的不一致 |

| 字段 / 路径白名单 | `core.writer` | 改 id、改坐标、往 `doc/` 里塞节点 |
| `update_body` 需持有全文 | 工具返回文本 + 卡片告警 | 截断写回吃掉后半篇（正文缩水超四成会在卡上喊） |
| 清单改动逐条校验 | `_one_list_edit` | 改成一个已存在的 id（那是重复，不是改名）、负荷填三档之外、把清单删空不吭声 |

| 续接前缀校验 | `turns.resume` | 接错一段上下文（宁可全量重发） |
| `seen_calls` 去重 | 循环内 | 同参工具调用空转烧钱 |
| `MAX_STEPS` 兜底 | 循环外 | 连着调 8 次还不收敛 → 停，用最后说的那段当答案 |
| 双闸裁上下文 + 截断告知 | `_fit_history` | prompt 撑爆 / 模型拿半截记忆当完整的用 |
| 缓存读写比告警 | `core.usage.cache_health` | 前缀悄悄断掉（不报错、答案全对、只有账单在涨） |
| 密钥不入库 | `.gitignore` + `knowrary check` | `*.local.json` 被 git 跟踪 |

## 6. 账单（实测基线）

`.knowrary/llm-usage.json`，截至 **2026-09-18**，默认 provider = claude-cli（Opus 档）。
**这是续接缓存上线之前的基线**，留着是为了下次能比：

| | 调用 | 花费 | 输出 token | 缓存读 | 缓存写 |
|---|---:|---:|---:|---:|---:|
| **合计** | 116（失败 5） | **$23.02** | 196,268 | 2,944,331 | 1,466,418 |
| `chat-教练` | 92 | $18.27（**79%**） | 154,664 | 2,610,538 | 1,180,294 |
| `chat`（改口径之前的老 op 名） | 7 | $0.96 | 3,590 | 115,684 | 79,390 |
| `suggest`（连边建议） | 7 | $2.03 | 8,693 | 94,283 | 113,334 |
| `quiz` + `quiz-diagnose` | 5 | $0.75 | 5,959 | 65,515 | 55,664 |
| `plan-propose`（拆点） | 3 | $0.65 | 15,247 | 47,715 | 24,234 |
| `plan-interview`（面试清单） | 2（失败 1） | $0.35 | 8,115 | 10,596 | 13,502 |

四条能直接读出来的结论：

1. **对话吃掉将近八成的账**——这也是为什么"别问要不要建、直接提卡"被写进提示词：
   每多一轮就是一次完整上下文重发。
2. **缓存读只有写的 2 倍。** 当时看着像"断点摆对了"，其实是个警报：
   真续上的话这个比值该在 5–10×。146 万的 cache_write 就是那 54 次新前缀的价钱。
3. 单次调用那一族（出题、拆点、建议）加起来才 $3.4。**不做成 agent 的部分，成本可以忽略。**
4. **卡片产出现在答得出来了**（2026-09-20 补的 `cards.jsonl`，见 §7）：今天摆了几张、点了几张、
   累计采纳率多少。**花费和产出是两份互不相干的流水**，在 `/api/llm/usage` 这个接口里才第一次
   拼到一起——卡片流水里一分钱都不存。

界面上有一个常设的模型调用监控（只看今天），以及一张学习日历——
**日历全是算出来的，没有第二份记录**：建了几个点来自 md 的 `learned`，
复习来自 `review-log.json`，答题来自 `quiz-log.json`，花了多少钱来自 `llm-usage.json`。

## 7. 数据契约：模型能碰哪几份

| 文件 | 性质 | 谁写 | 模型能不能直接写 |
|---|---|---|---|
| `nodes/*.md` | **唯一真值源** | 人（经 ChangeSet） | ❌ 只能提议 |
| `.knowrary/index.json` | 派生缓存，可随时删了重建 | `knowrary index` | ❌ |
| `.knowrary/layout.json` | 用户数据（位置、分组、折叠、贴图、边拐点） | 人拖拽 | ❌ |
| `review-log.json` | 第四份契约：复习**状态** | 复习动作 | ⚠️ 只能记「忘了」 |
| `pending.json` | 第五份契约：待审边（LLM 推测、人没认的） | 导入链路 | ❌ 审核通过才写回 md |
| `settings.json` | 第六份契约：会改变后端行为的开关（两档复习开关在这） | 人 | ❌ |
| `projects.json` | 项目 = 视角不是容器（一组 node_id 的引用） | 人（经项目卡 / 清单卡） | ❌ 只能提议 |
| `quiz-log.json` | 事件流，只追加 | 答题 | ❌ |
| `question-pool.json` | 题库 | `check` 围栏 / 批改 | ⚠️ 间接 |
| `chat/*/YYYY-MM.jsonl` | 对话**真值**，不入库不建索引 | 每一轮 | — |
| `cards.jsonl` | **旁路事件流**：摆了一张卡 / 这张卡被点了。**不存钱**，成本按天从账本现算 | 提卡与落盘两侧 | — |
| `turns.json` / `cli-sessions.json` | **可丢的缓存**：续接用，删了只是多花一次重发 | 每一轮 | — |
| `issues.jsonl` / `llm-usage.json` | **旁路**：记不上绝不能拖垮主线 | 全链路 | — |

两条贯穿的纪律：

- **推测出来的东西不进真值源。** 待审边、幽灵占位（计划里有、图里还没建的点）、复习记录，三者同理。
- **缓存和旁路都不许拖垮主线。** 读不出来当没有，写不上只打一行日志。
  这也是 `turns.json` 敢做成一个普通 JSON 文件的前提。

## 8. 事故驱动：几条规矩是怎么长出来的

| 事故 | 现在的规矩 | 写在哪一节 |
|---|---|---|
| 正文截到 1200 字，模型 `update_body` 整篇写回，后半篇没了 | `READ_CHARS` 提到 8000；部分读取只准 `append_body`；缩水超四成在卡上喊 | §3.7 |
| `create_node` 不读 `body`，建出来的节点只剩 desc 复读一遍 | 补上；**是教练在对话里自己读源码定位到的**，卡片 + diff + 出错留痕让它可查可绕 | §11.1 |
| 图谱快照写在提示词中间，采纳一张卡就让整段静态指令重买 | 改成队尾的 mid-conversation system，且没变就不贴 | §3.10 |
| `_hoist_system` 本意让快照别动，实际是最大的动源 | 删掉；改成只增不改 | §3.10 |
| `--resume` 在真实使用里约八成没生效（67 段会话 54 段只有一次往返） | 服务端留一份完整消息列表，只追加新的那句 | §3.8 |
| 一个开关同时管"教练别考我"和"今日面板还给不给复习" | 拆成总闸 + `review_in_chat` 子开关 | §3.6 |
| 教练换个说法再问一次，题库攒出一堆同义题 | 相似度 0.6 去重（阈值是量出来的），只对 chat 那一路 | §3.11 |
| 模型用一模一样的参数连搜两遍 | `seen_calls` 短路 + "别再调工具了" | §2.2 |
| `search_nodes` 不拆词，多词查询必然零命中 | `SPLIT_Q` 按词边界拆，逐词匹配计分 | §3.7 |

| 工具出错只在那一轮闪一下，规律无从查起 | `issues.jsonl`，只留最近 500 条 | §4 |
| "讲多深"和"记多满"用了同一栏口径，正文被压成一句 desc | `levels.py` 拆出第五栏 `note` | — |
| 模型每次都问"要不要建"，每问一次就是一轮完整重发 | 提示词硬规矩：**卡片本身就是这个问法** | §3.5 |

## 9. 没做的，和为什么

| 没做 | 为什么 |
|---|---|
| **向量检索 / RAG** | 95 个节点、64 条边。关键字 + 按词拆 + 一跳邻居已经够用，而 embedding 要引入第二份索引和它的失效问题。真正的检索问题不是"找不到"，是"图里根本没建"（详见《[向量库与RAG](选型对照/向量库与RAG.md)》） |
| **多 agent / 子 agent** | 口径差异用提示词解决（§3.3）。看着像该并行的两处都被故意做成串行：批量导入的队列**一次只拆一篇**，孤点的「问 AI 连什么」**一次一个点**（47 个孤点跑一轮就是 47 次调用，得让人看得见在花钱） |
| ~~**原生 function calling**~~ | **2026-09-20 做了**（§3.1）。当天先砍掉了 claude-cli 的对话能力，当天又加回来：围栏留作它那条路的适配层。**能力该由配置决定，不该由一次架构选择替用户决定** |
| **借通用 agent 客户端跑导入** | 同上那天收了回来（§1）：导入的输入集合能提前算出来，它是流水线不是 agent。真要给别的 agent 客户端用，该做的是把 CLI 暴露成 MCP，而不是让完整能力只长在某一个客户端里 |
| **MCP** | 工具全在自己进程里，跨进程协议纯属额外一跳。**但这只回答了作 client 那一半**——作 server（把 CLI 暴露给别的 agent 客户端）是该做还没做的，见《[MCP](选型对照/MCP.md)》 |
| **对话进数据库** | 真值是 JSONL 留档、`rg` 毫秒级；续接缓存是可丢的，0.2 MB。三条触发线写在 `turns.py` 里。知识层与行为层的分层判断见《[数据库](选型对照/数据库.md)》 |
| **在对话里开第二个复习入口** | 复习有专门的地方（项目下的「今日」分栏）。对话里每轮追问既费钱又没转化——教练那一侧该做的是少说话，不是多给入口 |
| **学习时长统计** | 唯一真正需要新记录的东西：手动计时会有"忘了停表"的脏数据，被动推断会把"开着页面去吃饭"算进去 |

以后可能做的：

- 可链 id 子集加一路"按名字模糊匹配"（如果导入时 stub 误报变多）。
- 如果哪天 provider 固定在支持原生 tool use 的那一侧，把文本协议换掉能省一批往返。

## 11. 复盘：对着使用记录看它实际跑成什么样（2026-09-19）

上面十节是"设计成什么样"。这一节是回头翻真实使用记录——
`review-log.json` / `quiz-log.json` / `question-pool.json` / `llm-usage.json` /
`.knowrary/chat/` 的 25 轮留档 / 67 段教练类 CLI 会话 / `git log` 的节点新增。

**查出来的问题已经折回正文了**（§3.6 的开关、§3.8 的续接、§3.5 的清单卡、§3.11 的去重尺子）。
这里只留三样：方法、还欠着的、以及教训。

### 11.1 被真实事故验证住的那一半

硬边界那一侧扛住了最糟的一次：手改了 Obsidian 里的文件，同时 `writer.py` 的 `create_node`
**静默吞掉 `body`**（几个节点的正文只剩 desc 复读一遍）。教练在对话里自己读源码定位到根因，
并用 `create_node`（空 body）+ `append_body` 两步绕开它。
**md 是唯一真值 + 卡片带 diff + 出错留痕**这三条，把一次静默数据丢失变成了可查、可绕、可修。

同样被验证的还有：工具返回即提示词（加上"一轮可以摆好几张卡"之后，日志里确实出现三张卡同时在桌上）、
分层加载（模型主动选 `append_body` 而不是 `update_body`）、文本协议 + claude-cli 兜底
（473 段机器会话没有一次栽在协议本身）。

> **最后这条要加一句脚注。** 它确实没栽过——但样本全是 Claude，而围栏失败是静默的：
> 真栽了，表现是"模型明明想查一下，那段话却被当成答案吐出来"，**留档上看不出任何异常**。
> "没观察到失败"和"不会失败"是两回事，尤其当唯一的观测手段查不出这类失败时。
> 2026-09-20 给能走原生的 provider 换上原生 tool use（§3.1），不是因为它栽了，
> 是因为这个论证本身不成立。围栏留给 claude-cli——**那条路上这个风险仍然在，
> 只是它换来的是"不填密钥就能用"**，代价说清楚了就是一笔可以做的交易。

### 11.2 三条教训，都是方法上的

**① 日志记的是过去，配置决定的是现在。** 最初写这份复盘时，我照着对话留档写了一整节
"复习闭环停摆、教练每轮还在念欠账"，并据此提方案——而 `review_enabled` 早在
**2026-09-18 21:15**（日志里最后一段对话结束后半小时）就关掉了。
等于对着一个已经修好的问题提修法。**诊断前先读配置当前值，再看日志。**
真正剩下的问题不是"没人复习"，而是那个开关太粗（§3.6）。

**② 先量，再定阈值。** 题库去重第一版按"考点集合相同"去并，跑下来只并掉 1 条——
考点是按当轮提到的节点算的，图在长、集合就在变。改成量题面相似度之后才发现
真重复和真不同之间有 0.19 → 0.68 这么宽的一段空白，阈值这才有地方落（§3.11）。

**③ 不报错的退化最贵。** `--resume` 续不上、缓存前缀断掉、用例喂错数据形状——
这三件事的共同点是：**功能全对、测试全绿、界面正常，只有账单在涨或者断言在空转。**
所以 §5 那张护栏表里专门留了一行"缓存读写比告警"：它不防错误，它防的是**静默变贵**。

### 11.3 还欠着的

**（2026-09-20：这一节清空了。）** 最后一条「出题 / 批改的摘录取正文开头」处理掉了，
而且处理的方向和原来写的不一样——原来想的是"按目录挑节铺开"，实际做成了**挑一节给足**：

> 一道题本来就只考一个点。24 节均分下来每节只剩几十字，既问不出任何一节的实质，
> 又让模型以为自己看全了——**题会变水**，正是 `MAX_NODES` 那条老注释早就警告过的。
> 正确的形状是**抽查本来就是采样**：每次挑一节给足，下次到期抽另一节，
> 跨几轮复习自然覆盖全篇，这就是间隔重复本来的样子。

轮换指针用 review-log 已有的 `step`（每复习一次 +1），**零新状态**；批改那一路不轮换，
按题干跟小标题的词重合挑节——它要给的是这道题的判分依据，挑错节等于没给。
短笔记（94 篇里 88 篇）走的还是"整篇给"，一个字都没动。

**但这条修的是症状。** 一篇 17k 字、24 个小标题的笔记，本身就违反了「一个知识点一个 md」——
摘录逻辑是在替一个数据模型问题擦屁股。真正该做的是把它拆开，
而"这篇太长了该拆"完全可以变成欠账面板里的一类（和孤点、stub 并列）。**这件事还没做。**
