# 实操：滑动窗口裁剪，让长对话每一轮都打断前缀缓存

> 日期：2026-09-30
> 代码基线：`dc1124e`
> 对应条目：《[架构提升点](../../架构提升点-2026-09-29.md)》#16
> 相关原理：《[前缀缓存与Agent上下文架构](前缀缓存与Agent上下文架构.md)》

## 一句话

`_fit_history` 在对话超过上限时，每一轮都**从最前面删掉一两条**。续接缓存要求"上一轮存下的可见历史"和"这一轮发来的可见历史"逐字一致，所以**超过上限之后，每一轮都对不上、每一轮都整段重建**。

用真实函数模拟 60 轮对话：从第 31 轮开始，一轮不落全部重建；60 轮累计写缓存 **107 万字**。改成"按块裁剪"之后，只重建 4 次，累计 **13.5 万字（减少 87%）**，而且不需要新增任何状态。

## 一、先摆出三个前提

| 前提 | 在哪里 | 内容 |
|---|---|---|
| ① 前端每一轮都重发**整段**可见历史 | `ChatRequest.messages`（`server/contracts.py`） | 会话状态在前端，服务端不持有 |
| ② 服务端能续就续 | `turns.resume`（`server/turns.py:74`） | 上一轮存下的可见投影 `== incoming[:-1]` 时，复用上一轮的完整内部消息列表，只追加新的一句 |
| ③ 前缀缓存只认逐字一致 | Anthropic 官方文档 | 前缀从第一个不同的字节起全部失效。写缓存按约 1.25 倍价格计费，读缓存约 0.1 倍 |

中间还有一步裁剪：`_fit_history`（`server/chat.py:1738`）有两道闸：

```python
MAX_MESSAGES = 60           # 最多带 60 条
MAX_HISTORY_CHARS = 24000   # 最多带 24000 字

kept = msgs[-MAX_MESSAGES:]
while len(kept) > 1 and total > MAX_HISTORY_CHARS:
    kept = kept[1:]         # 从最早的开始，一条一条往外丢
```

还有关键的一点：②里存下来的"可见投影"，是**裁剪之后**的历史（`chat.py:2075`）：

```python
turns.remember(vault, key, visible=[*history, answer], ...)   # history 已经被 _fit_history 裁过
```

### 插一段：会话状态放在前端，为什么服务端还要存一份

`ChatRequest` 的注释写的是"会话状态在前端，服务端不持有"。这句话写得比较早。复盘 §11.2 之后，服务端多了一份**可以随时丢掉的缓存** `turns.json`，现在准确的说法见《Agent 架构与选型》§3.8：**真值在前端和留档，服务端只有一份可丢的缓存。**

之所以需要这份缓存，是因为**前端发来的历史，和模型实际看到的历史，天然就对不上**。前端只存给人看的可见轮次；只要上一轮调过工具，模型那一侧就会多出几条前端不会回传的消息：

```
你问："TCP 和 UDP 什么区别？"

模型实际经历的（服务端内部列表）：
  user:      TCP 和 UDP 什么区别？
  assistant: （调 search_nodes("TCP")）
  tool:      [搜索结果：TCP 节点、UDP 节点……]
  assistant: （调 read_node("TCP")）
  tool:      [TCP 节点正文 3000 字]
  assistant: TCP 是面向连接的……（最终回答）

前端存下、下一轮会回传的（可见轮次）：
  user:      TCP 和 UDP 什么区别？
  assistant: TCP 是面向连接的……（只有最终回答）
```

如果下一轮只用前端发来的可见轮次重新拼，前缀里就**少了中间 4 条工具往返**，和上一轮实际发给模型的对不上，缓存就断了。设计文档记录的真实数据是：67 段教练会话里有 54 段，几乎每一轮都在重开前缀，原因就是这个。

所以 `turns.resume` 分两步：
1. **校验**：上一轮存下的可见投影，是否等于这一轮发来的 `incoming[:-1]`（除去最新一句之外的部分）。相等，说明前端这段历史没有被改过、删过；
2. **续接**：校验通过，就取出上一轮的**完整内部列表**（包括工具往返），只在末尾追加这一轮的新问。这样前缀和上一轮逐字一致，缓存能够命中。

校验不通过（前端改过、换了一段对话、服务端重启后缓存丢了），就退回去用可见轮次整段重建。结果只是多花一次钱，不会出错，所以它是缓存，不是真值。

**本文的问题正出在第 1 步：** 校验用的"可见投影"是裁剪之后的历史，裁剪起点每一轮都在往后挪，存下来的和这一轮发来的就永远对不上。

## 二、流程拆解：第 30、31、32 轮分别发生了什么

用 HunDun 真实留档的平均值来算：用户消息 85 字，回复 682 字，**每一轮约 767 字**。按这个速度，聊到第 30 轮时，一共 59 条消息，约 22,300 字。

```
第 30 轮（还没到上限）
  前端发来：M1 M2 … M58 M59(新问)                    共 59 条
  _fit_history：没超，原样保留                         history = M1 … M59
  resume 比对：上一轮存的是 [M1 … M58]，== incoming[:-1] → ✅ 续上
  这一轮写缓存：只有 M58(上一轮回复) + M59(新问) ≈ 767 字
  存下：visible = [M1 … M59, M60(回复)]

第 31 轮（碰到 60 条的条数闸）
  前端发来：M1 … M60 M61(新问)                        共 61 条
  _fit_history：只留最后 60 条                        history = M2 … M61
  resume 比对：上一轮存的是 [M1 … M60]，这一轮是 [M2 … M60] → ❌ 对不上
  → 走 _rebuild：system（约 11,500 字）+ 60 条历史，整段重写缓存 ≈ 34,500 字
  存下：visible = [M2 … M61, M62(回复)]

第 32 轮
  前端发来：M1 … M62 M63(新问)                        共 63 条
  _fit_history：只留最后 60 条                        history = M4 … M63
  resume 比对：上一轮存的是 [M2 … M62]，这一轮是 [M4 … M62] → ❌ 又对不上
  → 又整段重建 ≈ 34,500 字

第 33 轮、第 34 轮……每一轮开头都比上一轮多丢 2 条，每一轮都对不上。
```

**根本原因：** 滑动窗口的本质是"每一轮都改开头"，而前缀缓存的前提是"开头永远不动"。两者正面冲突。

一旦越过上限，就进入一个稳定的坏状态：每一轮都付约 34,500 字的写缓存，而不是约 767 字，**每一轮大约多付 45 倍的写入量**。

两道闸都会触发这个问题：条数闸（60 条，约 30 轮）和字数闸（24000 字）按上面的平均值差不多同时到达。只要有几条特别长的回复，字数闸就会先到。

### 3.4 两处更正

1. **真实数据里还没有触发过。** HunDun 现有 7 段对话，最长的一段 10,474 字，没有一段超过 24000 字。这是一个**潜在**问题：一旦有人连续聊 30 轮以上，就会触发。

## 四、解决方案

目标只有一个：**超过上限之后，裁剪起点不要每一轮都挪。**

### 方案 A：迟滞，一次裁到一半（需要记住起点）

超过上限时，一次性裁到上限的一半；之后起点固定不动，直到再次超过上限。

```python
def fit_with_hysteresis(msgs, start):          # start 要存起来，比如存进 turns.json
    kept = msgs[start:]
    if 超过两道闸之一(kept):
        while 超过一半(kept):
            kept = kept[1:]
        while kept[0]["role"] != "user":       # 起点对齐到 user 消息
            kept = kept[1:]
        start = len(msgs) - len(kept)
    return kept, start
```

**结果：** 60 轮只重建 3 次（第 1、31、47 轮），累计写缓存 99,950 字，**减少 91%**。

**代价：** 需要一份新状态，也就是 `start`。它还和"前端改过、删过历史"的情况纠缠在一起，要额外处理。

### 方案 B：起点按块取整（零状态，推荐）

起点只能取 `CHUNK` 的整数倍。选择能同时满足两道闸的**最小倍数**：

```python
CHUNK = 20      # 一块 = 20 条消息（10 轮）

def _fit_history(msgs):
    start = 0
    while True:
        kept = msgs[start:]
        total = sum(len(m.get("content") or "") for m in kept)
        if (len(kept) <= MAX_MESSAGES and total <= MAX_HISTORY_CHARS) or len(kept) <= 1:
            return kept, start
        start += CHUNK
        if start >= len(msgs):
            return msgs[-1:], len(msgs) - 1
```

**为什么起点稳定：** 历史在往后增长，但满足两道闸的"最小块倍数"只会在跨过块边界的那一轮才变一次。其余轮次起点完全相同，前缀就完全相同。

**附带的好处：** 起点是 20 的倍数，是偶数，而可见轮次是一问一答交替的，所以起点**天然落在 user 消息上**，不需要额外对齐。

**结果：**

```
轮次  带过去的条数  丢掉的条数  历史字数  续上?  这一轮要写缓存的字数
  30          59         0     22328     是         767
  31          41        20     15425     否       26925
  32          43        20     16192     是         767
  33          45        20     16959     是         767
  40          59        20     22328     是         767
  50          59        40     22328     是         767
  60          59        60     22328     是         767
整段重建的轮次（共 4 次）：[1, 31, 41, 51]
60 轮累计写缓存：135,312 字
```

60 轮只重建 4 次，**减少 87%**。比 A 多重建一次，但**不需要任何新状态**，是一个纯函数，符合 Knowrary 一贯的"零新状态"做法。

**CHUNK 大小的取舍：**
- CHUNK 越大，重建越少：每跨过一块才重建一次，大约每 CHUNK / 2 轮一次；
- 代价是刚裁完的那一轮，带过去的上下文更少；
- 20 条（10 轮）是一个折中：裁完之后仍然至少保留约 2/3 的上限。

### 再加一层：利用"免费窗口"

《前缀缓存与Agent上下文架构》§7 的原则："缓存死了的那一刻，是重排、压缩、归档唯一免费的窗口。"

**做法：** 距离上一轮已经超过缓存 TTL（默认 5 分钟；配了 1 小时就按 1 小时）时，缓存本来就已经过期，这一轮无论如何都要整段重写。这时顺手把起点往前推，比如推到一块，**不会多花一分钱**。距离上一轮的时间，从续接缓存或留档里都能拿到。

### 参考来源：OpenClaw 和 Claude Code 怎么处理上下文增长

这个方案借鉴的是两个成熟 agent 处理上下文增长的方式。它们遵守的是同一条原则：**动前缀开头这件事，要少做、集中做，由阈值或者缓存过期来触发，不能每一轮都做。**

| | 做法 | 共同点 |
|---|---|---|
| **OpenClaw** | 发请求前先估算 token（`src/agents/embedded-agent-runner/run/preemptive-compaction.ts`），快满了才**一次性**压缩或截断；cache-ttl 裁剪只在缓存过期之后才动手（`src/agents/agent-hooks/context-pruning/extension.ts`） | 平时只往后追加 |
| **Claude Code** | 一直往后追加，到"有效窗口减 13k"才压缩一次（`services/compact/autoCompact.ts`）；空闲超过 60 分钟、1 小时 TTL 必然已经过期时，才清理旧的工具结果（`services/compact/timeBasedMCConfig.ts`） | 动开头的时机，要么是撞上阈值，要么是缓存已经失效 |
| **Knowrary 现状** | 超过上限之后，每一轮都把起点往后挪 | 违背了这条原则 |

也有一处不同：OpenClaw 和 Claude Code 的"压缩"要**额外调一次模型**来写摘要；方案 B 只是按块取整裁剪起点，**不调模型**，更便宜。这也符合 Knowrary 的设计：按照"md 是唯一真值"的设计，聊清楚的东西本来就应该已经写进 md 了，被裁掉的历史不需要摘要，缺什么上下文让模型自己去图里查，`_rebuild` 的提醒语已经这么告诉模型了。

## 五、落地清单

1. **改 `_fit_history`**：换成方案 B 的写法，返回值的形状 `(kept, dropped)` 不变。
2. **改现有用例**：`chat_长对话按条数和字数两道闸裁_并且说出来`（`server/tests/run.py`）里的 `dropped == 18` 会变成 20，也就是块的倍数。断言要改成"dropped 是 CHUNK 的倍数，并且裁完不超过两道闸"。
3. **补一条新用例**：构造刚好越过上限的对话，连续跑 10 轮，每轮都走 `_fit_history → turns.resume → turns.remember`，断言**只有越过块边界的那一轮是重建，其余轮次都续上**。本文附录的模拟脚本就是这条用例的雏形。
4. **上线后验证**：看 `llm-usage.json` 的 `prefix` 诊断（`dc1124e` 加的）。长对话里，"可见轮次对不上"应该只在跨过块边界时出现一次，而不是连续出现。
5. **可选**：加上"超过 TTL 顺手裁剪"那一层。

## 六、这件事的教训

- **"只追加"是全局约束，不是某一个函数的约束。** 续接缓存、系统提示词、工具表都守住了"只追加"，结果在裁剪这一环悄悄破了。凡是会动消息列表开头的地方，都要问一句：它会不会每一轮都动？
- **不报错的退化最贵**，《Agent 架构与选型》§11.2 ③写过这一点。这个问题功能完全正确、测试全绿、界面正常，只有账单在涨；而且只在长对话里出现，日常短对话永远测不出来。
- **用真实函数做模拟，比读代码更可靠。** 读代码时我以为"提醒语里的 N 也会断前缀"，跑一遍就证伪了。

## 附录：模拟脚本

在 Knowrary 仓库根目录下，用 `.venv/bin/python sim_fit_history.py` 运行。只使用临时目录。

```python
"""复现：滑动窗口裁剪让续接缓存每轮失效。直接调用 chat._fit_history 与 turns.resume / remember。"""
import os, sys, tempfile
from pathlib import Path

REPO = Path.home() / "IdeaProjects" / "Knowrary"
sys.path.insert(0, str(REPO))
os.environ["KNOWRARY_HOME"] = tempfile.mkdtemp(prefix="sim-home-")
from server import chat, turns

USER_CHARS, ASSISTANT_CHARS = 85, 682   # HunDun 真实留档的平均值
SYSTEM_CHARS = 11500                     # 渲染后的系统提示词约 11,500 字
TURNS, KEY, CHUNK = 60, "demo|s1|教练", 20


def fit_chunked(msgs):
    start = 0
    while True:
        kept = msgs[start:]
        total = sum(len(m["content"]) for m in kept)
        if (len(kept) <= chat.MAX_MESSAGES and total <= chat.MAX_HISTORY_CHARS) or len(kept) <= 1:
            return kept, start
        start += CHUNK
        if start >= len(msgs):
            return msgs[-1:], len(msgs) - 1


def simulate(fit):
    vault = Path(tempfile.mkdtemp(prefix="sim-vault-"))
    (vault / ".knowrary").mkdir()
    visible, rows = [], []
    for i in range(1, TURNS + 1):
        visible.append({"role": "user", "content": "问" * USER_CHARS})
        history, dropped = fit(list(visible))
        prior = turns.resume(vault, KEY, history)
        resumed = prior is not None
        hist_chars = sum(len(m["content"]) for m in history)
        write = (USER_CHARS + ASSISTANT_CHARS) if resumed else SYSTEM_CHARS + hist_chars
        answer = {"role": "assistant", "content": "答" * ASSISTANT_CHARS}
        internal = (prior or [{"role": "system", "content": "S"}, *history[:-1]]) + [history[-1], answer]
        turns.remember(vault, KEY, visible=[*history, answer], messages=internal)
        visible.append(answer)
        rows.append((i, len(history), dropped, hist_chars, resumed, write))
    rebuilds = [r[0] for r in rows if not r[4]]
    print(f"重建 {len(rebuilds)} 次：{rebuilds}；累计写缓存 {sum(r[5] for r in rows):,} 字")


simulate(chat._fit_history)   # 现状
simulate(fit_chunked)         # 方案 B
```
