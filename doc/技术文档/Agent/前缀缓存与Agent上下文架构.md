## 一句话

有前缀缓存时，重发历史近乎免费，**重开前缀才是账单大头**——所以 agent 的消息列表必须只增不改。

---

## 为什么会有这东西

聊到第二十轮，下一句话跟前面毫无关系。把前面那一大堆再发一遍给模型，直觉上就是在烧钱。
于是很自然会想到两个方案：**前面加一个小模型判断相不相关，无关就重新开始**；
或者**把旧历史压缩成一段摘要**。

这两个方案都建立在同一个隐含假设上：**token 按量计费，每个 token 一样贵。**

前缀缓存把这个假设打破了。同一批 token，根据它处在什么状态，有**三种完全不同的价格**：

| 状态 | 价格（相对基础输入价） | 差距 |
|---|---|---|
| 缓存命中（读） | **0.1×** | — |
| 没有缓存（普通输入） | 1.0× | 10× |
| 写入缓存（5 分钟档） | **1.25×** | **12.5×** |
| 写入缓存（1 小时档） | 2.0× | 20× |

一旦知道这张表，"重发历史很浪费"这个直觉就站不住了：**你想省的那一项是最便宜的一项，
而"重新开始"这个动作命中的恰恰是最贵的一项。**

这篇讲的就是这张表如何一路决定 agent 的上下文设计——从消息列表的形状，
到什么时候该归档，到为什么不该加那个判断器。

## 够用版

### 1. 一条不变量，其余都是它的推论

> **前缀缓存是前缀匹配。前缀里任何一个字节变了，它之后的全部失效。**

缓存键来自渲染后 prompt 的**精确字节**，一直算到每个断点。渲染顺序固定：
`tools` → `system` → `messages`。所以第 N 个位置上改一个字符（一个时间戳、一个重排过的
JSON key、一个多出来的工具），位置 ≥ N 的所有断点全部作废。

这条不变量直接推出三件事。

### 2. 推论一：只能追加，或者整个重来——不能廉价地改中间

| 你想做的 | 会发生什么 |
|---|---|
| 在末尾追加新消息 | ✅ 前面全部命中，只写新增那一小段 |
| 改写中间某几轮（压缩、摘要、删无关的） | ❌ 断点全废，整段重新写一遍 |
| 丢掉最早几轮 | ❌ 同上——丢头部也是改前缀 |
| 整段重开 | 付一次完整写入 |

**"压缩历史省钱"是个陷阱。** 把 20 轮旧对话换成 200 字摘要，token 数确实少了，
但你**改写了中间**，于是要为整段重新付一次 1.25× 的写入。
只有当"重写一次的代价 < 继续按 0.1× 重发的代价"时它才划算，而这需要历史长到相当程度。

如果你的 agent 本来就给上下文设了上限（比如"最多 60 条 / 24000 字"），
**那个上限本身已经是压缩了**，再叠一层摘要几乎必然是负收益。

### 3. 推论二：成本驱动是"开了多少次新前缀"，不是"单轮 prompt 多大"

这两件事很容易混：

- **单轮 prompt 的大小** 决定的是**会不会炸**（超上下文窗口）。分层加载、按需读取解决的是这个。
- **新前缀的次数** 决定的是**贵不贵**。

一个真实的对照：某个 agent 的账单里，`cache_write` 118 万 token、`cache_read` 261 万 token。
看 token 数是 1:2，看**钱**就反过来了——

```
cache_write:  118 万 × 1.25 = 147 万  ← 59% 的账单
输出:          15 万 × 5.0  =  77 万  ← 31%
cache_read:   261 万 × 0.1  =  26 万  ← 10%
```

**重发的历史只占 10%。** 而那 59% 全部来自"又开了一次新前缀"。

### 4. 时间维度：缓存什么时候死

三条机制决定一个缓存条目活多久（Anthropic 口径）：

1. **两个档位**：默认 5 分钟，或显式 `ttl: "1h"` 买 1 小时。写入价随档位涨（1.25× → 2×）。
2. **一次读会免费把计时器续上**。
3. **寿命从请求"开始"算起**——生成时间也算在里面。一次跑了 4 分钟的生成，
   只给下一个请求留大约 1 分钟。

第 2 条最容易被忽略，但它解释了很多反直觉的现象（见下面「深入」里那个 16 小时的例子）。

按**相邻两次请求的间隔**选档：

| 间隔 | 选哪档 |
|---|---|
| < 5 分钟 | 默认档。每次请求都在续期，永远热着，买 1 小时档纯亏 |
| 5–60 分钟 | **1 小时档是唯一划算的窗口** |
| > 1 小时 | 两档都救不了。要么定时预热，要么接受冷启动 |

### 5. 多 provider：差的不是数字，是种类

这是设计要支持多个模型时最大的坑——**不要做一张「模型 → 缓存时长」的配置表。**

| provider | 谁决定缓存 | 保温多久 | 命中折扣 | 你能调的 |
|---|---|---|---|---|
| **Anthropic** | 你（显式断点，最多 4 个） | **你选** 5 分钟 / 1 小时 | 0.1× | 断点位置 + TTL |
| **OpenAI** | 平台（自动前缀） | 5–10 分钟不活动即清，**1 小时内必清** | **0.5×** | 只有"别动前缀" |
| **DeepSeek** | 平台（磁盘缓存） | 几小时到几天，**明说不保证** | ≈0.1× ⚠️ | 只有"别动前缀" |
| **本地 vLLM / Ollama** | 显存 | **不是时间，是 LRU 淘汰** ⚠️ | 不计 token，计算力 | 并发 / 显存 |

三处会直接翻转结论的差异：

- **折扣差 5 倍。** OpenAI 命中只打 5 折，不是 1/10。同一段历史在 OpenAI 上重发，
  代价是 Anthropic 的 **5 倍**。"要不要归档"的答案本来就该随 provider 变。
- **OpenAI 没有 1 小时档可买。** 1 小时是硬上限，不是选项。
- **本地模型根本不按时间过期。** vLLM/Ollama 的前缀缓存是显存里的 KV block，按 LRU 淘汰——
  别人发个大请求就可能把你挤掉，跟隔了多久无关。而且它不按 token 计费，
  没命中就是真的要重新 prefill：那是**延迟**问题，不是账单问题。
  一张写着"时长"的表，在这一行连单位都对不上。

**结论：把「缓存还在不在」做成实测量，不做预测量。** 每次调用的 `usage` 里都有
`cache_read_input_tokens`；把它按 (provider, 距上次同 key 调用的间隔) 分桶，
看它什么时候掉到 0，就是这个 provider 在你的流量上的实际保温时长。
这比查表准（含平台实际负载的影响），而且上游改策略时你的数字自己就跟上了。

### 6. 那个"相关性判断器"为什么不该加

回到开头那个方案：前面加个小模型判断新消息跟历史相不相关，无关就重开。

**第一，它想省的是账单里最便宜的 10%**（在缓存命中的前提下），
而"重开"这个动作本身命中的是最贵的那一项。

**第二，判错的代价是不对称的：**

| 判错方向 | 后果 |
|---|---|
| 该留却判成"无关" | 模型不知道自己少了上下文，重新解释、重新检索、重新问你"哪个项目"。**你付得更多，答案更差，而且它不报错**——你只觉得"今天这 AI 有点笨" |
| 该丢却判成"有关" | 多花那 10% 里的一小块。没有任何东西坏掉 |

一边静默且不可恢复，一边只是小钱。**这种形状的决策，必须硬偏向安全的那一侧。**

**第三，也是最要紧的一条：历史带的不是"话题"，是"状态"。**
聊了十轮 Transformer，下一句"帮我建个 NLP 项目"——看起来无关，实际最相关，
因为得知道刚才聊过什么才能判断这是新建还是并进已有的。
而历史里真正在承载的是：哪张卡还没确认、你刚纠正过它什么、它已经检索过哪些词、当前在哪个作用域。
**这些都不是话题，判话题相似度的模型结构上就看不见它们。**
话题切换 ≠ 上下文失效。

**第四，能用时钟解决的，不要用模型。** 如果真正想处理的是"隔太久了"，
那是一个**事实**（时间戳相减），不是一个**判断**。时钟没有假阳性。

### 7. 但缓存过期那一刻，是重构历史唯一免费的窗口

第 2 节说"改中间会打断前缀，所以别压缩"。这句话有个前提：**前缀还活着。**

一旦超过 TTL，前缀已经一文不值了——这时候压缩、归档、重排，**一分钱都不多花**。

于是有了这条总纲：

> **缓存活着的时候只增不改；缓存死了的那一刻，是重排、压缩、归档唯一免费的窗口。**

这也给了"什么时候该归档"一个**确定性**的触发器：不是问模型"相不相关"，
而是看一眼时钟有没有越过 TTL。越过了，继续带着历史就拿不到任何缓存红利，
这时"留还是丢"退化成一个纯粹的**内容价值**问题，跟成本无关了。

配套的一条：归档不必裸奔。把上一段的**最后一条回复 + 涉及的实体 id** 当一句状态摘要带上——
这些东西留档里现成就有，**不用额外调模型**，所以这个"压缩"是真的零成本。

## 深入：解剖一份真实账本

理论到此为止。下面是一个真跑了三天的 agent 的账本（默认 provider 是 `claude -p`，
即用 Claude Code 当后端），95 次成功调用。它推翻了上面好几条推演的适用条件。

### 现象一：命中率 100%，而且跨 16 小时还命中

```
09-17 16:20  距上次 60,079s（16.7 小时）→ cache_read 202,806  ✅
09-18 15:56  距上次 57,553s（16.0 小时）→ cache_read  13,103  ✅
```

16 小时远超任何 TTL 档位。而 `cache_read = 13,103` 这个值在三天里**一模一样出现了 53 次**——
它是一段恒定前缀。如果只有这个 agent 在刷新它，16 小时的空档里它早该死了。

**解释在第 4 节那条被忽略的机制上：一次读会免费续期。** 这台机器上有人整天在用
Claude Code 写代码，每一次开发调用都顺手刷新了同一段前缀的计时器。
**这个 agent 蹭的是别人（同一个人写代码时）保温的缓存。**（此为推断 ⚠️：
账本只能看到"它没凉"，看不到"是谁续的"。）

这件事的启发不是"你也去蹭"，而是：**同一套代码，在"蹭得到"和"蹭不到"的环境里，
账单结构完全不同。** 这正是第 5 节那条结论的实证——该测，不该查表。
顺带一提，这种蹭是脆弱的：它依赖同一台机器、同一个 workspace
（缓存按 workspace 隔离，不跨组织共享），以及"那个人一直在写代码"。

### 现象二：真正在烧钱的是"每个回合的第一次调用"

把 95 次成功调用按 `cache_read` 的形态分两类：

| | 次数 | cache_write | 占比 |
|---|---:|---:|---:|
| **回合首次**（`cache_read` = 恒定的 13,103） | 55 | **990,996** | **79%** |
| **回合内续发**（`cache_read` 递增到 3–6 万） | 40 | 268,688 | 21% |

- **回合内**（几秒内的多次工具往返）：`cache_write` 均值 6,717，最低只有 297——只发增量。
- **回合首次**：`cache_write` 均值 **18,018**，等于把整段对话历史重写一遍缓存。

根因是个很典型的架构错配：**前端每轮回传的是"可见轮次"（剥掉工具块的干净对话），
而服务端内部那份还夹着工具往返。** 两份构造性地对不上，于是每个新回合的第一次调用
必然重开前缀——**不报错，答案全对，只有账单在涨。**

修法就是第 2 节那条推论的直接应用：服务端按会话键留一份**完整**消息列表，
新一轮只把最后那句话追加上去；前端回传的那份降级成"证明这一段没被改过"的校验，
对不上才整段重建。

### 现象三：那 79% 值多少钱

`cache_write` 的定价是 1.25×，是 `cache_read` 的 12.5 倍。
55 次首发写掉的 **99 万** token，折成输入当量 **124 万**；
而同期**全部** cache_read 是 273 万 token，折成当量只有 **27 万**。

**光是"每个回合重开一次前缀"这一项，就比整整三天里所有被重发的历史加起来还贵 4.5 倍。**

**一句话：这个 agent 账单上最大的一块，是一个不报错的前缀失效 bug。**

## 我当时卡在哪

**① 我以为"重发历史"是浪费。**
→ 实际在缓存命中时它只要 0.1×，是整条链上最便宜的一项。
→ 因为前缀缓存把 token 拆成了三种价格，而直觉里只有一种。

**② 我以为缓存一过期就该加个判断器决定要不要重开。**
→ 实际时钟就够了，而且严格更好。
→ 因为"隔了多久"是事实，"相不相关"是判断；判断会错，而且错的那一侧是静默的。

**③ 我以为压缩历史能省钱。**
→ 实际在缓存活着时它更贵（改中间 = 整段重写），而在缓存死后它免费。
→ 因为前缀缓存只认"前缀有没有变"，不认"内容变短了没有"。
**这一条翻转了两次**，是整篇里我最容易再犯的一个错。

**④ 我以为 provider 之间只是"缓存时长不一样"，写张表就能兼容。**
→ 实际它们连语义都不一样：Anthropic 是"你买的时长"，OpenAI 是"平台的不活动清理"，
本地模型是"显存 LRU"——**最后一个根本没有时间这个维度**。
→ 因为缓存不是一个统一的抽象，是各家各自实现的一个优化。

**⑤ 我以为"够不着缓存旋钮"就等于"没有缓存"。**
→ 实际 `claude -p` 就是 Claude Code 本体，它自己是 API 客户端、自己摆断点，命中率 100%。
→ 够不着的是**选择权**（断点摆哪、买不买 1 小时档），不是缓存本身。
**"我控制不了它"和"它不存在"是两件事。**

**⑥ 我以为间隔超过 TTL 就一定冷。**
→ 实际被同一台机器上别的流量续了命，跨 16 小时照样命中。
→ 因为一次读会免费续期，而缓存是按 workspace 共享的，不是按应用。

## 容易混的

| A | B | 区别 |
|---|---|---|
| **提示词缓存** | **会话续用**（如 `--resume`） | 两层，串联。会话续用决定"这次发多少条消息给客户端"；提示词缓存决定"客户端发给 API 的那个请求前缀有没有命中"。前者稳住了，后者才有机会命中 |
| **缓存过期** | **上下文窗口溢出** | 前者是**钱**的问题（还能跑，只是贵），后者是**能不能跑**的问题。分层加载解决后者，只增不改解决前者 |
| **TTL** | **最小可缓存前缀** | 前者是时间（5 分钟 / 1 小时），后者是长度（512–4096 token，**随模型变且不单调**）。前缀太短会**静默不缓存**，不报错，只是 `cache_creation_input_tokens: 0` |
| **context editing** | **compaction** | 前者**清除**旧的工具结果 / thinking 块，后者**摘要**历史。两者都改中间，都会打断前缀 |
| **cache_write 便宜** | **cache_write 量小** | 上面那份账本里 write 的 token 数只有 read 的一半，但因为单价高 12.5 倍，**钱**上它是 read 的 5 倍。看 token 数会得出完全相反的结论 |

## 出处与待核实

**已核实：**
- Anthropic 计价（读 0.1×、写 1.25× / 2×）、TTL 两档、读免费续期、寿命从请求开始算、
  最多 4 个断点、最小可缓存前缀分模型表（512 / 1024 / 2048 / 4096）、
  mid-conversation system message 的机型支持——来自 `claude-api` skill 的 `shared/prompt-caching.md`。
- OpenAI：自动缓存、≥1024 token、按 128 token 递增、5–10 分钟不活动清理、1 小时内必清、
  命中打 5 折——[Prompt caching | OpenAI API](https://developers.openai.com/api/docs/guides/prompt-caching)、
  [Prompt Caching in the API | OpenAI](https://openai.com/index/api-prompt-caching/)
- DeepSeek：磁盘缓存、自动、"不再使用后自动清除，通常几小时到几天"、best-effort 不保证——
  [Context Caching | DeepSeek API Docs](https://api-docs.deepseek.com/guides/kv_cache/)

**⚠️ 待核实：**
- DeepSeek 的命中折扣 ≈0.1×，是按它公布的 cache hit / miss 单价（$0.014 / $0.14 每百万 token）
  推算的，**来自搜索摘要而非定价页原文**，且价格会变。用前核一次。
- 本地 vLLM / Ollama 的前缀缓存按 LRU 淘汰——**没有查证官方文档**，属于一般认知。
- 通义 / Qwen（DashScope）的缓存策略**完全没查**。
- 「13,103 那段恒定前缀是被同机器的 Claude Code 开发流量续命的」是**推断**：
  账本只能证明它没凉，证明不了是谁续的。

**本篇没覆盖：**
- Anthropic 的 1 小时档之外的保温手段（`max_tokens: 0` 预热请求）只提了一句，没展开算账。
- 缓存与**并发**的关系（多个请求同时打同一个冷前缀会各写一份还是共享）。
- Bedrock / Vertex / Foundry 上缓存行为与第一方 API 的差异。
