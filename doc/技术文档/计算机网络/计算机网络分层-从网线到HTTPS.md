# 计算机网络分层：从网线到 HTTPS

## 一句话

每一层的「尺寸」都是被下一层逼出来的：线长定最短帧，内存定 MTU，MTU 定 MSS，隧道再吃掉一截。

## 全景图：一条尺寸链

```
物理层：线长 + 速率 → 2τ → 最短帧 64B
链路层：内存/公平性/效率的折中 → 最长载荷 1500（MTU）
IP 层：包超过某段链路的 MTU → 分片（只在目的主机重组）
TCP 层：MSS = 1500 − 20 − 20 = 1460，自己先切好，避免 IP 分片
VPN 隧道：外层头占掉一部分空间 → tun 的 MTU 设成 1420，不然内层包装不下
应用层：HTTPS = HTTP over TLS；经代理时用 CONNECT 打通一条字节隧道
```

为什么是 1500 而不是更大？一笔效率账：

```
载荷  500：  500 /  538 ≈ 93%
载荷 1500： 1500 / 1538 ≈ 97.5% 链路效率
载荷 9000： 9000 / 9038 ≈ 99.6%   ← 从 1500 加到 9000 只多了 2 个百分点
```

（分母 = 载荷 + 每帧固定开销 38 字节：前导码 8 + 头尾 18 + 帧间隙 12。）

下面自底向上，每层只讲本次真正聊透的那一块。

---

## 物理层：2τ 和最长网线，推出的是「最短 64 字节」

### 为什么会有这东西

早期以太网是**共享总线**：一根同轴电缆，所有机器都挂在上面，同一时刻只能有一个人说话。
协议是 CSMA/CD——先听线路空闲才发；发的同时继续听，听到冲突就停，随机退避后重发。

### 够用版

问题在于：怎么保证「冲突一定能被发送方听到」？

A 在电缆一端，B 在另一端，单程传播时延为 τ。最坏情况：

```
t=0      A 开始发
t=τ−ε    信号还差一点没到 B，B 听到线路空闲，也开始发
t=τ      两个信号在 B 附近相撞
t≈2τ     冲突信号传回 A
```

A 必须在 **2τ 时刻仍在发送**，才能检测到冲突。帧太短的话，A 早已发完，会误以为发送成功——数据其实已经撞坏了。

代入 10 Mbps 以太网：

- 最大网络：5 段 × 500 m 同轴缆、4 个中继器（「5-4-3 规则」），总长约 2500 m
- 信号在铜缆中约 2/3 光速，加上中继器延迟，往返 2τ 控制在 **51.2 μs** 内（称为 slot time）
- 51.2 μs × 10 Mbps = **512 bit = 64 字节**

所以以太网**最短帧 64 字节**；扣掉 18 字节头尾，数据区最少 46 字节，不够就补零（padding）。

**四个量绑死在一起**：线长、速率、2τ、最短帧。速率 ×10，要么最短帧 ×10，要么线长 ÷10。
千兆以太网半双工就是靠把 slot time 扩到 512 字节（carrier extension）来维持的。

### 深入

- 现代以太网是**交换机 + 全双工点对点**，收发各走各的线对，根本不存在冲突，CSMA/CD 已名存实亡。
- 但 64 字节最短帧作为兼容性被保留了下来。

## 数据链路层：MTU 为什么是 1500

### 为什么会有这东西

MTU（Maximum Transmission Unit）= **一种链路层帧能装的最大载荷**。它是**每种链路各自的属性**，1500 只是以太网的值。

| 链路 | MTU |
|---|---|
| 以太网 | 1500 |
| PPPoE（家用宽带拨号） | 1492（PPPoE 头占了 8 字节） |
| Wi-Fi 802.11 | 2304（实际桥接到以太网，一般还是按 1500 用） |
| 以太网巨型帧（数据中心） | 9000 |
| 本地回环 lo | 65536 |
| WireGuard 隧道 | 1420（外层再套 IP + UDP + WG 头） |

**PPPoE：家里就能撞见的「隧道吃 MTU」**

家用宽带拨号用 PPPoE，本质也是一种封装：PPP 帧套在以太网帧里跑。物理链路仍是以太网，载荷上限还是 1500，但 PPPoE 头要占 8 字节（PPPoE 头 6 + PPP 协议号 2），留给 IP 包的只剩：

```
1500 − 8 = 1492（MTU）
1492 − 20（IP 头）− 20（TCP 头）= 1452（MSS）
```

和 VPN 是同一个道理：**每多套一层壳，内层可用空间就少一截**，上层的 MTU / MSS 必须跟着调小，否则就会触发分片，或者包在半路被丢。家用路由器的 WAN 口 MTU 默认填 1492，原因就在这里。

以太网帧结构：

```
[前导码 7 + SFD 1][目的MAC 6][源MAC 6][类型 2][  数据 46 ~ 1500  ][FCS 4]
                  └──────────── 帧 64 ~ 1518 字节 ────────────────────────┘
帧与帧之间还有 12 字节的帧间隙（IFG）
```

### 够用版

1500 **不是物理推导出来的**，是 1980 年前后 DIX（DEC / Intel / Xerox）以太网定标准时的工程折中。

**太长不行：**
1. **共享总线的公平性**：一帧 1518 字节在 10 Mbps 下占线约 1.2 ms，期间所有人只能干等。帧越长，别人的延迟和抖动越大。
2. **内存贵**：网卡至少要缓存一整帧，当年 RAM 很贵。⚠️ 未核实：常被认为是最主要的原因，但没有找到当年标准制定者的一手说法。
3. **出错代价**：链路层误码整帧丢弃，帧越长越容易中招，重传代价也越大。
4. CRC-32 检错能力随长度下降，但到约 1 万字节仍可靠（巨型帧 9000 因此可行），属次要因素。

**太短也不划算**——每帧固定开销 38 字节（前导 8 + 头尾 18 + IFG 12）：

```
载荷  500：  500 /  538 ≈ 93.0%
载荷 1500： 1500 / 1538 ≈ 97.5%
载荷 9000： 9000 / 9038 ≈ 99.6%   ← 从 1500 涨到 9000 只多 2 个点，已进入收益递减
```

### 为什么 40 年没变

带宽从 10M 涨到 400G，内存便宜了上百万倍，1500 却纹丝不动——因为它**被写进了格式**：

- 以太网头那 2 字节一字两义：**≤ 1500** 表示长度（802.3 格式），**≥ 1536（0x0600）** 表示类型（IPv4 = 0x0800）。
- 路径 MTU 取全路径最小值。全世界设备都按 1500，单方面调大只会出问题。只有数据中心这种全程自控的网络才开 9000。

## 网络层（上）：IP 分片

### 够用版

包大于下一段链路的 MTU 时，IPv4 路由器会把它**切成多片**，每片带上同一个标识号和片偏移，各自独立转发（可能走不同路径）。

```
发送方 ─1500─ R1 ─576─ R2 ─1500─ 接收方
    1500B 的包    R1 切成 3 片    R2 原样转发，不拼      接收方内核才重组
```

关键事实：**只在最终目的主机重组，中途路由器不重组。**

**IPv6 更彻底**：路由器连切都不切，包太大直接丢弃，并回 ICMPv6「Packet Too Big」，由源主机自己切小。

### 分片的问题（为传输层埋伏笔）

- **IP 不重传**：丢任何一片，整个包都重组不出来。
- **只有第一片带端口号**：防火墙 / NAT 看不到后续分片的端口，经常直接丢。
- **重组要缓存 + 超时**：伪造分片可以耗尽接收方重组缓冲（分片类 DoS）。

## 网络层（下）：VPN 原理

### 为什么会有这东西

想在公网上访问一个私有网络（如公司内网），并且：
1. 应用无感知——不用每个程序单独配；
2. 公网上的人看不到、改不了内容；
3. 外人不能随便进来。

### 够用版：一个包的完整旅程

**① 路由表决定走不走 VPN**

应用调 `send()`，内核把数据组装成完整 IP 包（TCP 头、IP 头都在内核里加好），然后**查路由表**：

```
10.0.0.0/8       dev tun0                    ← VPN client 启动时加的
<server 公网IP>   via 192.168.1.1 dev en0     ← 例外路由，见 ③
default          via 192.168.1.1 dev en0
```

命中 tun0，内核就把这个 IP 包交给 tun 设备。

**② tun 是一块「假网卡」**

它的另一头不是网线，而是一个文件描述符（Linux `/dev/net/tun`，macOS `utun`）。
VPN client 进程对它 `read()`，读到的就是一个**完整的原始 IP 包**。不是 tun 主动「上传」，是 client 去读。

**③ 不改包，套壳**

client **不修改**原始包的目标 IP，而是把整个原始包加密后当成数据，外面再包一层新头：

```
原始包（内层）：
  [IP src=10.8.0.2 dst=10.0.5.20][TCP][HTTP 请求...]

发出去的包（外层）：
  [IP src=192.168.1.5 dst=<server公网IP>][UDP][加密后的(整个原始包)]
```

这就是「隧道」：IP-in-UDP（或 IP-in-TCP）。外层就是一个普通 UDP 包，通过普通 socket 发出去。

**例外路由必不可少**：外层包的目的地是 server。若它也被路由进 tun（例如全局模式下 default 指向 tun），就会被再封装一次、再进 tun……无限套娃。所以 client 一定会加一条「server IP 走物理网卡」。

**④ 鉴权在握手，不在每个包**

建连时握手一次（证书 / 账号密码 + MFA / WireGuard 的公钥），协商出会话密钥。
之后每个包用 AEAD 加密：**能用会话密钥解开且校验通过，就说明来自已认证的对端**；伪造包解密失败直接丢。
在此之上还可以叠 ACL（「这个用户只能访问 10.0.5.0/24」）。

**⑤ server 不是代理，是三层转发**

server 解密出内层原始 IP 包后，**写进自己机器的 tun**。对它的内核来说，相当于某块网卡收到了一个包：
- 开了 `ip_forward`，内核按路由表把包转发到内网；
- 通常再做 NAT（MASQUERADE），把源地址 10.8.0.2 换成 server 的内网 IP，内网服务器回包才知道回给谁。

**⑥ 回程**

```
内网服务器回包 → server（NAT 还原目标为 10.8.0.2）
  → 路由命中 tun → server 进程读出 → 加密封装 → UDP 发回 client
  → client 收到、解密 → 把内层包 write() 进 tun
  → 内核视为「tun 网卡收到一个包」→ 走协议栈 → 交给应用的 socket
```

### 深入

- **用户态 vs 内核态实现**：OpenVPN 就是上面的用户态路线，每个包多两次内核/用户态切换，性能差；WireGuard、IPsec 在**内核里**完成加解密，快。macOS / iOS 的 VPN 由系统的 NetworkExtension 框架托管 utun。
- **TUN vs TAP**：TUN 收发三层 IP 包（绝大多数 VPN）；TAP 收发二层以太网帧，能把两个局域网桥成一个。
- **分流 vs 全局**：只路由 10.x 进 tun 叫 split tunnel；接管 default 叫全局。DNS 要跟着处理，否则内网域名解析不出来。
- **MTU 要调小**：外层要多出 IP + UDP + VPN 自身头部，几十字节。tun 的 MTU 设成 1420 左右，否则内层包装不进外层的 1500，又要分片。（WireGuard 默认 1420 是按外层 IPv6 算的：1500 − 40 − 8 − 32 = 1420。）

### 和代理的区别

| | VPN（三层隧道） | 代理（SOCKS / HTTP） |
|---|---|---|
| 搬运的东西 | 整个 IP 包，什么协议都行（TCP / UDP / ICMP） | 应用层请求，代理自己发起新连接 |
| TCP 连接 | 应用与目标端到端直连，server 只转发包 | 被代理截成两段 |
| 对应用 | 透明，靠路由表接管 | 应用要配代理地址 |

## 传输层：TCP 为什么还要自己分段

### 为什么会有这东西

IP 已经能分片了，TCP 为什么还要按 MSS 切？

### 够用版

1. **丢一片 = 丢整个段（核心原因）**。IP 不重传。一个 4000 字节的 TCP 段被切成 3 片，丢 1 片整段作废，TCP 超时后要把 4000 字节**全部重传**，重传的又被切片、又可能丢……
   TCP 一开始就按 MSS 切好，丢哪段只重传哪段。
2. **分片对中间设备不友好**：后续分片没有端口号，防火墙 / NAT 常直接丢；接收方重组有缓存开销和攻击面。
3. **TCP 本来就得切**：TCP 是字节流，应用一次可能 `write` 10 MB，而 IP 包上限 64 KB；序号确认、滑动窗口、拥塞控制都以「段」为单位运转，段的大小就是重传粒度。既然必须切，就顺手切到**恰好不触发 IP 分片**的大小。

**配套机制：**
- 建连时双方在 SYN 里通告 MSS：1500 − 20（IP 头）− 20（TCP 头）= **1460**。
- **路径 MTU 发现（PMTUD）**：发包置 DF（Don't Fragment）位；途中有更小的 MTU，路由器丢包并回 ICMP，发送方据此调小段长——全程无分片。

### 反例：UDP

UDP 不分段，包大了只能吃 IP 分片，所以 UDP 上的协议都刻意把包做小：
- DNS：传统上限 512 字节，EDNS 一般建议 1232 字节，超了就改走 TCP。
- QUIC（HTTP/3）：自己置 DF，包控制在 1200 字节左右。等于在 UDP 之上又实现了一遍 TCP 的分段逻辑。

## 上三层：会话层、表示层、应用层

### 为什么会有这东西

OSI 七层模型在传输层之上还有三层。实际使用的 TCP/IP 模型把它们**合并成一个应用层**，所以很少看到某个协议单独标明自己属于「会话层」或「表示层」。

```
OSI 七层            TCP/IP 四层         谁在干活
─────────────────────────────────────────────────
7 应用层  ┐
6 表示层  ├──────── 应用层            用户态：程序自己 + 库（OpenSSL、protobuf…）
5 会话层  ┘
─────────────────────────── ← socket 接口：用户态 / 内核态的分界线
4 传输层  ───────── 传输层           内核：TCP / UDP
3 网络层  ───────── 网络层           内核：IP、路由表、tun
2 链路层  ┐
1 物理层  ┘──────── 网络接口层       网卡驱动 + 硬件
```

这条分界线把前面几节串了起来：**传输层及以下在内核，上三层都在用户态**。所以 VPN client 要用 tun 去「偷」内核里的 IP 包，而 HTTPS 代理只需要在用户态处理 CONNECT，不用碰内核。

### 够用版

**会话层（第 5 层）：管理「一次对话」**

职责是建立、维持、结束双方之间的一段对话，并提供同步点。TCP 只保证「这条连接上的字节可靠到达」，会话层关心的是更大的单位：
- **断点续传**：传了一半断了，从哪个检查点继续。
- **对话控制**：轮到谁说话（半双工令牌）。
- **会话恢复**：断线重连之后，还认不认得出是同一个人。

现实中的对应都不是独立的一层，而是散落在各个协议里：
- TLS 的会话恢复（Session ID / Session Ticket）：重连时跳过完整握手。
- Web 的登录态：Cookie / token 维持「已登录」。下文应用场景里换了出口 IP，也要尽量让网站认为还是同一个会话。
- RPC 框架的长连接、心跳和重连，数据库连接的 session。

**表示层（第 6 层）：管理「数据长什么样」**

让双方对数据的表示方式达成一致，主要做三件事：

| 功能 | 解决什么 | 现实中的例子 |
|---|---|---|
| 编码 / 序列化 | 内存里的对象怎么变成字节，大小端、字符集怎么统一 | JSON、Protobuf、ASN.1、UTF-8、Base64 |
| 加密 | 别人看不懂 | TLS 的加解密 |
| 压缩 | 传得更少 | gzip、brotli（HTTP 的 `Content-Encoding`） |

TLS 常被说成「横跨会话层和表示层」：握手和会话恢复属于会话层的职责，加解密属于表示层的职责。它在 TCP/IP 模型里没有明确的位置，正好说明这三层在实践中是揉在一起的。

**应用层（第 7 层）：业务语义**

定义「具体要干什么」：请求一个网页、查一个域名、发一封邮件。

| 协议 | 干什么 | 下层 |
|---|---|---|
| HTTP | 网页、API | TCP（HTTP/3 是 QUIC，基于 UDP） |
| DNS | 域名 → IP | UDP，包大了改走 TCP |
| SMTP / IMAP | 邮件 | TCP |
| SSH | 远程登录 | TCP |

**放到一次真实请求里**（一个程序向后端上报状态）：

```
应用层   POST /api/report  {"status": ...}       ← HTTP：业务语义
表示层   JSON 序列化 → gzip → TLS 加密           ← 数据长什么样
会话层   token / Cookie 维持登录态，TLS 会话复用   ← 是不是同一段对话
──────── socket ────────
传输层   TCP，按 MSS 1460 切段
...
```

### 为什么 TCP/IP 不分这三层

1. **TCP/IP 赢在先落地**：OSI 模型由 ISO 委员会在 80 年代初设计，那时 TCP/IP 已经在 ARPANET 上跑起来了。最终是「已经能用的」胜出，OSI 留下来的主要是一套分层术语。⚠️ 未核实：具体年份（OSI 参考模型标准 ISO 7498 的发布时间、ARPANET 切换到 TCP/IP 的时间）。
2. **这三层的功能和应用强相关**：每个应用要的序列化格式、会话语义都不一样，做成所有程序共用的一层反而不好用，交给各自的库更灵活。所以它们都在用户态，内核只到 socket 为止。

一句话：**下四层管「怎么把字节送到」，上三层管「送的是什么、用什么格式、属于哪段对话」**。实践中上三层被压成一个应用层，由各个程序自己实现。

## 应用层：HTTPS 走代理

### 够用版

HTTPS = HTTP over TLS。客户端与目标网站之间做 TLS 握手，之后的 HTTP 报文全部加密。

当浏览器配了 HTTP 代理时，HTTPS 流量不能让代理逐条解析（代理没有网站的证书私钥，也解不开），于是用 **CONNECT 方法**：

```
浏览器 → 代理：CONNECT www.example.com:443 HTTP/1.1
代理   → 浏览器：HTTP/1.1 200 Connection Established
此后：代理只在两端之间双向透传字节，TLS 握手和加密数据都从它身上原样穿过
```

**代理能看到 / 看不到什么：**
- 能看到：目标域名和端口（CONNECT 行、TLS 握手里的 SNI）、流量大小和时序。
- 看不到：URL 路径、请求头、Cookie、请求体——这些都在 TLS 里，端到端加密。

普通 HTTP（明文）走代理时，浏览器直接把完整请求发给代理，代理可以看、可以改头（比如补一个 `Proxy-Authorization`）。

### 应用场景：云桌面上的浏览器自动化，出口 IP 「跟人走」

（以下为某业务项目的抽象，已去除具体厂商、系统与配置。）

**背景**：一套自动化程序跑在机房的云桌面虚拟机里，用无头浏览器代替用户操作某个网站。
网站对「账号登录地突变」有风控：用户人在 A 城市，虚拟机在 B 城市的机房，账号会被判定为异地登录。

**做法**：让浏览器的出口 IP 落在用户所在城市。

```
浏览器（启动参数指定 --proxy-server=127.0.0.1:<本地端口>）
   │
   ▼
本地转发代理（同一台虚拟机上的 Node 进程）
   ├─ 普通 HTTP：转发时补上 Proxy-Authorization（上游账密）
   └─ HTTPS：收到 CONNECT → 带认证向上游发 CONNECT → 打通后双向透传
   │
   ▼
上游代理（第三方代理 IP 服务商按城市分配的出口 IP，有有效期）
   │
   ▼
目标网站：看到的来源 IP 在用户所在城市
```

**触发**：先分别定位用户 IP 和虚拟机 IP 的城市，**不同城才启用**代理，按用户城市去服务商取一个出口 IP。

**为什么本地还要多一层代理**：浏览器的 `--proxy-server` 参数不支持带账号密码。本地起一个**免认证**代理，由它替浏览器完成上游认证。换出口 IP 时只改本地代理的上游指向，浏览器不用重启。

**工程上的几处讲究：**
- **续期**：出口 IP 有有效期，到期前几分钟主动换。
- **健康检查**：定时经代理访问一个中立探测站；不通再探一个大站，区分「代理坏了」还是「探测站自己挂了」。**不拿目标网站做探测**，免得探测流量本身成为风控信号。
- **排水（drain）**：换 IP 时不立刻掐旧隧道——到期换就等它空闲几秒再关，IP 已坏就快速止损，两种情况都设绝对时间上限。
- **像浏览器一样克制**：限制全局与同域名的并发 CONNECT 数、连续建连之间错峰、同一域名连续失败就短时熔断。
- **止损**：短时间内频繁换 IP 仍不可用，说明代理整体有问题，直接终止任务，不再烧钱。
- **挂起恢复**：云桌面会话断开后进程可能被挂起，用 event loop 卡顿检测发现「刚被挂起过」，恢复后主动刷新出口 IP。

**放回分层里看**：这是**七层**（HTTP CONNECT）代理，只有配置了代理的浏览器走它；程序自己发的其他请求不受影响。和网络层的 VPN 对照：

| | VPN | 这个场景的代理 |
|---|---|---|
| 层级 | 三层，tun 接管 IP 包 | 七层，CONNECT 隧道 |
| 接管范围 | 路由表命中的所有流量 | 只有配了 `--proxy-server` 的浏览器 |
| 加密 | VPN 自己加密 | 代理本身不加密；HTTPS 内容由 TLS 端到端保护 |

## 我当时卡在哪

- **以为 VPN client「把目标 IP 改成 server 的 IP」** → 实际是**不动原包，整包加密后套一层新 IP+UDP 头** → 因为 server 拆壳后要拿到原封不动的原始包，才能按原目标地址转发。
- **以为 tun 把包「上传」给 client** → 实际是 client 进程对 tun 的文件描述符 `read()` → tun 是假网卡，另一端是 fd 不是网线；**走不走 VPN 由路由表决定**，应用完全不知情。
- **以为 server 每个包都要「校验权限」** → 实际鉴权在**握手时做一次**，之后靠会话密钥：能解开就是合法对端 → 每包做完整鉴权太贵，AEAD 解密本身就是认证。
- **以为 server「作为代理转发」** → 实际是**三层转发 + NAT**，TCP 连接端到端不被截断 → 代理是七层概念，会把连接截成两段。
- **漏了加密** → VPN 的 P 是 Private，内层包在公网上必须加密防篡改。
- **以为 IP 分片需要「每个路由器重组才能转发」** → 实际**只在目的主机重组**，路由器只切不拼 → TCP 自己分段的真正原因是「IP 不重传，丢一片整段作废」+ 分片在防火墙 / NAT 上的麻烦。
- **以为「最长网线、碰撞检测、2τ」决定了 1500** → 实际它们决定的是**最短帧 64 字节** → 1500 是内存 / 公平 / 效率的工程折中，后来被帧格式（长度与类型字段的分界）锁死。

## 容易混的

- **最短帧 64B vs 最大载荷 1500B**：前者是物理推导（2τ），后者是工程折中。
- **MTU vs MSS**：MTU 是链路层载荷上限（含 IP 头）；MSS 是 TCP 数据上限（不含 IP、TCP 头），1460 = 1500 − 40。
- **路由器分片 vs 主机重组**：IPv4 路由器只切不拼；IPv6 路由器连切都不切。
- **TCP 分段 vs「TCP 粘包 / 拆包」**：前者是本文的 MSS 分段；后者是应用层没有消息边界、需自定长度字段或分隔符的问题，两回事。
- **VPN vs 代理**：三层整包隧道、对应用透明 vs 七层请求转发、需应用配置。
- **TUN vs TAP**：三层 IP 包 vs 二层以太网帧。
- **OSI 七层 vs TCP/IP 四层**：OSI 的会话层、表示层、应用层在 TCP/IP 里合并成一个应用层。TLS 在 OSI 里横跨会话层和表示层，在 TCP/IP 里归应用层（夹在 HTTP 和 TCP 之间）。

## 出处与待核实

- IEEE 802.3（以太网，含 CSMA/CD、slot time 512 bit、最小帧 64 字节、EtherType ≥ 0x0600 的约定）
- RFC 791（IPv4，分片与重组）、RFC 8200（IPv6，路由器不分片）
- RFC 1191（IPv4 路径 MTU 发现）、RFC 8201（IPv6 路径 MTU 发现）
- RFC 9293（TCP，MSS 选项）
- RFC 9000（QUIC，最小 1200 字节的 UDP 载荷要求）
- RFC 9110 §9.3.6（HTTP CONNECT 方法）
- DNS Flag Day 2020（EDNS 缓冲区建议值 1232）
- WireGuard 官方文档（默认 MTU 1420）
- ISO/IEC 7498-1（OSI 参考模型）
- ⚠️ 未核实：1500 的历史动因（尤其「网卡内存成本是主因」这一说法）缺一手出处，目前为流传说法。
- ⚠️ 未核实：10 Mbps 以太网 2500 m / 5-4-3 规则与 51.2 μs 的具体推算（中继器延迟预算等细节）以 802.3 原文为准。
