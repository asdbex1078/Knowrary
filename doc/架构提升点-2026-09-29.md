## 三、P1：正确性

### 1. 会话中途切换配置，系统提示词和实际工具对不上

> 状态：✅ 已完成（2026-09-30，`c3de522`）。先写用例复现了（关掉复习后第二轮提示词里还有 `quiz`、schema 里没有），再修。
>
> **实际改法比下面提议的更简单**：`_system_prompt` 的渲染是确定性的，所以没另算指纹、也没改缓存 key——续接前把现在的系统提示词渲染一遍，和缓存里那份逐字比（`chat._still_valid`），不一样就走 `_rebuild`。所有输入（复习开关、档位、侧写、关系类型、工具表）都自动覆盖，提示词和 schema 始终出自同一份数据。

**现象：**
- 续接会话时，`turns.resume` 原样复用上一轮的消息列表，**连当时渲染好的系统提示词一起复用**（`server/chat.py` 的 `_assemble`）。工具表和复习规则，都是在那一刻按开关状态渲染的（`_system_prompt`、`_apply_review_switch`）；
- 但每一轮发给模型的工具 schema，是**按当前开关**重新算的（`_run` 里的 `allowed = tools_of(...)` 和 `tools = tool_schemas(allowed)`）；
- 续接缓存的 key 是 `llm_session_key`，只包含 `project|session|stance`，**不包含开关状态**。

**后果：**
- 会话中途关掉复习后，系统提示词里还写着 quiz、record_review 可以用，schema 里却已经没有了。这正是 `_system_prompt` 注释里警告的"表里写着能用、调了却说没有"；
- 工具列表在缓存前缀的最前面，工具一变缓存本来就失效，所以复用旧的系统提示词也没省下钱。

**会影响系统提示词的输入：**
- 复习开关（`review_in_chat` 和 `review_on`）；
- `{{level}}`；
- `{{me}}`（`_me_brief`）；
- `{{relations}}`（`_relations_brief`，登记新关系类型之后就会变）；
- 工具白名单。

**改法：** 把上面这些输入算成一个指纹，拼进续接缓存的 key 里，或者和缓存存在一起比对。指纹变了就走 `_rebuild`，保证系统提示词和 schema 始终是同一份数据。

**需要补的用例：** 开着复习聊一轮，关掉复习再聊一轮，断言第二轮的系统提示词里没有复习相关的工具，并且和 schema 一致。

### 2. 改名、合并这类写多份文件的操作没有事务

> 状态：✅ 已完成（2026-09-30，`ab40690`）。`core.guarded` 先快照再动手，任何一步抛异常就按快照恢复（快照里有的拷回去，快照里没有的和这次新建的删掉），再抛 `RolledBack`；`/api/rename`、`/api/merge` 失败回 500「已经恢复到动手之前」并带快照路径。用例在最后一步人为抛错，断言 md、文件路径、layout、记录逐字节回到动手之前；把恢复那一步去掉时用例会失败。

**现状：** `apply_rename`（`tools/knowrary/core/rename.py`）按这个顺序落盘：

```
改所有引用 md → 挪文件 → 改 layout.json → 改 review-log / quiz-log / projects.json
```

- 顺序是考虑过的："先改引用再挪文件"，这样中途出错时不会留下被静默吞掉的坏链接；
- 动手前有 `backup_rename` 做整份快照；
- 但中途失败**不会自动回滚**：md 已经改了，JSON 只改了一半，只能手动从 backup 恢复。merge 也是一样。

**改法：** 快照已经有了，成本很低。在 `apply_rename` 和 merge 外面包一层 try：一旦失败，用这次的快照自动恢复，删掉新建的文件，把改名的文件挪回去，然后把原始错误抛出去。不引入新概念。

**需要补的用例：** 在 `_rewrite_records` 里人为抛一个异常，断言 md、文件路径、layout 都恢复到了改名之前的样子。

### 3. 锁只在进程内有效，挡不住跨进程写入

> 状态：暂缓（2026-09-30 复核）。风险是真的：CLI 确实会写 `pending.json`（`knowrary.py` 里的 `add_pending`）和复习记录，和服务端同一刻写同一份文件就会互相覆盖。但日常用法是一个服务端、偶尔跑一次 CLI，要撞上得两边在同一瞬间改同一份文件，目前没有踩到过的证据。按《选型对照/数据库》的口径，第 ① 条触发条件还没到；真踩到一次再和 #4 一起做。

**现状：**
- 有 4 把 `threading.Lock/RLock`，分别在 `server/index_service.py`、`server/layout_store.py`、`core/pending.py`、`core/edge_checks.py`，只防同一个 FastAPI 进程里的线程并发；
- 会同时写同一个库的还有：
  - CLI（`tools/knowrary/knowrary.py` 会写 index 和 layout）；
  - day-info 定时脚本；
  - Obsidian 和 Claude Code 直接改 md；
- md 这一侧有指纹和 revision 兜底；JSON 这一侧只有 layout 和 projects 带 revision，冲突时返回 409；
- pending、review-log、quiz-log、edge-checks 都是"读出整份 → 改一处 → 写回整份"，跨进程并发时，**后写的会覆盖先写的**。

**改法：** 暂时不用上数据库。把"读 → 改 → 写回"统一收进一个 helper：
- 用 `fcntl.flock` 加跨进程锁（锁文件放在 `.knowrary/` 下）；
- 带 revision 的文件额外做比对，对不上就重试或者返回 409；
- 现有 4 把线程锁都改用这个 helper。

这正对应《选型对照/数据库》的第 ① 条触发条件"多进程 / 多端同时写"，建议先量一下是否已经踩到了。

## 四、P2：可维护性与性能

### 4. 机器状态文件越来越多，每份各写一遍同样的读写逻辑

> 状态：暂缓（2026-09-30）。要动二十来份文件的读写，改动面大，眼下又没有它挡住的具体故障；和 #3 绑在一起，等 #3 的触发条件到了一次收口。

**现状：** `.knowrary/` 下大约有 20 份状态文件：

```
pending.json  edge-checks.json  review-log.json  quiz-log.json  question-pool.json  quiz-open.json
projects.json  layout.json  layouts/  index.json  llm-usage.json  issues.jsonl
chat/*/titles.json  tidied.json  archived.json  plans.json  imports/  backup/ ...
```

- 每份都各自实现一遍 schema_version、形状不对就退回空值、加锁、原子写；
- "成果和流水"的分界，也就是能不能丢、要不要进 git，只写在 `seed/.gitignore` 的注释里；代码层面只对 `*.local.json` 做了特判。

**改法：** 做一个状态文件注册表，由一个模块统一负责：

| 字段 | 含义 |
|---|---|
| `path` | 相对库根的路径 |
| `owner` | 哪个模块负责写（例如 pending 只由导入和审核两条链路写） |
| `schema_version` 和校验函数 | 形状不对时怎么处理 |
| `disposable` | 丢了是否可以重建（index、turns 缓存可以；layout、projects 不行） |
| `tracked` | 是否应该进库的 git |

统一提供 `load` / `locked_update` / `atomic_write` / `migrate` 这几个方法。`knowrary check` 直接按注册表核对 git 跟踪状态。

这和《选型对照/数据库》§3.1 说的"三段式是提前付的保险"是同一个思路，只是推广到所有状态文件。以后真要把行为层迁到 SQLite，只改这一处。第 3 条的跨进程锁也自然放在这里。

### 5. 几个文件已经太大

> 状态：暂缓（2026-09-30）。纯搬家，用户看不到变化。真要做，先拆 `chat.py`（四件事边界最清楚、收益最大）。复核时的数字：`app.py` 是 78 个路由（不是 83），`App.vue` 已经 3960 行。

| 文件 | 行数 | 问题 |
|---|---|---|
| `server/app.py` | 1067 | 83 个路由都在一个文件里 |
| `server/chat.py` | 2089 | 《Agent 架构与选型》§10 记的是 1633 行，已经多了 28%。工具实现、提示词组装、会话留档、agent 循环四件事写在一起 |
| `server/contracts.py` | 1494 | 所有接口的数据模型都在这里 |
| `web/src/App.vue` | 3937 | README 写的是"只做编排"，这个体量已经不止在编排 |
| `server/tests/run.py` | 7338 | 所有服务端用例都在一个文件里 |

**改法（都是低风险的重构）：**
- 路由按领域拆成 `APIRouter`：layout、changes、chat、projects、quiz、pending、import、vaults、assets；
- `chat.py` 拆成 `chat_tools.py`（工具实现和 schema）、`chat_prompt.py`（系统提示词和快照）、`chat_log.py`（留档、标题、归档）、`chat.py`（循环本身）；
- `contracts.py` 按同样的领域拆开；
- `App.vue` 继续往 `composables/` 抽状态，往 `panels/` 抽视图；
- 测试按模块拆成多个文件，仍然用自己写的 `@case` 运行器收集，不引入第三方测试框架。

文件小了还有一个附带好处：让 agent 帮忙改代码时，一次要读进上下文的内容更少。

### 6. 每次请求都在全局锁里扫一遍所有文件

> 状态：暂缓（2026-09-30）。140 个节点时无感。另外「先删掉没用上的 `watchfiles`」做不到：`uvicorn[standard]` 本身就会把它装进来，删掉 `requirements.txt` 里那一行也不会少一个依赖，顶多改一下那行的注释。

**现状：**
- `current_index`（`server/index_service.py`）持有全局 `_LOCK`，对所有 md 执行 `rglob` 加 `stat` 来算指纹。所以每个 API 请求都在这把锁上排队；只要有变化，就全量重建；
- 125 个节点时完全没问题。按注释里"够几千个节点用"的上限，到那时这就是每个请求都要付的固定延迟；
- `watchfiles` 写在了 `server/requirements.txt` 里，但运行期没有用上（注释说"阶段 3 接"）。

**改法（二选一）：**
- 接上 `watchfiles`：文件变化触发缓存失效，并且只重新解析变化的文件，做增量重建；
- 先把这个没用上的依赖删掉，和"依赖越少越好"保持一致，真接的时候再加回来。

## 五、P3：能力扩展

### 7. 对外暴露 MCP server

《选型对照/MCP》已经写了"作为 server 该做还没做"。建议把优先级往前提，理由是《Agent 架构与选型》§11.1 那次事故：Obsidian 手改文件的同时，`create_node` 静默吞掉了正文。

- 现在 Claude Code 这类外部 agent 编辑库时是**直接写文件**的：会绕开 writer 校验、写回前的备份、revision 检查，也不会进待审流程；
- 如果把核心能力暴露成 MCP 工具，比如 `search_nodes`、`read_node`、`propose_changes`、`list_pending`，外部 agent 的修改就会走同一条带护栏的链路；
- 这其实就是应用内"agent 只提议、不写盘"那条纪律，延伸到外部客户端。

### 8. 把"长笔记该拆了"做成一类欠账

《Agent 架构与选型》§11.3 写过："摘录逻辑是在替一个数据模型问题擦屁股……这件事还没做。"

**改法：**
- 欠账面板加一类"超长节点"，和孤点、stub 并列。判断依据可以是正文字数，或者二级标题的数量；
- 配一张"拆成子节点"的变更卡：模型提议怎么拆，走现有的审核和写回链路。拆完之后，原节点通过 `包含::` 关系连到各个子节点。

### 9. 缓存告警能指出具体是哪一项变了

> 状态：✅ 已完成（2026-09-30，`dc1124e`）。
> - 系统提示词拆成具名的块（`chat._system_parts`：档位 / 工具表 / 工具格式说明 / 关系类型 / 侧写 / 口径说明 / 口径规矩），拼提示词和算指纹用同一份；再加复习开关和工具 schema，各取短哈希，跟着续接缓存存在 `turns.json`；
> - 每轮记一条前缀诊断进 `llm-usage.json` 的 `prefix`：续上了没有、重建原因（新会话 / 可见轮次对不上 / 前缀变了 + 变了哪几块）；
> - 用量对话框加「前缀（今天）」一行，读写比 / 命中率变红时告警段落补一句「今天整段重建的原因：工具表变了 2 · 新会话 1」；
> - **图谱快照没算进"变了哪块"**：它挂在队尾、变了是追加一条，不断前缀，所以单独数「追加了几次」，免得被当成重建原因。

**现状：** 护栏是读写比低于 3 倍就告警（`server/contracts.py` 里的 `healthy: float = 3.0`，以及 `core/usage.py`）。它只能说明"变贵了"，说不出原因。

**可以借鉴的做法：** Claude Code 对提示词的每个组成部分分别计算哈希，发现缓存读取量下降时，直接指出是哪一部分变了。

**改法：**
- `_system_prompt` 拼接时，顺手记下各部分的哈希：工具表、`{{relations}}`、`{{me}}`、`{{level}}`、口径说明；
- 对图谱快照和工具 schema 也各算一个哈希；
- 读写比告警时，附上"和上一轮相比变了哪几项"。

第 1 条那种问题，也能靠它第一时间发现。

## 六、多模型调用与切换（2026-09-30 追加）

> 依据：`tools/knowrary/llm_backend.py`、`server/llm_call.py`，对照 OpenClaw 和 Claude Code 的做法。
> Knowrary 是单用户、本机跑的工具。OpenClaw 的多账号轮换、冷却状态存 SQLite、多厂商大抽象都太重，不照搬；这里只借小而准的做法。

**现在已经做对的（不用动）：**
- 按角色（learn / review）选 provider，上层只认同一个契约，看不见底下是哪家；
- `LLMTransient` 只把连接失败、408、425、429、5xx（2026-09-30 起含 529）当作瞬时错误，配置错和 4xx 一次都不重试；
- **已经开始吐字就不再重试**（`_retrying` 里的 `spoke`）；
- Anthropic 打了三个缓存断点：最后一个工具、顶层 system、最后一条非 system 消息；会变的图谱快照放在断点之后；
- 报错会带上"角色 · provider · 模型"；每次调用都记账，失败的也记；另外有 `llm probe` 可以测首字节要等多久。

### 10. 同一角色配一条备选链

> 状态：暂缓（2026-09-30 复核）。当前配置是 learn = `claude-cli`、review = `qwen-max`；HunDun 账本 163 次调用（09-15 ～ 09-24）里 7 次失败，没有一次是某家长时间不可用，也没有一次 429 / 529。切换还要守住「review 和 learn 不同家族」、并且一切就整段缓存作废，改动面中等偏大。等真有一家挂过一阵再做；#11 已经把「过载」单独分类（`kind="overload"`），到时候直接拿来计数。

**借鉴：** OpenClaw 的模型备选链（`src/agents/model-fallback.ts`）；Claude Code 连续 3 次 529 才切到 `fallbackModel`（`services/api/withRetry.ts:335`）。

**现状：** `resolve_provider`（`llm_backend.py:120`）让一个角色只对应一个 provider。它过载或者宕机时，这个角色的所有功能都停摆，只能去设置里手动改。

**改法：**
- `roles` 支持写成列表，例如 `"learn": ["opus", "deepseek"]`；原来写单个字符串的配置照旧能用；
- **只在过载类错误（529、503）连续出现 N 次后才切换**。偶发的 429 靠退避解决（见 #11），不切换；
- 切换之后在界面上明确说"已改用 xxx"：换了一家，缓存前缀全部失效，这一轮会更贵；
- **Knowrary 特有的约束**：README 要求 review 和 learn 用不同家族的模型。备选链不能让 review 退到和 learn 同一家族，否则互审就没有意义了。建议 `validate_config` 里直接校验这一点；
- 切到备选之后，过一段时间再试一次主模型就行。不需要 OpenClaw 那种冷却期间探测的机制。

### 11. 退避读 `Retry-After`、加随机抖动；529 目前完全不重试

> 状态：✅ 已完成（2026-09-30，`6ac4781`）。
> - `llm_backend.error_kind` 统一分类：auth / billing / rate_limit / overload / transient / other，#15 的熔断也用它；欠费除了 402 还认正文（`insufficient_quota` / `Arrearage` / `credit balance`）；
> - 529 进了重试表，归到 overload；有 `Retry-After` 就照它等，**超过 60 秒不等、直接报**；没有就基础等待加最多 25% 的随机抖动；`_sleep` 可注入，用例量等了多久而不真等；
> - 顺手修了一个：非流式时上游回 200 但正文不是 JSON（代理回了网页），原来裸抛 `JSONDecodeError`、url 全丢，现在带 url 报出来；
> - 文中「SDK 那条路是否自己重试」：本机没装 `anthropic` SDK，anthropic 类型一律走 REST，所以 529 不重试这个缺陷原来是实打实的。
> - 没做「429 和过载分开计数供 #10 切换」：#10 暂缓，分类已经留好了。

**借鉴：** Claude Code 的 `getRetryDelay`（`withRetry.ts:530`）：有 `retry-after` 就按它等；没有就按 500ms × 2ⁿ 等待，上限 32 秒，再加 25% 的随机抖动。

**现状：**
- `RETRY_WAITS = (1.0, 3.0)`（`llm_backend.py:46`），固定等 1 秒、3 秒。如果 429 带的是 `Retry-After: 20`，两次重试在 4 秒内就用完了，白白多失败两次；
- **`RETRY_STATUS`（`:47`）里没有 529**。Anthropic 过载时返回的正是 HTTP 529，所以走 REST 的 anthropic 路径遇到过载，会被 `_http_failed`（`:371`）当成非瞬时错误，**一次都不重试**，直接失败。装了 SDK 走 SDK 流式的那条路径，是否由 SDK 自己重试，还需要确认。

**改法：**
- 把 529 加进 `RETRY_STATUS`，并且单独标记为"过载"类，供 #10 计数；
- 有 `Retry-After` 就按它等，设一个上限（比如 60 秒，超过上限就不等了，直接交给 #10 切换）；
- 没有就指数退避加随机抖动；
- 429（限流）和 529 / 503（过载）分开处理：429 等待后重试，过载计入 #10 的"连续过载"计数。

**需要补的用例：** 模拟一个 529 响应，断言会重试，并且会计入过载次数；模拟带 `Retry-After: 5` 的 429，断言等待时间不少于 5 秒（用例里把 sleep 换成可注入的替身）。

### 12. 后台任务遇到过载直接放弃，不重试

> 状态：暂缓（2026-09-30）。批量导入本来就是严格串行的一篇一篇发，不存在「几路一起撞、把过载放大」；而「留在队列里稍后自动继续」要和 #10 一起才有意义。

**借鉴：** Claude Code 的 `FOREGROUND_529_RETRY_SOURCES`（`withRetry.ts:58`、`:318`）：只有用户在等结果的调用才在 529 时重试，摘要、标题、分类这类后台调用直接放弃，避免把过载放大。

**现状：** 所有调用走同一套重试。但 Knowrary 有不少调用不是用户在等的：批量导入的队列、孤点的"问 AI 连什么"、写入审核、校验已有边、Curator 推荐。

**改法：** 调用时标记前台还是后台。可以复用 `llm_call` 已有的 `op` 字段，维护一张"前台 op"白名单，例如 `chat`、用户直接点出来的出题和批改。后台调用遇到 529 / 503 不重试，把这一项留在队列里下一轮再做，在界面上显示"模型过载，稍后自动继续"。

### 13. 分出首包超时和空闲超时（现在是 900 秒一刀切）

> 状态：✅ 已完成（2026-09-30，`6ac4781`）。**默认值取得比文中建议的保守**：实测 claude-cli 一次调用 p90 97 秒、最长 190 秒，120 秒会误伤正常的慢调用。
> - 流式：首包 300 秒、空闲 180 秒，provider 上用 `first_byte_timeout` / `idle_timeout` 覆盖；撞上说是哪道；`kind="timeout"` **不重试**（再等一轮 300 秒比原来一刀切还糟）；
> - 非流式仍是 900 秒：整段生成完才有第一个字节，给它首包时限等于限制了总生成时长；
> - claude-cli：300 秒没有任何 stdout 就结束**整个进程组**（`start_new_session` + `killpg`；只杀 `claude` 本身的话，它的子进程还占着管道，读的那头照样等到底），卡死结束的不再重发全文；因为进程组独立了、Ctrl+C 传不到，读的时候出任何异常、进程退出（`atexit`）都亲手结束还在跑的进程组；
> - 顺手修了一个：设置页保存原来只留页面认识的字段，手写进配置的键（比如这两个超时）点一次保存就消失，现在原样保留。

**借鉴：** OpenClaw 的首包超时（`packages/ai/src/utils/stream-first-event-timeout.ts`）和空闲超时（`src/agents/embedded-agent-runner/run/llm-idle-timeout.ts`），云端默认都是 120 秒，本地模型的首包超时是 300 秒；Claude Code 的流式看门狗（`services/api/claude.ts:1868`）。

**现状：**
- `TIMEOUT = 900`（`llm_backend.py:45`），HTTP 请求和 claude-cli 子进程共用；
- urllib 的 `timeout` 作用在**每一次 socket 读写**上，所以这 900 秒既是"等第一个字"的上限，也是"两段输出之间"的上限。连接卡住时，要干等 15 分钟才报错；
- `llm probe` 能测出首字节要等多久，但只是手动诊断用，运行时并不会据此主动中止。

**改法：**
- 首包超时单独配置：云端 provider 默认 120 秒左右，本地（Ollama、vLLM）默认更长，也允许在 provider 上覆盖；
- 流式的空闲超时单独配置，比 900 秒短得多；
- 和现有逻辑正好衔接：首包超时发生时一个字都还没吐，`_retrying` 本来就允许重试，#10 也可以接着切到备选；
- claude-cli 子进程同理：一段时间没有 stdout 输出就结束进程。

### 14. 模型能力撞到一次就记住，不再每次先失败一回

> 状态：暂缓（2026-09-30）。「先撞 400 再折叠重发」只在 `_chat_anthropic` 里，当前配置没有 anthropic 类型的 provider，这个往返现在一次都没付过。换到 anthropic（尤其是 Sonnet 5）时再做。

**借鉴：** Claude Code 把"影响行为的判断"锁定在会话内（`claude.ts:393`、`:1405`）；OpenClaw 把提前确定好的事实往下传，不在请求时反复重新判断（根目录 AGENTS.md 里 "Hot paths should carry prepared facts forward"）。

**现状：** `_chat_anthropic`（`llm_backend.py:929-941`）处理"Sonnet 5 不支持对话中途的 system 消息"的方式是：**每一次调用都先原样发出，吃到 400 之后，再把 system 折进 user 重发**，判断依据是报错文案里有没有 "role" 和 "system"。注释解释了原因：不维护一张"哪个模型支持"的表，因为它一定会过期。这个原则是对的，代价是这个模型的每一次调用都要多付一个必然失败的往返，耗时也翻倍。

**改法：** 保留"不维护表"的原则，只是把撞到的结果记下来：
- 第一次撞到这个 400 之后，在进程内存里记下"这个 provider 加这个模型要折叠中途 system"，之后直接折叠发送；
- 想跨重启也记得，可以写进 `~/.knowrary/` 下的一份可丢缓存，比如 `llm-caps.json`；丢了只是下次重新撞一次；
- 以后再遇到类似"某个模型不支持某种用法"的情况，都走这一个机制，别每处各写一次按报错文案匹配的逻辑。

### 15. 认证和计费错误熔断，并直接提示去改配置

> 状态：✅ 已完成（2026-09-30，`6ac4781`）。`server/llm_breaker.py`：401 / 402 / 403 第一次就在报错开头说清去哪儿改（「provider `q` 的密钥被拒了（HTTP 401）：去 设置 → 模型 里改密钥。保存之后自动恢复，不用重启」），并熔断这个 provider；之后的调用不发请求，直接报「这次没有发请求——…」；`llm.local.json` 一改（mtime 或大小变了）就自动解除。「测试连接」不走熔断，试新密钥不会被旧的挡住。只在进程内存里记，没有持久化；CLI 那条路没接（批量导入走的是服务端）。没做「熔断期间走 #10 的备选」：#10 暂缓。

**借鉴：** OpenClaw 按失败原因分级冷却（`src/agents/auth-profiles/usage.ts`：计费问题、认证永久失败单独设置退避时长）；Claude Code 在 401 或"token 已吊销"时刷新凭证后重试。

**现状：** 401 / 402 / 403 不重试，这是对的。但下一次请求照样发出去、照样失败。批量导入时，每一篇文章都要重复撞一次同样的错误，出错流水里也会刷满同样的记录。

**改法：**
- 错误分类：认证失败、余额不足、限流、过载、其他（和 #11 共用同一套分类）；
- 认证失败和余额不足，在进程内把这个 provider 标记为不可用，直到配置文件变了（`llm.local.json` 的 mtime 变了），或者用户手动点"重试"；
- 标记期间，这个角色直接走 #10 的备选；没有备选时立即报错，不发请求；
- 界面上直接说清楚：例如"`deepseek` 的密钥无效（401），去 设置 → 模型 里改"，不要只甩出一段原始 HTTP 报错；
- 不需要持久化：单用户改完配置自然就恢复了。

### 16. 历史用滑动窗口裁剪，超过上限后每一轮缓存都失效

> 状态：未开始，**已用模拟复现**（2026-09-30）。直接调用 `chat._fit_history` 和 `turns.resume`/`remember` 模拟 60 轮：从第 31 轮起每一轮都整段重建，累计写缓存 107 万字；改成"起点按块取整"后只重建 4 次、13.5 万字（减少 87%）。完整过程和方案见《[实操：滑动窗口裁剪打断前缀缓存](技术文档/Agent/实操-滑动窗口裁剪打断前缀缓存.md)》。
>
> 真实数据还没有触发过：HunDun 最长的一段对话 10,474 字，还没超过上限，属于潜在问题。
>
> **更新：✅ 已完成（2026-09-30，`f2442a7`）。** 先对着代码核对属实：前端每轮都发全部历史（`useChat.js`，只有「梳理」模式从上次整理之后发），裁剪只在服务端；claude-cli 也中招——它靠前缀指纹续会话（`_cli_session`），起点一动就每轮新开会话、重发全文。用真实的 `_fit_history` 另跑了一遍 60 轮模拟：现在重建 28 次 / 68.3 万字，方案 B 4 次 / 9.1 万字，方案 A 3 次 / 7.0 万字（数字和实操文章不同是随机长度不同，省下的比例一致）。选的是方案 B，实际改法：
> - 起点只取 `TRIM_CHUNK = 20` 的整数倍，取能同时过两道闸的最小那个；落在回复上就往后挪到下一句我说的话；连最后一块都过不了字数闸（一块里夹着几段超长正文）才退回逐条丢；
> - **比文中方案多了一条「起点只往后挪」**：起点存进续接缓存（`turns.json` 的 `trim`），下一轮取「按规则算的」和「上一轮的」里大的那个。只有这样「免费窗口」才成立——缓存过期时顺手推过的那一块，下一轮要是按纯规则算回去，前缀又断一次。起点那条消息对不上（历史改过、梳理换了基点）这份记录就作废；
> - **免费窗口**：距上一轮超过 `CACHE_TTL_SEC = 300` 秒、且留下的已经占了一半预算时，再推一块；推完至少还留一整块，短对话过期了也不丢上下文；
> - #9 的前缀诊断单独记「裁剪起点动了」（顺手推的注明「缓存已过期，顺手推了一块」），不再混进「可见轮次对不上」；
> - 用例：原用例 `dropped == 18` → 20，补了起点落在回复上、超长正文兜底、短对话不裁；新用例在 50 条历史上连聊 20 轮，只有跨块边界那一轮重建（旧逻辑下这条会失败）；另一条验证过期推一块之后下一轮照常续上、起点不回退。

**现象：**
- `_fit_history`（`server/chat.py:1738`）超过 `MAX_HISTORY_CHARS = 24000`（`:57`）时，**从最早的一条开始逐条丢**；
- 续接缓存 `turns.resume`（`server/turns.py:74`）要求"上一轮存下的可见轮次"和这一轮的 `incoming[:-1]` 逐字相同；
- 存下来的可见轮次是**裁剪之后**的历史（`chat.py:2075`，`visible=[*history, answer]`）。

**后果：**
- 对话超过 24000 字以后，每新增一轮，开头就要多丢一两条。上一轮存的是"从第 k 条开始"，这一轮发来的是"从第 k+2 条开始"，对不上，于是**每一轮都走 `_rebuild` 整段重建**；
- ~~`_rebuild` 在第 1 条插入的提醒"之前还有 N 轮没带过来"里，N 每轮都在变，这条提醒本身也会让前缀对不上~~。**更正**：这条提醒只在 `_rebuild` 时插入，能续上的轮次用的是缓存里原样的列表，N 不会变，所以它不是原因；
- 两道闸都会触发：条数闸 `MAX_MESSAGES = 60`（约 30 轮）和字数闸 24000 字，按真实平均值差不多同时到达；
- 结果是长对话越往后，每一轮都在按约 1.25 倍价格重写整段缓存，而不是按约 0.1 倍价格读缓存。

**借鉴：**
- **Claude Code** 不用滑动窗口：一直往后追加，直到接近上限（有效窗口减 13k）才**一次性压缩**，压缩后前缀重新稳定（`services/compact/autoCompact.ts:62`）。重写只发生一次，而不是每一轮；
- **本仓库自己的原则**：《前缀缓存与Agent上下文架构》§7 写了"缓存死了的那一刻，是重排、压缩、归档唯一免费的窗口"，但 `turns.py` 和 `chat.py` 里还没有任何按 TTL 判断的逻辑。

**改法（推荐方案 B，模拟过）：**
- **起点按块取整**：起点只能取 `CHUNK`（20 条）的整数倍，取能同时满足两道闸的最小倍数。纯函数，不需要新状态；起点天然落在 user 消息上；
- 另一个选项是方案 A"超限一次裁到一半"：重建更少（3 次），但要把起点存起来；
- **利用免费窗口**：距上一轮超过缓存 TTL 时，缓存本来就已经过期，这时顺手把起点往前推，不多花钱。

**需要改和补的用例：**
- 现有用例 `chat_长对话按条数和字数两道闸裁_并且说出来` 里的 `dropped == 18` 会变成 20，断言改成"dropped 是 CHUNK 的倍数，并且裁完不超过两道闸"；
- 新用例：构造刚好越过上限的对话，连跑 10 轮，断言只有越过块边界的那一轮重建。

### 17. 一次性提示词里固定规则在可变内容之后，批量导入无法复用缓存

> 状态：未开始。**先量再定**：用 `llm-usage.json` 里导入类 op 的 token 数算一下，看规则部分能不能达到最小可缓存长度，以及批量导入实际用得多不多，再决定做不做。

**现状：**
- `ask()` 这类一次性调用只发一条 user 消息，**不打缓存标记**（`tools/knowrary/llm_backend.py:280-318`）。对单次调用来说这是对的：写缓存要多付钱，又没有下一次来复用；
- 但批量导入会用同一份 `prompts/article.md` 连续调用很多次，每次拆一篇；
- 这份模板一共约 7.9k 字，**只有开头约 2k 字是固定的**。从第 19 行开始插入 `{{relation_types}}`、`{{all_ids}}`、`{{related_nodes}}`、`{{article}}`，**`{{article}}` 之后还有约 4.9k 字固定规则**（拆分原则、输出格式等）；
- 所以每一篇文章的前缀在第 19 行就已经不一样了，后面那 4.9k 字规则每次都按原价重新计费。

**借鉴：** OpenClaw 的缓存分界：稳定内容在前、动态内容在后，在分界处打断点（`src/agents/system-prompt.ts:1291`）；Claude Code 把 system 拆成静态段和动态段（`utils/api.ts:321`）。

**改法：**
- 把固定规则整体挪到前面，放进 system，并在末尾打一个缓存断点；关系类型表、节点列表、文章本身这些可变内容放在断点之后；
- **只对批量类调用打标记**（导入队列、校验已有边），单次调用维持现状；
- **要注意的取舍**：Anthropic 对长文档的建议是"长材料放前面，问题和指令放最后"，这样指令遵循得更好。所以不要把末尾的指令全部挪走，在文章之后保留一两句简短的任务提醒，大段规则放进前面的缓存段。

### 18. 运行时兼容旧格式，迁移逻辑散在各处

> 状态：未开始。

**现状：** 读取数据的路径上带着好几处兼容旧格式的逻辑：
- `tools/knowrary/core/sources.py:12`、`:36`：旧的 `source: xxx.md`（单个字符串）"照读"，当成只有一项的 `sources`；
- `tools/knowrary/core/projects.py:50`、`:95`、`:114`：旧的 `plans.json` 在运行时按需迁移，还留着 `legacy_id`，注释写着"迁完可以删"；
- `tools/knowrary/core/pending.py` 的 `load_pending`：每次读取都用 `setdefault` 补齐缺失的字段。

**借鉴：** OpenClaw 的硬性规定（根目录 AGENTS.md）：**运行时只读当前格式**；旧格式由 `openclaw doctor --fix` 一次性迁移；运行时不保留兼容层和回退读取。

**改法：**
- 给 `knowrary check` 加一个 `--fix`，统一负责迁移：`source` 改写成 `sources`、`plans.json` 转成 projects、pending 补齐字段；
- 迁移完之后，删掉运行时的兼容分支；
- **和 OpenClaw 不同的一点**：md 是会在 Obsidian 里手写的。有人还按旧写法写 `source:` 时，`check` 要能检查出来并提示，不能静默吞掉。
