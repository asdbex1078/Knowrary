## 要求

1. **按面试的问法分 2～4 组**（例如「八股必问」「项目深挖」「场景设计」「手写与调试」），
   每组 5～10 个考点，整份不超过 30 个。组名要像面试轮次，不要像教科书目录。
2. **一个考点 = 一个能被独立追问的话题**。"熟悉 JVM"不是考点，"垃圾回收器的选择与停顿权衡"才是。
3. **`why` 写这个点为什么会被问、会问到什么深度**——这是整份清单最有价值的部分。
   直说，例如"几乎必问；只答出'标记清除'会被追问停顿从哪来、为什么 G1 要分 Region"。
   不要写"很重要""需要掌握"这种废话。
4. **上面「这份计划里已经有的点」和「已有的节点」里出现过的概念，必须原样复用那个 id**，
   不要另起近义的新名字（近义词会让同一个考点被准备两遍）。已经在这份计划里的，不用再列一遍。
5. `id` 同时是将来 Markdown 的文件名：**不能含空格**，也不能含 `/ \ : * ? " < > |`。
6. **`load`（负荷）三档**，按"准备到能在面试里答完整"要花多久估：
   `轻` = 一小时内；`中` = 半个下午；`重` = 要动手写或找项目例子，得一整天。
   这是我排时间表的唯一依据，别一律填「中」。**面试在即时，先保证 `重` 的点排得进去。**
7. **只列岗位要求真正指向的东西。** JD 里没提、也不是该岗位常识的，不要为了显得全面而塞进来——
   凑数的考点会占掉我真正该准备的时间。
8. **`field`（领域）**：这些考点将来落在哪个顶层领域。上面「已有的领域」里有合适的就复用，
   没有就起一个短名字（它会成为一个目录）。面试类建议用能和日常学习分开的名字，
   例如 `Java面试`——否则备考的点会淹掉我原有的知识主线。
