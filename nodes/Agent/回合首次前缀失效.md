# 回合首次前缀失效

## 描述

一个真跑了三天的 agent 账本（95 次成功调用）里最大的一块开销，
是一个**不报错的前缀失效 bug**。

## 核心内容

### 现象：真正烧钱的是"每个回合的第一次调用"

把 95 次成功调用按 `cache_read` 的形态分两类：

| | 次数 | cache_write | 占比 |
|---|---:|---:|---:|
| **回合首次**（`cache_read` = 恒定值） | 55 | **990,996** | **79%** |
| **回合内续发**（`cache_read` 递增） | 40 | 268,688 | 21% |

- **回合内**（几秒内的多次工具往返）：`cache_write` 均值 6,717，最低只有 297——只发增量。
- **回合首次**：`cache_write` 均值 **18,018**，等于把整段对话历史重写一遍缓存。

### 根因：两份消息列表构造性对不上

**前端每轮回传的是"可见轮次"（剥掉工具块的干净对话），而服务端内部那份还夹着工具往返。**

两份构造性地对不上，于是每个新回合的第一次调用必然重开前缀。

**不报错，答案全对，只有账单在涨。**

### 这一项值多少钱

`cache_write` 的定价是 1.25×，是 `cache_read` 的 12.5 倍。
55 次首发写掉的 **99 万** token，折成输入当量 **124 万**；
而同期**全部** cache_read 是 273 万 token，折成当量只有 **27 万**。

**光是"每个回合重开一次前缀"这一项，就比整整三天里所有被重发的历史加起来还贵 4.5 倍。**

### 修法

[[消息列表只增不改]] 的直接应用：

- 服务端按会话键留一份**完整**消息列表，新一轮只把最后那句话追加上去；
- 前端回传的那份降级成"证明这一段没被改过"的校验，对不上才整段重建。

## 线头

- 同一类的错：会变的东西（图谱快照之类）贴在队尾，贴一条就动一次前缀，所以没变就别贴。
- 这种 bug 只能靠**监控**发现，不能靠测试发现——功能全对。
