# 缓存过期窗口

## 描述

[[消息列表只增不改]] 说"改中间会打断前缀，所以别压缩"。这句话有个前提：**前缀还活着。**

一旦超过 TTL，前缀已经一文不值了——这时候压缩、归档、重排，**一分钱都不多花**。

## 核心内容

### 总纲

> **缓存活着的时候只增不改；缓存死了的那一刻，是重排、压缩、归档唯一免费的窗口。**

### 它给了"什么时候该归档"一个确定性触发器

不是问模型"相不相关"（见 [[相关性判断器反模式]]），而是**看一眼时钟有没有越过 TTL**。

越过了，继续带着历史就拿不到任何缓存红利，这时"留还是丢"退化成一个纯粹的
**内容价值**问题，跟成本无关了。

### 归档不必裸奔

把上一段的**最后一条回复 + 涉及的实体 id** 当一句状态摘要带上——
这些东西留档里现成就有，**不用额外调模型**，所以这个"压缩"是真的零成本。

### 判断"缓存死没死"要实测，不要查表

`usage` 里的 `cache_read_input_tokens` 是唯一的实锤。把它按
(provider, 距上次同 key 调用的间隔) 分桶，看它什么时候掉到 0，
就是这个 provider 在你的流量上的实际保温时长。

这比查表准（含平台实际负载的影响），而且上游改策略时你的数字自己就跟上了。
**一次读会免费把计时器续上**，所以实际保温时长常常远超标称 TTL——
跨 16 小时仍然命中是观察到过的。

## 线头

- 归档之后那段历史去哪：留档是过程不是知识，值得留的应该被拆成节点进图。
- "缓存还在不在"做成实测量而不是预测量，这条对多 provider 尤其要紧。
