# 工具错误说给模型听

## 描述

agent 循环里跑工具，会遇到三条非正常路径。**一条都不该抛异常**——
全都把话说给模型听，对话继续往下走。

**这是产品行为，不是异常处理。**

## 核心内容

### 三条路径

**一、调了白名单外的工具**

```python
fn = TOOLS.get(name) if name in allowed else None
if fn is None:
    return f"这一档口径下没有 `{name}` 这个工具。可用的是：{'、'.join(sorted(allowed))}。", {}
```

不报错，而且**把可用清单一起列出来**——否则模型只知道"不行"，不知道该改成什么。

**二、同参数重复调用**

真实对话里模型确实会用一模一样的参数再搜一遍，每重复一次就白烧一个来回。
第二次直接还回上次的结果，**并明说别再调了**：

> 这次调用和刚才那次一模一样，结果没变，不再跑一遍：…
> **直接用这个结果回答，不要再调工具了。**

**三、工具自己炸了**

告诉模型它炸了（让它能换个方式），同时**记一笔到出错流水**。

理由是：工具出错原来只在那一轮对话里闪一下，"这东西为什么老出问题"没有任何地方能回答。
攒起来才看得出规律——**而且工具反复出错往往说明工具本身有问题**，不是模型手滑。

### 为什么框架在这里不好用

通用框架的工具错误走的是协议级的异常/错误标记，默认要么往上冒、要么塞一句固定文案。
做成"说人话 + 列出可用清单 + 不中断"要去改它的错误分支。

而这三条恰恰是最该由产品自己定的：**每一条的措辞都会直接影响模型下一步怎么做。**

### 推论：工具返回值本身就是提示词

既然错误要说给模型听，那正常返回也一样——
工具结果里可以夹带纪律（"这不是全文，只准追加"、"别再调工具了"），
它们和系统提示词是同等地位的东西，只是出现得更及时。

## 线头

- 工具表和白名单必须同一份数据，见 [[工具定义单一数据源]]。
- 人点「停止」要和"工具出错"分开：中断不算出错，不该进出错流水。
