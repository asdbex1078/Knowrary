# 依赖选型判据

## 描述

"要不要上这个框架 / 这个库"是个反复出现的问题，而且每次都容易变成偏好之争。
把它变成判断的办法：**先把项目的核心约束写死，再数一个现成方案的默认行为和它们冲几条。**

## 核心内容

### 主判据：数冲突条数

- **冲 0～1 条** → **用现成的。**
- **冲 2 条以上** → **自己写。** 因为这时候你不是"用框架"，是"绕着框架写"——
  而绕的成本不会一次付清，它跟着框架每次升级再来一遍。

### 副判据：规模问题必须配一条能验证的触发线

向量库、数据库这类不是"对不对"的问题，是"到量没到量"的问题。

所以：**凡是以"现在还不需要"为理由拒掉的，必须同时写下一条能验证的触发线**
（"作答超过 1 万条"、"单次读取超过 50ms"、"出现第二个客户端"）。

否则"现在还不需要"会变成一句永远正确、永远不重新评估的话——
**而那种话在一份设计文档里比说错还糟，它看起来像结论，实际上只是没想。**

### 推论：越想决定你怎么组织代码的依赖，越容易撞上

翻回去看被接受的那些依赖，共同点很齐：
**它们都是"某一层的实现"，不是"整体的组织方式"。**

- HTTP 框架决定"一个请求怎么进来"，不决定你的领域模型长什么样；
- 画布库决定"鼠标拖动时元素怎么跟手"，不决定图里有什么；
- Markdown 渲染器决定 `**粗体**` 怎么变成 `<strong>`，不决定正文写什么。

而 agent 框架决定的是**循环怎么转、消息怎么攒、工具怎么绑**——那是组织方式。
ORM / 数据库决定的是**真值住在哪**——那也是组织方式。

> **一个依赖越想决定你的代码怎么组织，它和你的约束撞上的概率就越大。**
> 判据背后真正的东西不是"少用依赖"，是"**别把组织方式外包出去**"。

同一条推论解释了一个看起来矛盾的结果：**SDK 进来了，框架没有。**
SDK 是"帮你发一个 HTTP 请求"，框架是"帮你跑一个循环"——
前者不碰消息列表的形状，后者的全部价值就在于碰它。

### 判据要能输出"用"，否则它是偏好

如果这套尺子量什么都得出"自己写"，那它就不是判据，是托词。

检验办法是**专门记下被接受的那些依赖**，以及**被判定为"该做、还没做"的那些**
（见 [[MCP两个方向]]）。能说"不做"也能说"做"的尺子，才是尺子。

## 线头

- 每个决策按同一个格式记：结论 / 冲突点 / 代码级对照 / 触发线 / 代价。
- **"代码级对照"允许留空，"代价"不允许**——没撞过墙的选型写不出真对照，硬写就是编；
  但"放弃了什么"任何时候都答得上来，答不上来说明这个决策还没想清楚。
