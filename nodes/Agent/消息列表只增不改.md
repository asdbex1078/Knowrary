# 消息列表只增不改

## 描述

有前缀缓存时，**重发历史近乎免费，重开前缀才是账单大头**——所以 agent 的消息列表必须只增不改。

这条原则的全部依据是 [[Prompt-Caching]] 的一条不变量：

> **前缀缓存是前缀匹配。前缀里任何一个字节变了，它之后的全部失效。**

缓存键来自渲染后 prompt 的**精确字节**，一直算到每个断点。渲染顺序固定：
`tools` → `system` → `messages`。所以第 N 个位置上改一个字符（一个时间戳、一个重排过的
JSON key、一个多出来的工具），位置 ≥ N 的所有断点全部作废。

## 核心内容

### 只能追加，或者整个重来——不能廉价地改中间

| 你想做的 | 会发生什么 |
|---|---|
| 在末尾追加新消息 | ✅ 前面全部命中，只写新增那一小段 |
| 改写中间某几轮（压缩、摘要、删无关的） | ❌ 断点全废，整段重新写一遍 |
| 丢掉最早几轮 | ❌ 同上——丢头部也是改前缀 |
| 整段重开 | 付一次完整写入 |

### "压缩历史省钱"是个陷阱

把 20 轮旧对话换成 200 字摘要，token 数确实少了，但你**改写了中间**，
于是要为整段重新付一次 1.25× 的写入。

只有当"重写一次的代价 < 继续按 0.1× 重发的代价"时它才划算，而这需要历史长到相当程度。

**如果你的 agent 本来就给上下文设了上限**（比如"最多 60 条 / 24000 字"），
**那个上限本身已经是压缩了**，再叠一层摘要几乎必然是负收益。

### 为什么直觉会错

这两个方案——前面加个小模型判断相不相关、或者把旧历史压缩成摘要——
都建立在同一个隐含假设上：**token 按量计费，每个 token 一样贵。**

前缀缓存把这个假设打破了。同一批 token 有三种完全不同的价格
（命中读 0.1×、普通输入 1.0×、写入缓存 1.25×～2×）。
一旦知道这张表，"重发历史很浪费"这个直觉就站不住了：
**你想省的那一项是最便宜的一项，而"重新开始"这个动作命中的恰恰是最贵的一项。**

### 成本驱动是"开了多少次新前缀"，不是"单轮 prompt 多大"

这两件事很容易混：

- **单轮 prompt 的大小** 决定的是**会不会炸**（超上下文窗口）。分层加载、按需读取解决的是这个。
- **新前缀的次数** 决定的是**贵不贵**。

一个真实的对照：某个 agent 的账单里，`cache_write` 118 万 token、`cache_read` 261 万 token。
看 token 数是 1:2，看**钱**就反过来了——

```
cache_write:  118 万 × 1.25 = 147 万  ← 59% 的账单
输出:          15 万 × 5.0  =  77 万  ← 31%
cache_read:   261 万 × 0.1  =  26 万  ← 10%
```

**重发的历史只占 10%。** 而那 59% 全部来自"又开了一次新前缀"。

### 这条原则有一个例外窗口

"改中间会打断前缀"有个前提：**前缀还活着**。缓存死了之后重排、压缩、归档是免费的——
见 [[缓存过期窗口]]。

## 线头

- 三种后端（claude-cli 续会话、anthropic 缓存断点、openai 自动前缀缓存）省钱手段不同，
  但要的都是同一件事：前面那一截一个字都别动。
- 框架自带的 Memory / checkpointer 抽象的职责是"把历史存起来、下一轮重新组装"——
  **重新组装和字节级不变天然对立**。

### 为什么通用框架的 Memory 抽象在这里用不了

这条原则和 agent 框架自带的记忆层（`ConversationBufferMemory` 一类，以及图式框架的 checkpointer）
**职责本身对立**，不是"配置一下就好"的关系。

框架 Memory 干的事是"把历史存起来，下一轮**重新组装**成 prompt"。**重新组装**正是问题所在：

- 它会摘掉或压缩 tool 往返；
- 它会按自己的模板重排；
- `trim_messages` 一类的工具会从中间删。

前缀一变，显式缓存断点和自动前缀缓存**同时失效**。

> **省钱的机制要的是字节级不变，而框架 Memory 的职责恰恰是重新生成。**

同理，缓存断点要挂在**倒着数第一条非 system 消息**的**最后一个 content block** 上
（队尾那条会变的 system 要留在断点之后，而且 mid-conversation system 上打断点本身会 400）——
这种位置级的精确控制，在框架把消息抽象成对象、格式化藏在 integration 内部之后就够不着了。

**判断一个框架能不能用，数它的默认行为和你的核心约束冲几条**，见 [[依赖选型判据]]。
