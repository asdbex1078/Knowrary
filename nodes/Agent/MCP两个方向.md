# MCP 两个方向

## 描述

"要不要上 MCP"这个问题必须先拆成两个方向，**它们的答案相反**：

| 方向 | 谁调谁 | 结论 |
|---|---|---|
| **作 client** | 自己的 agent 通过 MCP 调自己的工具 | **不做。** 纯属额外一跳 |
| **作 server** | 别的 agent 客户端调你 | **该做。** 这才是它解决的问题 |

混着谈会得出"MCP 没必要"这个错结论——**它对内没必要，对外是正解。**

## 核心内容

### 作 client：多一跳，收益为零

工具全在自己进程里时，一次调用就是一次函数调用，和索引、缓存共享同一份内存。

换成 MCP，每次调用变成：序列化参数 → 写 stdio / 发 HTTP → 对面反序列化 →
**重新加载一次索引** → 序列化结果 → 读回来 → 反序列化。

调用方和被调方是同一个人写的、同一个进程、同一次部署。**换来什么？什么都没有。**

而且会弄丢三件现成的东西：

- [[工具错误说给模型听]] 那三条路径要在客户端侧重新翻译一遍；
- 工具结果里夹带的纪律得自己在 content 里拼——等于把现在这套原样搬过去，白搭一层协议；
- 工具执行**中途**推事件（"这张卡的 diff 算出来了"）推不出去，MCP 的返回是一次性的结构化结果。

### 作 server：它解决的是"能力绑在一个客户端上"

反过来，如果你的能力现在是靠**一份写给某个 agent 客户端的说明书 + 几条命令行**拼起来的，
那它隐含三个前提：**用的人是我、机器是这台、客户端是那一个**。
三条全成立时一点毛病没有，**任何一条不成立就得重写**。

MCP 换掉的就是这三条：

| | 手搓（说明书 + CLI） | MCP |
|---|---|---|
| 工具怎么被发现 | 说明书里写死绝对路径 | `tools/list` |
| 参数长什么样 | 散文描述 + `--flag`，模型照着拼命令行 | JSON Schema |
| 换台机器 | 改说明书里四处绝对路径 | 改一行配置 |
| 换个客户端 | **重写一份说明书** | 不用改 |

**后两行是全部理由。**

### 作 server 的真冲突点：授权模型错位

**硬闸是安全的**：乐观锁、指纹校验、字段白名单、路径白名单——
它们长在写回通道上，不管请求从哪来。

**错位在授权模型上**：

> 能力边界该写在**服务端**（见 [[工具定义单一数据源]]），
> 而 MCP 的授权模型是**客户端决定调哪个工具**。

两者不冲突（服务端仍可拒绝），但**"某一档口径不给某类工具"这种口径级的边界，
在 MCP 那一侧没有对应物**——除非把口径做成连接参数，每档起一个 server。

**所以真要暴露，该暴露没有口径的那一半**（只读 + 固定流水线），
带口径的那套留在自己进程里。

### 还有一半到不了：需要界面的那些

产物是"一张要人确认的卡片"的工具不该走 MCP——
卡片要渲染 diff、要人点那一下，到了别的客户端就只剩一段文本和一个 approve 按钮。

## 线头

- 判据本身见 [[依赖选型判据]]：MCP 作 server 是那套尺子里少见的"该做、还没做"。
- 真要暴露时，dry-run 的 diff 要尽量自解释——到了别人的客户端，那段文本就是全部界面。
